01 Kubernetes Cluster — Creation & Upgrade P1 · 70% weight

0/7

The client's #1 topic. Expect a live whiteboard walk-through, not a definitions quiz — be ready to draw the VPC-to-application flow from memory and narrate every hop.

This is the flow the client is listening for — say it in this order before diving into any one box:

VPC→ Public Subnets→ Private Subnets→ NAT Gateway→ EKS Control Plane→ Managed Node Group→ kubectl access→ Deploy app
  • VPC: one CIDR (e.g. 10.0.0.0/16) spanning at least 2–3 AZs for HA.
  • Public subnets: host the NAT Gateway and any internet-facing ALB. Tag kubernetes.io/role/elb=1 and kubernetes.io/cluster/<name>=shared so the AWS Load Balancer Controller can auto-discover them.
  • Private subnets: host the worker nodes — no direct public IP. Tag kubernetes.io/role/internal-elb=1.
  • IGW + route table on public subnets (0.0.0.0/0 → IGW); NAT Gateway + route table on private subnets (0.0.0.0/0 → NAT).
  • IAM: an EKS cluster role (trusted entity eks.amazonaws.com, policy AmazonEKSClusterPolicy) and a node role (AmazonEKSWorkerNodePolicy, AmazonEKS_CNI_Policy, AmazonEC2ContainerRegistryReadOnly).
  • Control plane + managed node group created against the private subnets.
  • kubeconfig and verification.
eksctl create cluster \
  --name prod-cluster --region ap-south-1 --version 1.29 \
  --vpc-private-subnets=subnet-aaa,subnet-bbb \
  --vpc-public-subnets=subnet-ccc,subnet-ddd \
  --nodegroup-name ng-1 --node-type m5.large \
  --nodes 3 --nodes-min 2 --nodes-max 6 --managed

aws eks update-kubeconfig --region ap-south-1 --name prod-cluster
kubectl get nodes -o wide
kubectl get pods -n kube-system   # coredns, aws-node, kube-proxy all Running
Likely follow-up: "Why private subnets for nodes?" — blast-radius reduction; nodes reach the internet only via NAT, egress-only, nothing inbound from the public internet directly.

Nodes in private subnets have no route to the internet except through the NAT Gateway, and no public IP at all — nothing on the internet can initiate a connection to a node. The NAT Gateway sits in a public subnet with an Elastic IP and translates outbound traffic from private-subnet resources (pulling images, calling AWS APIs, hitting external endpoints) so the reply routes back, without exposing the node's private IP externally.

  • One NAT per AZ in production (HA) — a single NAT is a single point of failure and a cross-AZ data-transfer cost.
  • VPC endpoints (S3 gateway endpoint, ECR/STS interface endpoints) reduce NAT data-processing cost for high-volume traffic like image pulls.
Likely follow-up: "What if NAT goes down?" — nodes lose egress (no new image pulls, no AWS API calls), but already-running pods with no external dependency keep serving. Exactly why multi-AZ NAT matters.

IRSA (IAM Roles for Service Accounts): EKS exposes an OIDC provider; you create an IAM role whose trust policy trusts that OIDC provider for a specific Kubernetes ServiceAccount (via annotation eks.amazonaws.com/role-arn). The pod using that ServiceAccount gets short-lived, auto-rotated AWS credentials injected — no static AWS keys stored in the cluster, and permissions scoped per-workload instead of one broad node-wide role.

Why it matters to the client: without IRSA, every pod on a node effectively inherits the node role's permissions if it can reach the instance metadata service — IRSA (with IMDSv2 + hop-limit hardening) is the standard least-privilege answer.

Two phases, always control plane first, only one minor version at a time (K8s doesn't support skipping — e.g. 1.27 → 1.29 needs a stop at 1.28):

Check deprecated APIs→ Upgrade control plane→ Upgrade add-ons→ Upgrade node group→ Validate 
aws eks update-cluster-version --name prod-cluster --kubernetes-version 1.29
aws eks update-nodegroup-version --cluster-name prod-cluster --nodegroup-name ng-1

A managed node group upgrade replaces nodes for you following its configured update config, but it's still cordon → drain → replace → uncordon under the hood — exactly why PodDisruptionBudgets and readiness probes matter (next question).

Likely follow-up: "What do you check before upgrading?" — a tool like Pluto or kube-no-trouble (or kubectl get pods -A -o yaml | grep apiVersion) to catch removed/deprecated API usage before it breaks post-upgrade.
kubectl cordon node-1                                    # stop new scheduling
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data   # evict pods gracefully
# replace / upgrade the node (new AMI or kubelet version)
kubectl get nodes                                         # confirm new node Ready
kubectl uncordon node-1                                    # allow scheduling again
  • cordon marks the node unschedulable — existing pods keep running.
  • drain evicts pods respecting PodDisruptionBudgets, terminating them gracefully (respecting terminationGracePeriodSeconds) so ReplicaSets reschedule them elsewhere first.
  • --ignore-daemonsets is required or the drain hangs — DaemonSet pods relaunch on the new node automatically instead.
Likely follow-up: "What if drain hangs?" — usually a PDB with minAvailable that can't be satisfied while draining, or a bare pod with no controller that drain refuses to evict without --force.

Four things working together — name all four, this is a favorite follow-up:

  • Multiple replicas spread across nodes/AZs (podAntiAffinity or topology spread constraints) so draining one node never removes every replica at once.
  • Readiness probes so the Service/LB only sends traffic to pods that are actually ready — a new pod isn't added to Endpoints until it passes.
  • PodDisruptionBudget (minAvailable or maxUnavailable) so drain/eviction is throttled and never takes availability below your floor.
  • RollingUpdate strategy on the Deployment (maxSurge/maxUnavailable) controlling how many new pods come up before old ones go down.
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels: {app: web}

Add-ons versioned independently, which must stay compatible with the new control-plane version: CoreDNS, kube-proxy, and the VPC CNI. Check compatible versions before upgrading nodes:

aws eks describe-addon-versions --addon-name vpc-cni --kubernetes-version 1.29
aws eks update-addon --cluster-name prod-cluster --addon-name coredns --addon-version <version>

Also worth naming: the version skew policy — kubelet can trail the control plane by a couple of minor versions depending on the release, which is why a mixed-version cluster mid-upgrade is still supported and safe, but shouldn't be left that way for long.

02 Kubernetes Networking P1 · 70% weight

0/7

Second-most-tested area. The client wants the actual packet path, not just service-type definitions — narrate the hop-by-hop flow first, every time.

Going through a Service (the normal case, since pod IPs are ephemeral):

Pod A→ CoreDNS→ Service (ClusterIP)→ Endpoints/EndpointSlice→ Pod B
  • Pod A resolves service-name.namespace.svc.cluster.local via CoreDNS to the Service's ClusterIP.
  • kube-proxy's iptables/IPVS rules on the node DNAT that ClusterIP to one healthy backend pod IP, chosen from the Endpoints/EndpointSlice object (kept in sync with pods matching the Service selector and passing readiness).
  • Same node: traffic goes through the node's local bridge/veth pairs directly, no extra routing hop.
  • Cross node: in EKS with the VPC CNI, pod IPs are real VPC IPs (assigned from ENIs), so cross-node pod traffic is native VPC routing — no overlay/encapsulation needed. Overlay CNIs (Flannel, some Calico modes) instead wrap the packet (VXLAN) or use BGP routing between nodes.
Likely follow-up: "What if you bypass the Service and hit the pod IP directly?" — works, but pod IPs churn on every reschedule, so nothing production-grade should hard-code them; that's precisely the problem Services solve.

Production example: Ingress + AWS Load Balancer Controller provisioning a single ALB with path-based routing across microservices and TLS via ACM annotation for the public web tier; a type: LoadBalancer Service with an NLB annotation for a Kafka/gRPC workload needing static IPs and raw TCP throughput; plain ClusterIP for internal-only service-to-service calls.

Likely follow-up: "Why not just use NodePort in production?" — no health-aware load balancing across nodes, ports are unmemorable/hard to firewall cleanly, and you'd still need something in front distributing across node IPs — you've just reinvented a worse LoadBalancer.

CNI (Container Network Interface) is the plugin contract that assigns each pod an IP and wires up its networking when the kubelet creates it. The AWS VPC CNI assigns pods real, routable VPC IPs directly from ENIs attached to the node (secondary IPs, or IP prefixes with prefix delegation for higher pod density) — no encapsulation, so pod traffic is native VPC traffic and shows up in VPC Flow Logs; security groups can (with security-groups-for-pods) apply directly to pods.

Overlay CNIs (Flannel, Calico in overlay mode) instead give pods IPs from a separate virtual CIDR and encapsulate pod traffic (VXLAN) to move it between nodes, decoupling pod networking from the underlying VPC — more portable across clouds, but with encapsulation overhead and less native visibility.

Likely follow-up: "What's the downside of the VPC CNI?" — IP exhaustion: each node can only hold as many pods as it has spare ENI secondary-IP slots (instance-type dependent); prefix delegation raises the ceiling significantly and is the standard mitigation.

kube-proxy runs on every node and programs the traffic rules that implement Services — it watches the API server for Service/Endpoints changes and keeps the node's packet-handling rules in sync.

  • iptables mode (default, most common): a chain of iptables NAT rules; matching is sequential, so lookup time grows roughly linearly with Service count — fine for most clusters.
  • IPVS mode: uses the kernel's IP Virtual Server, backed by a hash table — O(1) lookup regardless of Service count, plus more load-balancing algorithm choices. Better for very large clusters.
Worth naming: newer setups increasingly replace kube-proxy entirely with eBPF (Cilium) for lower overhead and richer policy/observability — mention it if the client is clearly infra-modernization focused.

Every pod's /etc/resolv.conf points at the kube-dns Service, which fronts the CoreDNS Deployment. A query for svc-name.namespace.svc.cluster.local is answered by CoreDNS's Kubernetes plugin, which reads Service/Endpoints objects from the API server (via watch, so it's always current) and returns the ClusterIP. Pods also get a shorter search-domain form (just svc-name within the same namespace) via the pod's DNS search list.

Likely follow-up: "What if CoreDNS itself is unhealthy?" — cluster-wide DNS failures, which is why CoreDNS should always run with 2+ replicas and its own PDB/HPA — it's a critical-path system component, not just another workload.

NetworkPolicy is a namespace-scoped allow-list for pod traffic — by default (no policy at all) every pod can talk to every other pod. Once any policy selects a pod for ingress or egress, that direction becomes deny-by-default except for what's explicitly allowed (selector-based, by pod label and/or namespace label).

Enforcement is a CNI responsibility, not a core Kubernetes feature — the object can exist without anything acting on it. Traditionally, the plain AWS VPC CNI did not enforce NetworkPolicy on its own, so teams paired it with Calico purely for policy enforcement; the VPC CNI has since added native, eBPF-based NetworkPolicy enforcement as an option, but Calico is still very common in the field. Always confirm which is actually running before assuming policies are enforced.

Likely follow-up: "Give me a default-deny example." — a policy with an empty podSelector: {} and no ingress rules, applied per namespace, then explicit allow policies layered on top per app.
kubectl run debug --image=busybox:1.36 --rm -it -- sh
# inside: nslookup my-service.my-namespace.svc.cluster.local

kubectl get pods -n kube-system -l k8s-app=kube-dns    # CoreDNS pods Running?
kubectl logs -n kube-system -l k8s-app=kube-dns         # errors, SERVFAIL, throttling?
kubectl get svc -n my-namespace my-service               # does the Service even exist / right name?
kubectl get endpoints -n my-namespace my-service          # any backing pod IPs at all?
cat /etc/resolv.conf   # inside the debug pod — confirm nameserver points at kube-dns ClusterIP

Common root causes, roughly in order of frequency: wrong namespace in the query, Service selector not matching any pod's labels (empty Endpoints), CoreDNS under resource pressure/CrashLoop, or a NetworkPolicy blocking egress to port 53.

03 Kubernetes Security P1 · 70% weight

0/8

Expect a layered answer, not a single control. Structure every security answer as: cluster → network → workload → supply chain → runtime.

Give it in layers — the structure itself signals seniority:

  • Cluster: private API endpoint (or restricted public CIDR allow-list), RBAC least privilege, encrypted etcd/Secrets at rest (KMS envelope encryption).
  • Network: NetworkPolicy default-deny + explicit allow, Security Groups, mTLS via service mesh if present.
  • Workload: non-root, read-only root filesystem, dropped capabilities, resource limits, no privileged containers.
  • Supply chain: image scanning (Trivy) in CI, signed images, admission control blocking unscanned/unsigned images.
  • Runtime: Falco for anomalous syscall detection, audit logging enabled and shipped off-cluster.
  • Compliance: CIS Kubernetes Benchmark via kube-bench, regular access reviews.

Likely follow-up: "When would you use a ClusterRole bound with a RoleBinding instead of a plain Role?" — reusing a common permission set (e.g. "view") across many namespaces without redefining rules each time.
  • Never run workloads on the default ServiceAccount in a namespace — create a dedicated SA per app with only the RBAC it needs.
  • Set automountServiceAccountToken: false on pods/SAs that never call the K8s API — removes a token that's otherwise sitting in every container by default.
  • For AWS permissions, tie the SA to an IRSA IAM role (Chapter 1) instead of broad node-level IAM permissions.
  • Bound service account tokens (time-limited, audience-scoped, since K8s 1.22+) reduce blast radius vs the old non-expiring Secret-based tokens.

ConfigMaps hold non-sensitive config; Secrets are meant for sensitive data — but a Secret is only base64-encoded, not encrypted, by default. Anyone with get RBAC on that Secret (or etcd access) can trivially decode it. Two things actually make it secure:

  • Encryption at rest: enable envelope encryption of Secrets in etcd via KMS (EKS supports this natively).
  • Tight RBAC on who can get/list Secret objects — usually the bigger real-world gap.

For production-grade secret management, most architects expect an external secrets manager (AWS Secrets Manager or Vault) paired with the External Secrets Operator, which syncs secrets into the cluster and supports rotation — rather than hand-managing raw Secret manifests.

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
  seccompProfile: {type: RuntimeDefault}
  • runAsNonRoot / runAsUser — a compromised process shouldn't get root inside the container, limiting container-breakout impact.
  • readOnlyRootFilesystem — malware/tampering can't write to the container's own filesystem; app writes go to an explicit mounted volume instead.
  • allowPrivilegeEscalation: false — blocks setuid-style privilege escalation inside the container.
  • capabilities.drop: [ALL] — strips Linux capabilities the process almost never needs, add back only the one or two it truly requires.

These are also exactly what Pod Security Admission (the "restricted" standard) enforces at the namespace level, replacing the deprecated PodSecurityPolicy.

They sit in the API request path (ValidatingAdmissionWebhook/MutatingAdmissionWebhook) and enforce policy-as-code before an object is persisted — turning security requirements from "documentation" into something mechanically impossible to violate. Typical policies: deny privileged containers, require resource requests/limits on every pod, require specific labels for cost allocation, deny :latest image tags, restrict allowed image registries to your trusted ECR.

Likely follow-up: "Gatekeeper vs Kyverno?" — Gatekeeper policies are written in Rego (OPA's policy language, steeper learning curve, very expressive); Kyverno policies are plain Kubernetes YAML (faster to adopt for teams already fluent in K8s manifests).
  • Scan on build (Trivy in CI) and again scan on push (ECR scanning) — fail the pipeline on CRITICAL/HIGH CVEs above threshold.
  • Sign images (cosign/Sigstore) and enforce signature verification at admission — unsigned images simply can't run.
  • SBOM (software bill of materials) for auditability of exactly what's in a running image.
  • Falco operates after all of that, at runtime — it watches syscalls (via eBPF) for anomalous behavior a scan can't catch: a shell spawned inside a container that never should spawn one, an unexpected outbound connection, a write to a sensitive path. It's the detective control for the "scanning missed it or it's a zero-day" case.

Credential-harvesting bots scan GitHub's public event stream continuously and can find a leaked AWS key within minutes of a push — CI/CD scanning alone is too late, because by the time a pipeline runs, the secret is already in git history and possibly already seen. The fix is layered, each layer catching what the one before it misses:

git-secrets pre-commit hook→ GitHub push protection→ Secrets Manager (never in code)
  • Layer 1 — pre-commit hook (git-secrets): blocks the commit on the developer's own machine, before it ever leaves — but it's bypassable with git commit --no-verify, so it stops accidents, not deliberate bypasses.
  • Layer 2 — GitHub secret scanning + push protection: server-side backstop; rejects the push itself if a recognizable secret pattern is detected, even if Layer 1 was skipped or never installed on that machine.
  • Layer 3 — a real secrets manager (AWS Secrets Manager/Vault): the actual fix — if the credential is never in code at all, there's nothing to leak regardless of what slips past the first two layers.

If a key does leak, the runbook is time-critical — every minute it's valid is more exposure:

aws iam delete-access-key --access-key-id AKIAXXXXXXXXXXXXXXXX     # 1. revoke first, before anything else

aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAXXXXX \
  --query 'Events[*].{Time:EventTime,Event:EventName}'              # 2. audit blast radius

git filter-repo --path secrets.env --invert-paths --force            # 3. purge from git history
git push origin --force --all --tags                                  #    (coordinate — this rewrites history for everyone)

# 4. rotate every credential the leaked key could have touched, not just the one key
# 5. file an AWS Support billing case — unauthorized-access charges are often refunded if you act fast
Likely follow-up: "Why still revoke it if you already deleted the file?" — deleting the file doesn't remove it from git history; any past commit still has it in plaintext until git filter-repo (or BFG) actually rewrites history, and by then bots may already have it. Treat anything that touched a public repo as compromised the moment it's pushed, not when someone notices.

04 Kubernetes Troubleshooting P1 · most important

0/6

The client called this "most important." For every scenario, narrate the diagnostic sequence, not just the final cause — that's what's actually being graded.

kubectl get pods                      # confirm status + RESTARTS count
kubectl describe pod <pod>            # Events: OOMKilled? failing probe? image pull error?
kubectl logs <pod>                    # current attempt's output
kubectl logs <pod> --previous         # the crash BEFORE this restart — usually the real clue

--previous is the detail people forget: the current container may be freshly restarted with no logs yet, but the previous instance's logs show exactly why it died. Common root causes in rough order of frequency: missing/wrong env var or config, an overly aggressive liveness probe killing a slow-starting app, OOMKilled (check describe pod for reason, then compare memory limits against actual usage), or a dependency (DB, downstream API) unreachable at startup.

Likely follow-up: "How do you tell OOMKill apart from a probe failure?" — describe pod shows Last State: Terminated, Reason: OOMKilled explicitly for the former; a probe failure shows up as repeated "Liveness probe failed" Warning events instead.

kubectl describe pod Events again — the scheduler tells you exactly why it can't place the pod:

  • "Insufficient cpu/memory" — no node has room; needs Cluster Autoscaler/Karpenter to add capacity, or the request is oversized.
  • Unbound PVC — check PVC status, whether the StorageClass/provisioner exists and can actually provision in that AZ.
  • Taints without a matching toleration — e.g. dedicated GPU nodes tainted, pod has no toleration for it.
  • nodeSelector/affinity that doesn't match any node's labels — typo or a label that was never applied.
kubectl get nodes                     # confirm NotReady + how long
kubectl describe node <node>          # Conditions: MemoryPressure / DiskPressure / PIDPressure / NetworkUnavailable
# SSH or SSM into the node:
systemctl status kubelet
journalctl -u kubelet -f
df -h                                  # disk pressure?
systemctl status containerd
# check node-to-control-plane connectivity / security group rules

The control plane marks a node NotReady after it misses heartbeats for node-monitor-grace-period (default 40s), and starts evicting its pods after pod-eviction-timeout (default 5 min) if it stays unreachable — that eviction timer is worth naming, it's exactly why "one node down" doesn't mean instant pod loss.

Grafana/Prometheus→ Pod CPU/Mem→ Downstream (DB/API)→ Recent deploy?
  • kubectl top pod / kubectl top node and the Grafana dashboards for CPU throttling (container_cpu_cfs_throttled_periods_total — not the same signal as raw usage) and memory trend.
  • HPA status — is it scaling as expected, or maxed out at its ceiling?
  • Database — connection pool exhaustion, slow query log, lock contention.
  • kubectl rollout history — did the slowdown start right after a deploy? Correlate the timestamp.
  • Noisy-neighbor — another pod on the same node hogging shared resources.
Likely follow-up: "CPU limit is set but usage looks fine — still slow?" — check throttling metrics specifically; a container can look "under its limit" on average while still getting throttled in short CFS periods, which shows up as latency, not as an obvious usage spike.
  • ImagePullBackOff: wrong image tag/typo, private registry without an imagePullSecret (or an expired ECR token), or a network path issue reaching the registry from private subnets (missing VPC endpoint/NAT).
  • PVC stuck Pending: kubectl describe pvc — no StorageClass matches, the provisioner isn't running, or (for EBS) the pod is scheduled in an AZ where the requested volume can't attach — usually a topology/zone mismatch between the StorageClass's volumeBindingMode and the pod's actual AZ.

kubectl get pods --show-labels        # compare against the Service's selector exactly

05 Helm Charts P1 · 70% weight

0/5

"Client loves scenarios" — expect them to push past definitions into override precedence, rollback mechanics, and secret handling.

Chart.yaml→ values.yaml→ templates/*.yaml→ _helpers.tpl→ charts/ (subcharts)
  • Chart.yaml: metadata — name, chart version, appVersion, dependencies.
  • values.yaml: the default configuration every template reads from.
  • templates/: the actual K8s manifests, written with Go templating ({{ .Values.image.tag }}) plus Sprig functions.
  • _helpers.tpl: reusable named templates (e.g. a standard label block) to avoid repeating the same snippet in every manifest.
  • charts/: subcharts/dependencies for umbrella-chart patterns.

Why: it separates configuration from manifest logic — the same chart deploys to dev/staging/prod just by swapping values, instead of editing templates (unreviewable, error-prone, defeats the point of templating).

helm install myapp ./mychart -f values-prod.yaml --set image.tag=1.2.3

Precedence (lowest to highest): chart's default values.yaml → -f file(s), applied left-to-right so the last one wins → --set flags, which always win over any file.

helm upgrade myapp ./mychart -f values-prod.yaml --set image.tag=1.3.0 --atomic
helm history myapp
helm rollback myapp 4

--atomic rolls the release back automatically if the upgrade fails health checks — without it, a failed upgrade can leave the release in a broken, half-applied state that needs a manual helm rollback. helm history lists every revision so you know exactly which number to roll back to.

Never plaintext secrets in values.yaml committed to Git. Standard options: the helm-secrets plugin encrypting values with SOPS, Sealed Secrets (encrypt client-side, only the controller in-cluster can decrypt), or — most common at scale — keep secrets out of Helm entirely and let the External Secrets Operator pull them from AWS Secrets Manager/Vault directly into the cluster, with the chart only referencing the resulting Secret name.

Two proven patterns, pick based on how similar the services are:

  • One chart per service + a shared library chart (Helm's type: library) providing common templates/helpers (standard labels, probes, security context) — best when services genuinely differ in shape.
  • Umbrella chart with each service as a subchart dependency — best when one helm install should stand up the whole stack together.

In practice, most orgs land on "one generic chart, many values files" — a single templated chart parameterized enough to serve every stateless microservice, with each service just supplying its own values-<service>.yaml. Far less template duplication to maintain than either extreme.

06 GitOps — ArgoCD P1 · 70% weight

0/5

Marked "must know." Get Auto Sync / Self Heal / Prune exact and crisp — these three get mixed up constantly and it's an easy tell of real experience.

Git (desired state)→ ArgoCD (watches & compares)→ Sync→ Kubernetes (actual state)

Git is the single source of truth for what the cluster should look like. An operator (ArgoCD) continuously compares Git's desired state against the cluster's live state and reconciles any drift. Everything is declarative, versioned, and auditable — rollback is just "go back to an older commit," and every change has a PR trail.

Jenkins = CI — build, test, package, push the image, update the manifest/values with the new tag. It's push-based: it has to push into the cluster or into Git.

ArgoCD = CD — pull-based: it watches Git and pulls/applies changes itself; cluster credentials never need to live inside the CI system. That separation is the real answer the client wants — it's a security boundary (CI can't accidentally or maliciously touch the cluster directly) as much as a workflow split.

  • Auto Sync: applies Git changes to the cluster automatically the moment drift is detected, instead of waiting for a manual "Sync" click.
  • Self Heal: if someone kubectl edits a resource directly in the cluster, ArgoCD detects that drift and reverts it back to match Git — automatically, without anyone asking it to.
  • Prune: if a resource is removed from the Git manifests, ArgoCD deletes the corresponding live resource instead of leaving it orphaned — keeps the cluster in exact 1:1 sync with Git.
Likely follow-up: "Would you enable all three in production day one?" — Self Heal + Prune are powerful but unforgiving; most teams enable Auto Sync first, prove it out, then turn on Self Heal/Prune once they trust the manifests are complete and reviewed (an accidental Prune can delete something no one meant to remove from Git).
argocd app history myapp
argocd app rollback myapp <revision-id>

11 FinOps — Kubernetes Cost Optimization P5

0/10

The client shared a FinOps article directly — they expect you to connect cost to reliability, not treat them as separate topics.

Structure the answer as a priority-ordered list, not a random pile of tactics — this is what separates a senior answer from a checklist recital:

  • 1. Right-size first — usually the single biggest, lowest-risk win; most clusters run requests 2-3x actual usage "just in case."
  • 2. Autoscaling — HPA so replica count tracks real demand instead of being pinned at peak sizing 24/7; Cluster Autoscaler/Karpenter so node count tracks pod demand.
  • 3. Spot for the right workloads — stateless, fault-tolerant, batch — often 60-90% cheaper for that slice of the fleet.
  • 4. Clean up orphaned resources — unused PVCs, unused LoadBalancers, idle dev/test environments left running 24/7.
  • 5. Commit for the baseline — Reserved Instances/Savings Plans once the true steady-state floor is known (only after right-sizing, or the commitment locks in an inflated number).
Likely follow-up: "How do you make sure this doesn't hurt availability?" — every step above is additive to existing PDBs/readiness probes/multi-AZ design (Chapter 1), not a replacement for them; cost work should never touch availability guardrails.

Use real historical usage — Prometheus/kubectl top data over a representative window (including peak, not just average) — rather than guessing. The Vertical Pod Autoscaler can generate sizing recommendations automatically in "recommendation-only" mode without actually resizing anything live, a safe way to surface the gap between requested and actual usage across a whole cluster at once. Over-provisioned requests waste reserved node capacity; under-provisioned requests cause throttling (CPU) or OOMKills (memory) — right-sizing is a balance, not a race to the bottom.

Cluster Autoscaler scales predefined Auto Scaling Groups up/down based on pending pods — the instance types/node group shapes are decided in advance. Karpenter provisions nodes directly, just-in-time, picking the instance type and size that best fits the actual pending pod's requirements (bin-packing aware) — no pre-defined node groups needed, faster provisioning, and native, first-class Spot support. Most new EKS builds default to Karpenter now for exactly that efficiency gain.

  • Only for workloads that tolerate interruption — stateless, multiple replicas, quick to reschedule.
  • Diversify instance types/sizes in the node group — reduces the odds of many nodes being reclaimed simultaneously.
  • Run the Node Termination Handler (or Karpenter's built-in equivalent) to catch the 2-minute interruption notice and cordon/drain gracefully before the instance disappears.
  • Keep PodDisruptionBudgets in place — Spot interruption is still a disruption event PDBs should govern.
  • Mix with On-Demand/Reserved via node group weighting so a bad Spot market doesn't take out capacity entirely.

ResourceQuota caps total CPU/memory/object count per namespace; LimitRange sets default and max per-pod requests/limits within it — together they stop one team's misconfigured deployment from starving the whole cluster. For visibility, tools like Kubecost or OpenCost attribute real cost per namespace/label back to the AWS bill, enabling chargeback or at least showback — teams behave very differently once they can see their own number.

For a SaaS platform, cluster spend is Cost of Goods Sold, not just an engineering line item — every dollar saved on infrastructure drops straight to gross margin. A platform going from, say, 40% to 60% gross margin by cutting infra cost from $6M to $4M on flat $10M revenue is the kind of number that gets a platform team a seat at the leadership table, and it's the framing that makes a FinOps initiative fundable in the first place.

Visibility means being able to answer, per namespace/team/service: what does this workload actually cost, not just what does the whole cluster cost. Without that breakdown, nobody can be held accountable for their own consumption, and nobody has the information needed to optimize it.

A cluster can show nodes at high pod-count while still running at 30% CPU / 35% memory utilization — pods are scheduled across many nodes without being packed efficiently, so you're paying for capacity that's never actually used. Better bin-packing (letting the scheduler consolidate workloads onto fewer, fuller nodes rather than spreading them thin) directly reduces the node count needed to run the same workload — Karpenter's just-in-time provisioning (Chapter 11, Q3) already optimizes for this by design, which is exactly why it tends to beat a statically-sized Cluster Autoscaler node group on cost.

Automate the schedule — scale non-prod environments down (or to zero) outside working hours instead of leaving them running around the clock for convenience. A simple 9 AM–7 PM active window, suspended nights and weekends, is a very common, very cheap win on non-prod spend specifically, with no availability risk at all since nothing there is customer-facing.

  • Orphaned PVCs left behind after a workload is deleted — nothing deletes the underlying volume automatically unless the reclaim policy and cleanup automation are set up for it.
  • Oversized allocations — provisioning far more capacity than the workload will ever use.
  • Wrong storage class for the workload — expensive SSD-backed storage for something that's really just logging/archival data that would be fine on standard disks.

The fix is matching storage class to actual performance need (high-I/O databases get SSD, cold/archival data doesn't) plus routine automated cleanup of anything orphaned.

Governance: make it a hard rule that every workload defines CPU/memory requests and limits before it can deploy at all (enforced via admission policy — Chapter 3, Q6 — not a wiki page), plus namespace-level budgets so a team's spend has a visible ceiling.

Culture: the bigger lever, longer-term — expose cost per API request, per tenant, per microservice back to the engineers who own that service. Developers who can actually see the financial impact of their own architecture choices start designing more efficient systems on their own, without being told to; cost awareness becomes a design input instead of an afterthought bolted on by a platform team after the fact.

13 Bonus — AI/ML Platform Engineering not in the original blueprint

0/6

Not part of the client's stated blueprint, but good breadth if the conversation drifts toward where platform engineering is heading — DataOps, MLOps, and AIOps as one system rather than three separate stacks.

Traditional monitoring is built around the idea that a problem throws an error: latency spikes, an error rate crosses a threshold, an alert fires. AI systems fail differently — a model can be technically healthy (fast, up, low error rate) while being business-wise wrong, and that kind of failure is silent. A fraud model trained on last year's patterns, a recommender that slowly drifts stale as behavior shifts, a churn model thrown off by a seasonal change — none of these throw an exception, they just quietly lose accuracy.

That's why AI observability needs three layers instead of one: data (drift, schema changes, missing values), model (accuracy over time, prediction distribution, bias/fairness), and system (the traditional latency/throughput/error-rate layer). Watching only the third layer is exactly how a model degrades for weeks before anyone notices.

DataOps (raw → governed data)→ MLOps (features → deployed models)→ AIOps (telemetry → auto-remediation & retrain triggers)

Each loop can be built as its own stack, but the value compounds only when they share a registry, a common observability plane, and one governance contract. Run them as three disconnected efforts and you get exactly the failure mode most orgs hit: models trained on data nobody trusts, deployed through heroics instead of a paved road, monitored by a system that can't see model behavior at all — three siloed tools, no closed loop, and audit prep that takes weeks because lineage lives in three different places.

  • Lineage: every model traceable to its code commit, training-data snapshot, hyperparameters, and evaluation metrics — the ML equivalent of a build provenance record.
  • Staged promotion: dev → staging → prod with automated gates, not a manual heroic push to production.
  • Canary/shadow deployment: a new model competes against the incumbent on live traffic before it's trusted with 100% of it — the same instinct as Argo Rollouts canary analysis (Chapter 7, Q4), applied to models instead of application code.
  • Event-driven retraining: drift detected → pipeline triggered → candidate registered → A/B tested → promoted on a win, not on a calendar schedule.

Tiering is the governance decision that makes all of this affordable: Tier 1 (revenue/safety-critical) gets a human approval gate and full audit trail; Tier 2 (internal decisioning/recommendations) gets automated canary and monitoring; Tier 3 (experimental, low blast radius) can auto-promote on a metric win. Applying Tier-1 rigor to every model is over-engineering; applying Tier-3 looseness to a revenue-critical model is the incident waiting to happen.

Collect→Correlate→ Detect→Diagnose→ Heal
  • Collect: telemetry across every service and every model — metrics, logs, traces, predictions, feature distributions, not just infra signals.
  • Correlate: topology-aware grouping and dedup collapse a large volume of raw alerts down to a much smaller number of actual incidents — this is where most of the "alert fatigue" problem actually gets solved.
  • Detect: anomaly models (forecasting, outlier detection) catch drift that a static threshold would miss entirely, ideally with real lead time before customers notice.
  • Diagnose: causal inference over the service dependency graph points at a root cause automatically instead of a human tracing it by hand.
  • Heal: pre-approved playbooks execute automatically — scale, roll back, reroute — with a human gate retained only for the highest-risk (Tier 1) changes.

The loop only counts as AIOps, rather than "monitoring with extra steps," when the same telemetry that triggers an incident can also trigger a model retrain when the root cause turns out to be drift.

The business layer is the one platform teams most often skip, and it's the one leadership actually asks about — MTTR and accuracy numbers only matter to the extent they move a number the business already tracks.

Quantify the loop, not the experiment — model accuracy alone never convinces a CFO. The numbers that do: MTTR (a documented case reported roughly 4 hours down to under an hour), alert volume (thousands of raw alerts per day collapsed to a couple hundred grouped incidents through correlation), deploy frequency going up rather than down as governance is added, and audit prep time collapsing from weeks of senior engineer time to hours once lineage and access logs live in one place instead of scattered across disconnected tools.

Likely follow-up: "Isn't this a huge platform team investment?" — yes, and that's exactly why model tiering (Q3) matters: it's what stops the investment from being uniform (and therefore wasteful) across every model regardless of how much that model actually matters to the business.

Each chart defines its own Ingress with a unique hostname, but all reference the same ingress class (nginx) — so all 10 share a single ingress controller and a single external IP/load balancer, instead of provisioning 10 separate load balancers. On the DNS side: 10 CNAME/A records (Route 53 / Azure DNS) all pointing at that one external IP. Install the AWS Load Balancer Controller via Helm — it watches for Ingress resources annotated kubernetes.io/ingress.class: alb and provisions the ALB automatically. Each Helm chart's Ingress (unique hostname) becomes one listener rule on that shared ALB, each forwarding to its own target group. Route 53 gets one alias record per hostname, all pointing at the same ALB DNS name; TLS is a single ACM certificate attached to the listener. Target type is typically ip mode, for direct pod targeting.

Browser DNS lookup→ Route 53 → ALB DNS name→ ALB listener (443)→ Listener rule matches host→ Target group→ Pod

Route 53 resolves abc.com to the ALB's DNS name; the request hits the ALB listener; the ALB evaluates its listener rules and matches on the abc.com host header, forwarding to the corresponding target group; the target group holds pod IPs registered by the AWS Load Balancer Controller; the pod processes the request and the response retraces the same path.

Key distinction worth stating explicitly: in ip target mode, the ALB bypasses kube-proxy entirely and hits pods directly. In instance target mode, traffic lands on the node first, and kube-proxy forwards it to the pod via the Service — an extra hop that ip mode skips.

resource "azurerm_kubernetes_cluster_node_pool" "pools" {
  for_each              = var.node_pools
  name                  = each.key
  kubernetes_cluster_id = azurerm_kubernetes_cluster.aks.id
  vm_size               = each.value.vm_size
  node_count            = each.value.node_count
  mode                  = "User"
}

for_each gives each pool a stable identity in state, keyed by name — see Q10 for why that matters.

count is integer-indexed (count.index) — fine for a set of truly identical resources. for_each is map/set-keyed (each.key, each.value) — the right choice for named, distinct resources like node pools.

The concrete reason it matters: with count, removing an item from the middle of the list shifts every subsequent index down by one — Terraform sees that as every one of those resources changing identity, and destroys and recreates all of them, not just the one you removed. With for_each, each resource is tracked independently by its key, so removing pool2 only touches pool2.

Scenario: S3 Public Bucket Remediation

Discovery→ Design (API layer)→ Migration / cutover→ Lock down bucket→ Config-as-code going forward
  • Phase 1 — Discovery: use CloudTrail S3 access logs and CloudWatch to identify every consumer of the bucket; map which applications/services/external systems actually read the file, and classify the data's sensitivity before touching anything — you can't safely cut off access you haven't mapped.
  • Phase 2 — Solution design: build an API service as the new access layer — consumers → API Gateway → backend service → private S3 bucket. The bucket policy is updated to allow access only from the backend service's IAM role, and public access block gets enabled at this point (on the plan, not yet enforced).
  • Phase 3 — Migration & cutover: deploy the API to lower environments first and validate every consumer against it; update all consumers to call the API instead of hitting S3 directly; run both paths in parallel during the transition, using CloudTrail to confirm direct S3 access has actually dropped to zero before flipping the public access block on for real.
  • Phase 4 — Ongoing (new environment onboarding): treat the JSON file as config-as-code in Git from here on — a new environment entry is a PR, peer-reviewed, pipeline-validated against a schema (and checked for duplicates), then CI/CD deploys the update to the API service. Never hand-edit S3 and the API service separately in two places — Git is the single source of truth and the pipeline is what keeps both in sync.
Likely follow-up: "Why not just lock the bucket down immediately on day one?" — because you don't yet know who's consuming it; an immediate lockdown without discovery first is how you turn a security fix into an outage. Discovery always comes before enforcement.
