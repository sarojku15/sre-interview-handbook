CI/CD mechanics, Jenkins, Kubernetes basics, Docker, Helm. All squarely in your wheelhouse across every role on your resume.

"I've built and run Jenkins pipelines across every role I've held, most recently helping cut deployment cycle time by 25% in my current work supporting Azure Synapse-adjacent services. My default is a declarative Jenkinsfile: checkout, build — Maven for the Java-based services — a SonarQube quality gate, Docker build, push to JFrog Artifactory, then deploy. The deploy stage's mechanics depend on the target: helm upgrade --install against EKS or AKS for containerized workloads, sometimes fronted by ArgoCD for GitOps; for the legacy Apache/WildFly/Lucee estate I supported for years at Sandals Resorts, deploy went through Rundeck, which we used specifically to standardize deployments and cut manual effort by about 60%."
"A shared library is what stops you copy-pasting the same 200 lines of Jenkinsfile across a dozen repos. You define it as its own Git repo, with a vars/ directory holding custom pipeline steps as Groovy files — and a src/ directory if the logic needs to be more than a simple step. You register it in Jenkins' global config, or reference it inline with @Library('my-shared-lib') _ at the top of a Jenkinsfile, and from there every pipeline that needs it just calls the step by name — say, a buildAndScan() that wraps Maven build, SonarQube, and the JFrog push into one call. With as many services as I was standardizing CI/CD across during the Sandals containerization work, that's exactly what keeps pipeline maintenance from becoming its own job."
"Two different worlds, and I paired the tooling to match rather than forcing one tool everywhere. The containerized Java and Lucee applications I migrated at Sandals Resorts went Docker build to Kubernetes deploy via Helm, with Jenkins and GitHub Actions driving the pipeline. The legacy application-server estate — Apache, Nginx, WildFly, GlassFish, ColdFusion and Lucee before they were containerized — deployed through Rundeck, which gave us a controlled, auditable deployment surface without needing everything containerized first. That combination is also exactly why the migration mattered — moving from Rundeck-driven VM deploys to Helm-driven Kubernetes deploys directly improved rollback capability, which is called out on my resume for a reason: rolling back a bad legacy VM deploy was a much slower, riskier process."
"'Pipeline runs' and 'build succeeds' aren't the same claim, and the gap is usually one of a few things: a flaky or environment-dependent test that passes locally but not in the CI runner's exact JDK/dependency version; a SonarQube quality gate configured to warn instead of actually fail the stage, so a real regression sails through looking green; a Maven dependency resolution issue where a snapshot got overwritten upstream between runs; or the one that costs the most time to catch — a credential or token that silently expired, registry push auth especially, so the pipeline 'completes' but the artifact never really landed where it should have. My instinct from the SRE side is the same as any incident — check the stage-level logs before assuming the code is at fault, because a surprising number of 'build failures' are actually pipeline plumbing failures."
"A webhook is what lets GitHub push an event to Jenkins instead of Jenkins having to poll the repo on a timer. Push a commit or open a PR, GitHub fires an HTTP POST to Jenkins' webhook endpoint, and that triggers the corresponding job immediately rather than waiting for the next poll interval. That's what makes CI feel instant instead of laggy, and it's been standard in every pipeline I've built with GitHub Actions and Jenkins working together."
"With Terraform I provision the managed control-plane resource — aws_eks_cluster on AWS, azurerm_kubernetes_cluster on Azure — plus the node group or node pool resource for the workers, wired together with the VPC/VNet, subnets, and IAM roles Terraform also manages. That's core to how I provisioned and managed cloud infrastructure at Sandals Resorts — infrastructure-as-code end to end, no manual console changes. On what each half does: the control plane — API server, etcd, scheduler, controller-manager — is what makes decisions, where pods go and what state the cluster should be in, and on EKS or AKS that whole layer is managed for you, which is a big part of why I lean on managed Kubernetes over self-hosting the control plane. The worker nodes are where kubelet, kube-proxy, and the container runtime actually run the pods the control plane decided on."
"These come up constantly once you're running real production workloads on Kubernetes, which is exactly where I was after the Java and Lucee containerization at Sandals Resorts. For CrashLoopBackOff, my sequence is kubectl describe pod first — the Events section almost always tells you the category before you've read a single log line — then kubectl logs --previous specifically, since the current container instance may have no logs yet if it just restarted. Most of what I've hit falls into a few buckets: a missing or wrong environment variable causing the app to exit on startup, an overly aggressive liveness probe killing a slow-starting JVM app before it's actually ready, or OOMKilled from a memory limit that didn't account for real usage. For ImagePullBackOff, it's almost always a tag typo, a registry auth issue — we ran JFrog Artifactory, so an expired or misconfigured pull secret against it — or a network path problem reaching the registry from a private subnet."
"kubectl exec -it <pod> -- sh gets me a shell inside a running container for live debugging — useful in the moment, but not something I'd rely on for anything beyond investigation. The more important half of that question is the second part: everything should be declarative YAML committed to Git, not ad-hoc kubectl create or kubectl edit against a live cluster — imperative changes drift from source control and nobody remembers they happened. In practice that meant Helm charts for templated, versioned deploys, and where I've used ArgoCD, GitOps on top of that, so the cluster's actual state is continuously reconciled against what's declared in Git rather than whatever someone last typed by hand."
"Chart.yaml for metadata — name, chart version, appVersion; values.yaml holding the default config; a templates/ directory with the actual manifests, templated so the same chart deploys to dev, staging, and prod just by swapping values files; and a _helpers.tpl inside templates/ for shared snippets like standard labels so I'm not repeating them everywhere. To ship it: helm lint to validate before anything touches a cluster, helm upgrade --install -f values-prod.yaml for the target environment, and helm rollback sitting there as the fast path back if something goes wrong."
"Each instruction in a Dockerfile is its own cached layer, which is why ordering matters — I put anything that changes rarely, base image, OS packages, dependency installation, before anything that changes on every commit, the actual application code, so a code-only change doesn't bust the whole cache and rebuild everything from scratch. On ENTRYPOINT versus CMD: ENTRYPOINT defines the executable that always runs, CMD supplies default arguments to it that can be overridden at docker run time. Get that backwards and you either can't override behavior at runtime when you need to, or you accidentally let someone replace the whole command when you meant to lock it down. For the JVM and Lucee apps I containerized, that distinction mattered specifically for reusing the same image across environments just by overriding CMD-level args instead of rebuilding per environment."
"My production experience wires RDS, EC2, and EKS specifically — EKS has been the container orchestrator on every AWS environment I've run, so ECS hasn't been part of my day-to-day stack, and I'd rather say that plainly than overstate it. On the RDS/EC2/EKS side: workloads on EKS or EC2 connect to RDS via a connection string sourced from a secret, never hardcoded, with IAM controlling exactly what can reach the DB instance's security group — that IAM policy governance piece is directly part of my background. The concept transfers straight over to ECS if I needed it — a task also just needs the RDS endpoint and credentials injected the same way, and aws ecs update-service --cluster <name> --service <name> --force-new-deployment is the command to redeploy a service after a task definition change."
Coaching note: this is the most honest way to handle a question that reaches past your resume — name the real boundary of your experience confidently, then show you still know the concept. It reads as more credible than pretending ECS is a tool you use daily, and it closes off a follow-up question that could otherwise catch you out.
"JFrog Artifactory — it's been my registry across CI/CD pipelines, and pairing it with Xray for image and dependency scanning has been part of how I've approached the security-scanning side of the pipeline, especially coming from a PCI DSS compliance background where scanning isn't optional."

"The model I've worked within is a protected main branch, feature branches merged in through a PR with required review, so main is always deployable. For a hotfix, I branch directly off the release/production tag rather than off a main that might already be ahead of prod, fix forward with the minimum change needed, and cherry-pick that same commit back into main once it's out — so the fix doesn't quietly disappear the next time main gets released. With as much production incident response and SLA-bound support as I've done, keeping that hotfix path short and untangled from whatever unfinished feature work is sitting in main has mattered more to me than which specific branching model name is on the whiteboard."
"Checkout, build — Maven for the Java-based services — a SonarQube quality gate, Docker build, push to JFrog Artifactory, then deploy. The deploy stage's actual mechanics changed by target: helm upgrade --install against EKS or AKS for containerized services, or triggering a Rundeck job for the legacy application-server estate before it was fully containerized. Every stage after checkout was written to fail loudly and stop the pipeline rather than continue quietly — a SonarQube gate that only warns is a gate in name only, and I made sure that wasn't the case on anything I owned."
"Same shared library as before — once it's registered globally in Jenkins or referenced with @Library, individual Jenkinsfiles shrink down to calling named steps instead of each repo maintaining its own copy of the same 150 lines of pipeline logic. The real payoff shows up when I need to change something across every pipeline at once — a new mandatory scan stage, a changed deploy target — I change it once in the library instead of touching a dozen Jenkinsfiles individually."
"PCI DSS scanning and remediation is directly part of my background from a payment-processing environment at Sandals Resorts, so image and dependency scanning has never been an afterthought for me. With JFrog as the registry, Xray is the natural fit — it scans on push and can gate promotion between repositories based on severity. At the static-analysis layer, SonarQube is already in the pipeline for code quality, which is a natural place to also enforce security-relevant rules rather than treating code quality and security scanning as two separate pipelines."
"Build-time configuration that isn't sensitive goes in as Docker build ARGs, injected by Jenkins from the pipeline's own parameters. Anything sensitive never goes in as a build ARG or gets baked into a layer at all — layers are inspectable, so a 'secret' ARG is really just a secret sitting in plaintext in the image history. Sensitive values get injected at runtime instead, as Kubernetes Secrets mounted into the pod. Images themselves live in JFrog Artifactory, tagged with the commit SHA so every build traces back to an exact source commit rather than relying on a mutable tag like latest."
"Connection details come from a secret, never a config file committed to Git — the app reads connection values injected as environment variables from a Kubernetes Secret, or for the legacy VM-hosted apps, from a secured config file managed outside the deploy artifact. Network-level access is controlled by security groups scoping exactly which compute can reach the RDS instance at all, which sits alongside the IAM policy governance work on my resume — the DB shouldn't be reachable from anything that doesn't specifically need it, regardless of whether the credential itself is correct."
"aws eks update-kubeconfig --region <region> --name <cluster> to get cluster access locally, backed by IAM — the same IAM policy governance work on my resume extends directly to controlling who can actually authenticate to the cluster in the first place, not just what they can do once they're in via RBAC. For secrets inside the cluster, Kubernetes Secrets for anything that has to live as a native object, with the same principle as the database question — nothing sensitive committed to the Git repo the pipeline deploys from."
"I'll be straightforward — my AWS production hours have been EC2, EKS, and RDS-centric rather than Lambda; I haven't run serverless as a primary workload type. That said, the CI/CD mechanics transfer directly from what I do run: package the function code, zip it or build a container image for larger functions, and aws lambda update-function-code --function-name <name> --zip-file fileb://function.zip pushes a new version through a pipeline the same way I'd push a container image to EKS. If Terraform is already the IaC tool of record — which it has been on every environment I've provisioned — the Lambda function itself would just be another Terraform-managed resource rather than something created manually."
Coaching note: same approach as the ECS question — lead with the honest boundary, then immediately show the transferable knowledge. This is a stronger answer than either bluffing hands-on Lambda experience or going quiet.
"Helm chart signing isn't something I've had to implement day to day, but the mechanism is helm package --sign --key <key> --keyring <keyring>, which produces a provenance file alongside the packaged chart that helm verify checks before install — the same supply-chain-integrity idea as image signing, just at the chart layer. On the email side, that's typically S/MIME or PGP for signed or encrypted mail, which is more of a general security-hygiene practice than something I'd tie to a specific project."
Coaching note: this question is a bit of an outlier compared to the rest — if it comes up, a short, accurate answer like the one above is plenty. Don't over-invest prep time here relative to the Kubernetes/CI-CD material that's actually central to the role.
