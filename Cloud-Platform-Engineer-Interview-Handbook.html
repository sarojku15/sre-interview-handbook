Cloud Platform Engineer — AWS / Terraform / GitHub Actions

Scoped to the JD's own emphasis: Terraform IaC, ECS + EKS, Python Lambda, Bedrock AgentCore, GitHub Actions-based CI/CD, governance & compliance across pipelines, and cloud-native AI workloads. 01 Terraform & IaC

The JD leads with this: "build and manage scalable cloud infrastructure using Terraform." Expect both mechanics questions (state, graph, modules) and governance questions (policy-as-code, drift) — this role explicitly owns "governance, compliance, and security controls across cloud infrastructure and CI/CD pipelines."

Q1.1TerraformCore

How does Terraform decide apply order, and what breaks when a dependency is missing?

Show answer

Terraform builds a directed acyclic graph (DAG) from every resource's references. Any interpolation of one resource's attribute inside another (aws_instance.web.subnet_id = aws_subnet.a.id) creates an implicit dependency edge; the graph walker then creates/updates in topological order and, where nothing depends on anything else, in parallel (default -parallelism=10).

When two resources are related only operationally — no attribute reference exists, e.g. an IAM policy that must exist before a Lambda starts invoking it via an unrelated trigger — Terraform can't see the relationship and may create them in either order or in parallel. That's what depends_on is for: an explicit edge with no data flow.

⚠ Common trap: missing an implicit dependency doesn't error at plan time — it applies "successfully" and fails at runtime (e.g. a Lambda deployed before its execution role's policy attachment propagates). Interviewers use this to test whether you understand IAM eventual consistency, not just Terraform syntax.
Q1.2TerraformState

Walk through a production S3 remote-state backend — and how locking actually works.

Show answer

Standard pattern: an S3 bucket with versioning + SSE-KMS enabled for the state file itself, and a lock mechanism so two engineers (or two CI runs) can't apply concurrently and corrupt state.

terraform {
  backend "s3" {
    bucket         = "acme-terraform-state"
    key            = "platform/prod/network.tfstate"
    region         = "ap-south-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"   # pre-1.11 pattern
    # Terraform 1.11+ can lock natively via S3 conditional writes
    # instead of a separate DynamoDB table.
  }
}

Historically locking used a DynamoDB table (one item per state key, written on lock-acquire and deleted on release). Newer Terraform versions added native S3-based locking using conditional PUTs, removing the DynamoDB dependency — worth mentioning you're aware of both, since a lot of production estates still run the DynamoDB pattern.

Q1.3TerraformDesign

Workspaces vs. directory-per-environment for dev/stage/prod — which do you default to, and why?

Show answer

Native terraform workspace gives you one state file per workspace under the same config — fast to spin up, but every environment is forced through identical code, and it's easy to terraform apply against the wrong workspace since the indicator is just a CLI prompt, not a directory you can see in your editor tab.

Directory-per-environment (or a thin wrapper like Terragrunt) duplicates the backend config per env but makes blast radius explicit — you physically cd into envs/prod, and prod can diverge slightly (bigger instance sizes, extra guardrails) without conditionals littering the module. For anything regulated or with real prod/non-prod asymmetry, directory-per-environment with shared modules is the safer default; workspaces are fine for ephemeral, structurally-identical environments (PR preview envs, feature branches).

Q1.4TerraformModules

What makes a Terraform module reusable across teams instead of becoming a "god module"?

Show answer

Pin versions (source = "git::...?ref=v2.3.0" or a private registry with semver) so consumers upgrade deliberately, not on every merge to main. Keep the interface small — expose the 5–8 inputs teams actually vary, give everything else sane defaults, and resist adding a boolean flag for every edge case a single team needs; that's usually a sign the module is doing two jobs.

  • Compose from smaller modules (network, cluster, IAM) rather than one monolith that provisions "the whole platform" — smaller blast radius per apply, easier to test in isolation.
  • Output the identifiers other modules will need (VPC ID, subnet IDs, cluster OIDC issuer URL) so downstream modules consume outputs, not hardcoded values.
  • Validate inputs with validation blocks so a bad value fails at plan time with a clear message, not three resources deep into apply.
Q1.5TerraformTrap

When is terraform apply -target appropriate — and why do some teams ban it outright?

Show answer

-target is genuinely useful for emergency, surgical fixes — e.g. one security group is misconfigured and you need it fixed now without running the full plan for a 400-resource stack. Used routinely, though, it lets state drift silently: resources depending on the targeted one don't get reconciled, so the "official" full plan later shows a pile of unexpected changes nobody remembers approving.

⚠ The honest answer interviewers want: "I've used it for incident response, never as a habit — and I always follow it with a full untargeted plan to confirm nothing drifted." Claiming you never use it can sound like you haven't handled a live incident under a broken full plan.
Q1.6SecurityTerraform

How do you keep secrets out of Terraform state and code?

Show answer

Never hardcode a secret in a .tf file or a .tfvars committed to git — that's the baseline. Beyond that, remember state itself is not encrypted at rest by Terraform; anything Terraform reads or creates, including secret values passed as resource arguments, lands in plaintext inside the state file unless the backend encrypts it (SSE-KMS on the S3 bucket) and access is locked down via bucket policy + IAM.

Pattern: reference secrets via a data source at apply time — data "aws_secretsmanager_secret_version" — rather than passing literal values as variables, and mark any variable that must carry a literal secret as sensitive = true so it's redacted from plan/apply console output (note: this hides it from the CLI output, it does not encrypt it in state).

Q1.7TerraformOperations

How do you catch and reconcile drift — infra that changed outside Terraform?

Show answer

Scheduled, read-only terraform plan (or plan -refresh-only) on a cron in CI, posting the diff to a channel rather than auto-applying — drift is a signal to investigate, not necessarily to immediately overwrite (someone may have made an emergency console change during an incident that Terraform should learn to represent, not stomp on).

When the drift is legitimate, terraform apply -refresh-only updates state to match reality without changing infrastructure; when it's not, a normal apply reverts it. For resources created outside Terraform entirely, terraform import (or the newer declarative import {} block in recent versions) brings them under management without recreating them.

Q1.8GovernanceTerraform

How do you enforce policy — "no public S3 buckets," "every resource must be tagged" — before apply, not after?

Show answer

Policy-as-code gates the plan, not the running infrastructure. Three common tool shapes come up:

  • Sentinel — HashiCorp's own, only available in Terraform Cloud/Enterprise, evaluates against the plan JSON with policy sets tied to workspaces (advisory / soft-mandatory / hard-mandatory enforcement levels).
  • OPA / Conftest — open source, run against terraform show -json plan.out in any CI, policies written in Rego; works regardless of which Terraform tier you're on.
  • Checkov / tfsec / Trivy — static analysis on the .tf source itself, catching known-bad patterns (open security groups, unencrypted volumes) before a plan is even run — fastest feedback loop, but can't see values only known at apply time.

Good pipelines layer these: static scan on every PR, policy-as-code gate on the plan before any prod apply, and drift detection after.

Q1.9TerraformMulti-account

How does one Terraform run provision resources across multiple AWS accounts?

Show answer

Provider aliasing — define one provider block per account/role, each assuming a cross-account IAM role, then point specific resources at the aliased provider:

provider "aws" {
  alias  = "shared_services"
  region = "ap-south-1"
  assume_role { role_arn = "arn:aws:iam::111111111111:role/terraform-exec" }
}

resource "aws_route53_zone" "internal" {
  provider = aws.shared_services
  name     = "internal.acme.com"
}

At larger scale this becomes account-per-environment with a central "management" account holding state buckets and assuming into spoke accounts — which is also the natural place to run the org-wide Service Control Policies (SCPs) that back up whatever Terraform-level governance you've layered on top.

Q1.10TerraformScenario

CI is stuck: "Error acquiring the state lock" — the run that held it was killed. Walk through your fix.

Show answer

First confirm no other apply is genuinely in-flight — check the CI job history and, if using DynamoDB locking, read the lock item (it has the operation, "who," and a timestamp). If it's a stale lock from a crashed runner, terraform force-unlock <LOCK_ID> clears it — deliberately, one lock ID at a time, never scripted as a blanket "retry with force-unlock on failure" step, because that would silently break real concurrent-apply protection.

After unlocking, run a plan (not apply) first — the killed run may have partially applied before dying, so state and real infrastructure can already disagree. If plan shows unexpected deletes, that's a signal to inspect further (possibly state rm/import surgery) rather than blindly applying.

02 AWS ECS

Listed ahead of EKS in the JD's "containerized workloads" bullet — don't assume the interviewer only cares about Kubernetes. ECS questions tend to probe the IAM role split and networking model, since that's where ECS diverges most from EKS.

Q2.1ECSCore

Task definition, task, and service — how do these three relate?

Show answer

A task definition is the blueprint — JSON describing one or more containers, their images, CPU/memory, port mappings, IAM roles, and volumes; it's versioned (each update creates a new revision, never mutates in place). A task is one running instance of that definition. A service is the controller that keeps a desired count of tasks running, replaces failed ones, and wires them into load balancing and auto-scaling — analogous to a Kubernetes Deployment sitting on top of a Pod template.

Q2.2ECSDesign

Fargate vs. EC2 launch type — how do you actually decide?

Show answer

Fargate removes the underlying instance entirely — AWS manages the host, you pay per task's vCPU/memory-seconds. Default choice for most services: no AMI patching, no capacity planning, scales to zero between traffic, and you can't get host-level SSH access even if you wanted to (which is itself a security win for regulated workloads).

EC2 launch type still wins when you need: GPU instances (Fargate GPU support is limited/pricier at scale), very high sustained CPU/memory density where Fargate's per-task pricing gets expensive vs. bin-packing many tasks onto reserved/spot instances, host-level daemons (custom log/metric agents that need host access), or Windows containers with specific host requirements.

Q2.3IAMECSTrap

Task role vs. task execution role — this trips people up constantly. What's the actual difference?

Show answer

Execution role: used by the ECS agent itself, before your application code ever runs — pulling the container image from ECR, writing container logs to CloudWatch, decrypting SSM/Secrets Manager values referenced in the task definition's secrets block.

Task role: assumed by your application code at runtime — what lets your app call s3:GetObject, publish to SNS, write to DynamoDB. This is the one that follows least-privilege per-service, not per-cluster.

⚠ The classic mistake: granting broad permissions to the execution role "to make it work," when the app's own S3/DynamoDB calls actually need the task role. Interviewers ask this specifically to see if you understand the boundary between "what the platform needs to run the container" and "what the container's code needs to do its job."
Q2.4Networking

What does awsvpc network mode actually change vs. the older bridge mode?

Show answer

In awsvpc mode, every task gets its own elastic network interface (ENI) with its own private IP, directly in the VPC subnet — meaning its own security group, independent of whatever host it happens to land on. That's what makes per-task security groups possible (task A can only talk to the RDS instance, task B can only talk to the queue) instead of one shared host-level security group covering everything co-located on an EC2 instance under bridge mode. It's mandatory for Fargate, and generally recommended for EC2 launch type too — bridge/host modes still exist mainly for legacy or very port-dense workloads where ENI limits per instance become the bottleneck.

Q2.5Scaling

How do you auto-scale an ECS service on something other than CPU — say, SQS queue depth?

Show answer

Application Auto Scaling supports target tracking on any CloudWatch metric, not just the built-in CPU/memory ones. For a queue-worker service you'd publish (or use the existing) ApproximateNumberOfMessagesVisible metric and set a target tracking policy aiming for, say, "5 messages per running task" — Auto Scaling then adds/removes tasks to hold that ratio. This is the standard pattern for decoupled, queue-driven workers where CPU alone doesn't reflect real backlog.

resource "aws_appautoscaling_policy" "queue_depth" {
  policy_type = "TargetTrackingScaling"
  target_tracking_scaling_policy_configuration {
    target_value = 5
    customized_metric_specification {
      metric_name = "ApproximateNumberOfMessagesVisible"
      namespace   = "AWS/SQS"
      statistic   = "Average"
      dimensions { name = "QueueName", value = aws_sqs_queue.jobs.name }
    }
  }
}
Q2.6Deployments

Rolling update vs. blue/green on ECS — what's actually different operationally?

Show answer

Rolling (the ECS-native default) replaces tasks in place, governed by minimumHealthyPercent / maximumPercent — e.g. 100/200 means it can double capacity temporarily while draining old tasks, never dropping below full capacity. Simple, but the old and new versions serve traffic side by side for the whole rollout, which matters if you can't tolerate mixed-version behavior.

Blue/green via CodeDeploy stands up an entirely new task set behind a second (or the same, with listener rules) ALB target group, shifts traffic — all at once or linearly/canary over time — and keeps the old task set warm for a configurable bake time so a bad deploy is an instant rollback (flip traffic back) rather than a redeploy. Costs more (double capacity during the switch) but gives you a real rollback button instead of "roll forward with a fix."

Q2.7Cost

What's a capacity provider strategy, and how does it help with cost efficiency?

Show answer

A capacity provider strategy tells a service how to split placement across multiple capacity sources with weighted ratios — most commonly FARGATE and FARGATE_SPOT. A base of on-demand Fargate keeps a guaranteed floor of stable capacity, and a weight split above that base routes the bulk of scale-out tasks to Spot at up to ~70% lower cost, with ECS automatically replacing Spot tasks that get reclaimed. For EC2 launch type, a capacity provider tied to an Auto Scaling Group with managed scaling lets ECS itself drive the ASG size based on actual task placement demand, rather than you hand-tuning scaling policies on the ASG separately.

Q2.8Service Discovery

How do ECS services find each other without hardcoded IPs?

Show answer

Two patterns, for different traffic shapes. North-south (external/ALB-fronted) traffic goes through target groups — the ALB tracks healthy task IPs itself, you never see them. East-west (service-to-service) traffic typically uses AWS Cloud Map: each service registers its tasks' IPs under a DNS namespace (e.g. orders.internal), and ECS keeps that registration in sync as tasks come and go, so other services just resolve orders.internal via standard DNS. For richer east-west needs — retries, circuit breaking, mTLS between services — that's where you'd bring in App Mesh or a service mesh sidecar rather than relying on Cloud Map alone.

Q2.9Decision

The JD asks for both ECS and EKS. When would you actually reach for ECS over EKS on a new service?

Show answer

Good framing for an interview, not a religious war: ECS wins on operational simplicity — no control plane to manage or upgrade, a much smaller AWS-specific IAM/networking surface to reason about, faster for a small platform team to run well. It's the right default for straightforward service-and-worker workloads that don't need Kubernetes-specific ecosystem tooling.

EKS earns its extra operational weight when you need portability across clouds/on-prem, the CNCF ecosystem (Helm charts vendors ship as their primary distribution format, Argo CD/Flux GitOps, custom operators/CRDs), or finer-grained scheduling control (affinity/anti-affinity, custom schedulers, DaemonSets for node-level agents). A pragmatic answer for a platform team: standardize on EKS as the default for anything ecosystem-dependent, keep ECS available for teams that just need "run this container reliably" without the Kubernetes learning curve.

Q2.10ScenarioTroubleshooting

A service's tasks keep cycling: START → RUNNING → STOPPED every 30–60 seconds. Where do you look first?

Show answer

Order of investigation: aws ecs describe-tasks for the stoppedReason field first — it's usually blunt and specific ("Essential container in task exited," "CannotPullContainerError," a failed health check). If it's an exit, check CloudWatch Logs for that task's log stream for an application crash. If it's CannotPullContainerError, verify the execution role has ECR pull permissions and that the subnet has a route to ECR (NAT gateway or VPC endpoint — a common gap in fully private subnets).

If tasks start healthy then get killed specifically by the ALB, it's almost always the target group health check — wrong path, wrong port, or a health-check grace period too short for a slow-starting app (the service scheduler kills tasks the ALB reports unhealthy, even if the app would've passed 10 seconds later).

03 AWS EKS

Kept intentionally lean here since your Kubernetes-core handbooks already run deep on generic K8s. This chapter is EKS-specific: the parts that only exist because you're running Kubernetes on AWS — IRSA, VPC CNI, managed node groups, and where EKS quietly differs from vanilla K8s.

Q3.1EKSArchitecture

What does AWS actually manage in "managed control plane," and what's still on you?

Show answer

AWS runs and patches the API server, etcd, and the core controllers across multiple AZs, scales the control plane itself, and handles its availability SLA — you never SSH into a control plane node or see etcd directly. What's still yours: the data plane (worker nodes — patching, sizing, right-sizing instance types), cluster version upgrades (you choose when to move to a new K8s minor version, AWS doesn't force it until the version hits end-of-standard-support), add-on versions (VPC CNI, CoreDNS, kube-proxy), and everything above the infrastructure line — RBAC, network policy, workload scheduling, ingress.

Q3.2IRSAEKS

Explain IRSA — how does a pod get scoped AWS permissions instead of inheriting the node's role?

Show answer

Before IRSA, every pod on a node inherited whatever IAM instance profile the node itself had — meaning any workload on a node could call anything the node's role allowed, a massive over-privilege problem on shared nodes. IAM Roles for Service Accounts fixes this by giving the cluster an OIDC identity provider, then letting you annotate a Kubernetes ServiceAccount with an IAM role ARN that trusts that OIDC provider, scoped to that specific service account via a trust policy condition.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/orders-api-role

The EKS Pod Identity webhook injects short-lived, auto-rotating credentials into any pod using that service account — no static keys, no node-wide blast radius. Note: AWS also now offers EKS Pod Identity as a newer, simpler alternative to IRSA (no OIDC provider setup, a direct trust to the EKS Pod Identity service) — worth mentioning both since a lot of production clusters are still on IRSA and migrating.

Q3.3Compute

Managed node groups vs. self-managed nodes vs. Fargate profiles on EKS — when does each make sense?

Show answer

Managed node groups are the default: AWS handles the ASG, drains/upgrades nodes in order during a version bump, and integrates with the console — you still choose instance types, AMI, and scaling policy. Self-managed nodes give you full control over the AMI (custom bootstrap scripts, a hardened golden image, non-standard kernel modules) at the cost of owning the lifecycle yourself — mostly for specialized workloads or strict compliance imaging requirements. Fargate profiles run individual pods with no node to manage at all, matched by namespace/label selectors — good for bursty, small, or untrusted workloads where per-pod isolation matters, but you lose DaemonSets, host networking, and some node-level customization on anything scheduled to Fargate.

Q3.4NetworkingTrap

A large EKS cluster keeps hitting "not enough IP addresses" for new pods, even though nodes aren't CPU/memory constrained. What's happening?

Show answer

Classic VPC CNI IP exhaustion. By default, the Amazon VPC CNI assigns each pod a real routable IP from the VPC subnet — so the number of pods a node can run is capped by (ENIs per instance type × IPs per ENI), not by CPU/memory. On smaller instance types packed with many small pods, you hit the IP ceiling long before compute limits.

⚠ Fixes interviewers want to hear, roughly in order of how much they cost to adopt: (1) enable prefix delegation so each ENI slot gets a /28 prefix instead of one IP — dramatically raises pod density per node with minimal change; (2) size subnets correctly up front (a /24 fills up fast at real cluster scale); (3) for extreme density, consider an alternate CNI like Cilium in overlay/eBPF mode that doesn't consume one VPC IP per pod at all.
Q3.5Ingress

How does an Ingress object on EKS actually become a real ALB in AWS?

Show answer

The AWS Load Balancer Controller (successor to the older "ALB Ingress Controller" name) runs as a deployment in-cluster, watches for Ingress objects annotated with kubernetes.io/ingress.class: alb, and calls the AWS API to provision and configure an actual Application Load Balancer, target groups, and listener rules to match — reconciling continuously, the same controller pattern as everything else in Kubernetes. The same controller also provisions Network Load Balancers for Service objects of type LoadBalancer with the right annotations. Target type matters: instance mode routes through node ports (extra hop), ip mode registers pod IPs directly in the target group — the latter is standard on EKS with the VPC CNI since pods already have routable VPC IPs.

Q3.6Upgrades

Walk through upgrading an EKS cluster a minor version — what order, and what can go wrong?

Show answer

Control plane first (AWS upgrades it in place, brief API server disruption but no workload impact), then upgrade managed add-ons (VPC CNI, CoreDNS, kube-proxy) to versions compatible with the new control plane, then roll node groups — for managed node groups this can be a guided in-place update or, more safely, standing up a new node group on the target version and cordoning/draining the old one so you can roll back by just re-pointing workloads if something's wrong.

What breaks in practice: Kubernetes only supports a skew of a few minor versions between control plane and kubelet, so nodes left too far behind become unsupported; deprecated/removed API versions (a classic one historically was extensions/v1beta1 Ingress) silently fail if manifests or Helm charts haven't been updated; and any admission webhook or CRD-based operator not yet compatible with the new API server version can start rejecting or mishandling objects cluster-wide.

Q3.7Storage

EBS CSI driver vs. EFS CSI driver — how do you decide which a workload needs?

Show answer

EBS is block storage, AZ-bound, ReadWriteOnce — one pod (or a set of pods on the same node) at a time, the default for a database or anything needing low-latency block I/O. If that pod gets rescheduled to a different AZ, the volume has to move with it or the pod stays Pending, which is why EBS-backed stateful workloads typically pin via topology-aware provisioning or run in a single AZ deliberately. EFS is NFS, works across AZs, and supports ReadWriteMany — the right choice when multiple pods (potentially in different AZs) need to read/write the same files concurrently, like shared config, ML model artifacts, or a legacy app that assumes a shared filesystem. EFS throughput and per-operation latency are both worse than EBS, so it's not a default — use it because you specifically need shared access, not as a general-purpose volume.

Q3.8Autoscaling

Cluster Autoscaler vs. Karpenter — what's the actual architectural difference?

Show answer

Cluster Autoscaler works against fixed Auto Scaling Groups — it watches for unschedulable pods, picks which ASG to scale based on which node group's instance type would fit, and bumps that ASG's desired count. You're still choosing node group shapes ahead of time.

Karpenter skips ASGs entirely — it watches unschedulable pods and provisions the right EC2 instance type and size directly via the EC2 API, matched to what the pending pods actually need (bin-packing more precisely, mixing Spot and on-demand per NodePool policy), and can deprovision/consolidate nodes far faster since it isn't bound to ASG scaling semantics. Generally faster scale-up, better bin-packing, and less node-group sprawl to maintain — most new EKS builds default to Karpenter today, but Cluster Autoscaler is still extremely common in existing estates, so know both.

Q3.9Add-ons

What's an "EKS managed add-on," and why does it matter for upgrade planning?

Show answer

Managed add-ons (VPC CNI, CoreDNS, kube-proxy, EBS/EFS CSI drivers, Pod Identity Agent) are operated by EKS itself — AWS publishes tested version compatibility matrices per Kubernetes version, and you can update them through the EKS API/Terraform provider rather than manually applying manifests. The practical payoff: before a cluster version upgrade, you check the add-on compatibility matrix first, since an incompatible CNI or CoreDNS version is one of the most common causes of "upgrade succeeded, cluster is broken" — pods failing to get IPs or DNS resolution silently failing cluster-wide.

Q3.10ScenarioTroubleshooting

Nodes intermittently flip to NotReady for 30–60 seconds under load, then recover on their own. Where do you look?

Show answer

Start with kubectl describe node for the condition transitions and reason — usually kubelet failing its own liveness ping to the API server. Common root causes at this specific symptom (transient, self-recovering): CPU pressure on the node starving the kubelet process itself of scheduling time (check if a pod without CPU limits is starving neighbors — the classic "noisy neighbor"), or the VPC CNI's ipamd struggling to keep up with high pod churn on that node. Also check kube-proxy and CNI pod logs on that specific node — if they're crash-looping or OOMing under load, the node reports unhealthy even though the underlying EC2 instance is fine. Instance-level: a burstable instance type (T-family) exhausting CPU credits under sustained load presents almost identically — check CPUCreditBalance in CloudWatch before assuming it's a Kubernetes-layer problem at all.

04 AWS Lambda & Python

JD calls this out specifically as Python-based development, not just "serverless familiarity" — expect at least one question where they want to see actual handler code or error-handling logic, not just architecture talk.

Q4.1LambdaPerformance

What actually causes a Python Lambda cold start, and what's in your control to reduce it?

Show answer

A cold start is the time to download/mount the code package, initialize the execution environment, and run everything at module scope before your handler is invoked — imports, SDK client construction, config loading. In your control: keep the deployment package small (unused dependencies directly add init time), move expensive imports and client construction to module scope so they're reused across warm invocations rather than per-call, and avoid pulling in heavyweight libraries you only use for one code path.

Out of your control but worth knowing: memory allocation also scales CPU, so a function set to 128MB can have a visibly slower cold start than the same code at 1024MB purely from less CPU during init — bumping memory is a legitimate cold-start fix, not just a throughput one. For latency-critical synchronous paths, provisioned concurrency keeps a pool of pre-initialized environments warm, sidestepping cold starts entirely at a fixed cost.

Q4.2LambdaPackaging

Zip deployment package, Lambda layers, and container image Lambdas — when do you reach for each?

Show answer

Plain zip is the default for most functions — simple, fast to deploy, 50MB direct upload / 250MB unzipped limit. Layers pull shared dependencies (a common requests/boto3-extras/internal-utils package) out of every function's own package, deployed and versioned once, referenced by ARN from many functions — keeps individual function packages small and avoids redundant uploads, but layers are still bound by the same combined 250MB unzipped ceiling.

Container image Lambdas (up to 10GB) matter when dependencies genuinely don't fit zip limits — heavy ML libraries, native binaries, or when the team wants one consistent Docker-based build/test/deploy pipeline across both Lambda and ECS/EKS workloads rather than maintaining two different packaging mechanisms.

Q4.3Event SourcesTrap

How does Lambda's error-handling behavior differ between an API Gateway trigger, an S3 event, and an SQS trigger?

Show answer

This is really three different invocation models wearing the same "trigger" name:

  • Synchronous (API Gateway, ALB, direct Invoke): caller waits for a response; on error, the caller sees the failure directly — Lambda itself doesn't retry.
  • Asynchronous (S3, SNS, EventBridge): Lambda queues the event internally and retries automatically (twice, by default, with a delay) before sending to a configured Dead Letter Queue or on-failure destination — the invoking service already got an immediate "accepted" response and moved on.
  • Poll-based (SQS, Kinesis, DynamoDB Streams): Lambda's own polling infrastructure reads batches and calls your function; for SQS specifically, an unhandled exception fails the whole batch by default, meaning even the messages that would've succeeded get retried too — unless you implement partial batch response (report specific failed message IDs back) so only the actual failures are retried and re-visible on the queue.
⚠ "Partial batch failure" for SQS is a very commonly asked follow-up — know that it requires both enabling ReportBatchItemFailures on the event source mapping and returning the right shape ({"batchItemFailures": [{"itemIdentifier": "..."}]}) from your handler, or it silently does nothing.
Q4.4Concurrency

Reserved concurrency vs. provisioned concurrency — these get confused constantly. What does each actually control?

Show answer

Reserved concurrency is a cap, not a warm pool — it sets both the maximum number of concurrent executions a function can use and guarantees that capacity is carved out of the account's shared pool so noisy neighbor functions can't starve it. Set it too low and you get throttling (429s) under load; it's a governance/isolation tool, not a performance one.

Provisioned concurrency is the performance tool — it pre-initializes a set number of execution environments so invocations hit warm code immediately, eliminating cold starts for that slice of traffic, at the cost of paying for that capacity whether it's used or not. The two compose: you might reserve 50 concurrent executions for a function and provision 10 of them to always be warm, letting the other 40 scale normally with cold starts under burst.

Q4.5DesignTrap

Why does idempotency matter so much more for Lambda than for a typical always-on service?

Show answer

Most Lambda event sources (SQS, SNS, S3, Kinesis, EventBridge) offer at-least-once delivery, not exactly-once — a message can and will occasionally be delivered twice (a consumer times out after successfully processing but before deleting from the queue, a retry races a slow success, etc). A handler that isn't idempotent — e.g. "charge the customer's card," "insert a row" without a uniqueness constraint — will double-charge or double-insert on that inevitable redelivery.

Standard pattern: derive or accept an idempotency key (a message ID, a client-supplied request ID) and record it — DynamoDB with a conditional write is the common building block, or the AWS Lambda Powertools idempotency utility for Python, which wraps a handler and automatically short-circuits repeat invocations with the same key, returning the cached prior result instead of re-executing.

Q4.6Observability

What does good observability look like inside a Python Lambda handler, specifically?

Show answer

AWS Lambda Powertools for Python is the practical default rather than hand-rolling this — it gives you structured JSON logging with automatic correlation IDs tied to the request, a @tracer.capture_lambda_handler decorator that wires up X-Ray tracing (including automatic sub-segments around boto3 calls), and custom EMF (embedded metric format) metrics that show up in CloudWatch without a separate PutMetricData call per point.

from aws_lambda_powertools import Logger, Tracer, Metrics
from aws_lambda_powertools.metrics import MetricUnit

logger = Logger()
tracer = Tracer()
metrics = Metrics()

@logger.inject_lambda_context
@tracer.capture_lambda_handler
@metrics.log_metrics
def handler(event, context):
    logger.info("processing order", order_id=event["id"])
    metrics.add_metric(name="OrdersProcessed", unit=MetricUnit.Count, value=1)

The payoff in a real incident: structured logs let you filter CloudWatch Logs Insights by order_id across every function in the trace, and X-Ray shows you exactly which downstream call (a specific DynamoDB table, a specific HTTP dependency) is where the latency actually lives — instead of guessing from wall-clock duration alone.

Q4.7NetworkingTrap

When does a Lambda function actually need to be attached to a VPC — and what's the cost of that?

Show answer

You need VPC attachment when the function must reach something with no public endpoint — an RDS instance in private subnets, an internal ElastiCache cluster, an internal-only service. If everything a function talks to is a public AWS service API (S3, DynamoDB, SQS) or reachable over the internet, keep it out of the VPC — it's genuinely simpler and was historically also faster to cold-start.

Cost: VPC-attached Lambdas need ENIs in your subnets, and NAT gateway (or VPC endpoints) if they also need to reach public AWS APIs from inside the VPC — a function that's VPC-attached only for RDS access but also calls S3 needs an S3 VPC endpoint, or its S3 calls silently fail/timeout with no NAT path out. AWS's Hyperplane ENI improvement years ago made the historical "VPC Lambda = terrible cold start" problem mostly a non-issue for new deployments, but it's still one extra layer of networking to get right — a common real interview trap is a Lambda that times out only when VPC-attached, which is almost always a missing NAT gateway or missing VPC endpoint for whatever public API it also needs.

Q4.8Orchestration

When do you reach for Step Functions instead of chaining Lambdas by having one invoke the next?

Show answer

Direct Lambda-invokes-Lambda chaining hides the workflow inside code — no visual state, no built-in retry/backoff per step, and a failure partway through leaves you reconstructing what happened from logs. Step Functions makes the workflow itself the artifact: each state's retry/catch policy is declarative, the execution history shows exactly which step failed and with what input/output, and long-running or human-in-the-loop steps (wait for an approval, wait for a callback token) are natively supported without a Lambda sitting there polling or timing out. Reach for it once you have more than two or three steps with real branching/retry logic, or whenever "what happened during this specific failed run at 3am" needs to be answerable without log spelunking.

Q4.9ScenarioTroubleshooting

One malformed message in an SQS queue is causing an entire Lambda-backed pipeline to stall. What's happening and how do you fix it?

Show answer

Classic "poison pill" scenario. Without partial batch response enabled, a single unprocessable message inside a batch fails the whole batch, so it goes back to the queue, gets redelivered, fails again identically — and because it keeps getting re-batched with otherwise-healthy messages, it can drag good messages down with it on every retry cycle until maxReceiveCount is hit.

Fix, in order: (1) enable ReportBatchItemFailures so only the actually-failing message ID is retried, not the whole batch; (2) configure a dead-letter queue on the source SQS queue with a sane maxReceiveCount (e.g. 3–5) so a message that will never succeed stops consuming pipeline capacity and lands somewhere for inspection instead of looping indefinitely; (3) make the handler defensive — validate/parse the message in a try/except and explicitly route unparseable payloads to the DLQ path rather than letting an uncaught exception be the only signal.

Q4.10Local Dev

How do you test Lambda functions before they ever hit AWS?

Show answer

Three layers, and a mature pipeline uses all three rather than picking one: unit tests against the handler function directly — construct the event payload as a plain dict, call the handler, assert on the return value, mocking boto3 calls with moto or unittest.mock so tests run in milliseconds with no AWS credentials needed at all. SAM CLI (sam local invoke, sam local start-api) runs your actual packaged function inside a Docker container that mimics the real Lambda runtime — closer to production behavior, catches packaging/dependency issues unit tests can't. LocalStack emulates a wider slice of AWS (SQS, DynamoDB, S3) locally for integration-style tests of the whole event flow, not just the handler in isolation. CI typically runs the fast unit tests on every commit and reserves SAM/LocalStack integration tests for pre-merge or nightly, since they're slower.

05 Bedrock AgentCore & Agentic AI New Territory

Why this chapter gets extra weight: the JD lists "AWS Agent Core" as a required skill, not a nice-to-have — and it's genuinely new. Parts of it only reached general availability in mid-2026, and AWS has been actively steering new agent builds away from the older "Bedrock Agents" approach toward this platform. Most candidates for a role like this won't have touched it. This section is current as of research done for this handbook — the space is moving fast enough that it's worth a quick skim of the current AWS docs the night before the interview in case anything's shifted since.

Correct name is Amazon Bedrock AgentCore — the JD's "AWS Agent Core" is almost certainly this. Frame it in interview answers as: the production/operations layer for AI agents, sitting on top of whatever foundation model and agent framework a team already uses, filling the gap between "we built an agent prototype" and "we can run this in production with real security boundaries."

Q5.1AgentCoreCore Concept

What problem does Bedrock AgentCore actually solve — how is it different from "Bedrock Agents"?

Show answer

Bedrock Agents (now often referred to as "Bedrock Agents Classic") is the older, more opinionated way to build an agent directly inside Bedrock — you define action groups and it handles orchestration for you, but it's comparatively rigid and tied closely to Bedrock's own model catalog. AgentCore is explicitly framework-agnostic and model-agnostic — it doesn't care if the agent logic is written with LangGraph, CrewAI, LlamaIndex, Strands Agents, or something custom, and it works with models from Bedrock, SageMaker, or elsewhere. What it provides instead is the operational plumbing every production agent needs regardless of framework: a place to run the agent securely, a governed way for it to call tools, an identity/credential model, memory, and observability — the "day 2" concerns that a prototype notebook never has to deal with.

🎯 Interview framing: position this as "AWS realized every team building agents was reinventing the same infrastructure — session isolation, tool-calling security, credential handling — so they extracted it into a shared platform, the same way Kubernetes extracted container orchestration instead of every team hand-rolling it." That analogy tends to land well with a platform-engineering interviewer.
Q5.2AgentCoreArchitecture

Name AgentCore's core components and what each one owns.

Show answer

Five primary services, each usable independently or composed together:

  • Runtime — hosts and executes the agent's code with session-level isolation between users/conversations.
  • Gateway — turns existing APIs and Lambda functions into tools an agent can call, acting as a governed integration/policy-enforcement point between agents and the systems they touch.
  • Identity — manages the agent's own workload identity and its access to external services (which user is this agent acting on behalf of, what's it allowed to touch).
  • Memory — short-term, long-term, and episodic storage so an agent can retain context across a session or across sessions entirely.
  • Observability — traces, dashboards, and metrics for what an agent actually did, built on OpenTelemetry.

Plus auxiliary building blocks: a Code Interpreter tool for secure sandboxed code execution, and a Browser tool for web interaction — both meant to be called the same way any other Gateway-exposed tool would be.

Q5.3GatewayLambda

How does AgentCore Gateway connect to the Lambda/Python side of this same JD?

Show answer

This is the most concrete, practical intersection of the two JD requirements. Gateway's core job is turning existing APIs and Lambda functions into tools an agent can discover and call — meaning the same Python Lambda skills the JD asks for elsewhere are directly reusable as "agent tools" once fronted by Gateway, rather than needing an entirely separate agent-specific toolchain. Tool exposure goes through MCP (Model Context Protocol) — Gateway effectively acts as an MCP server, translating your existing Lambda/API surface into MCP tool calls the agent framework understands, with policy enforcement (what this agent is allowed to invoke) sitting at that boundary.

In a platform-engineering interview, this is a strong concrete answer to "how would you operationalize an agent tool" — you're not writing bespoke agent-framework glue code per tool, you're exposing the same Lambda functions you'd build for any other purpose, governed centrally.

Q5.4IdentityIAM

How does AgentCore Identity handle "this agent needs to act as this specific user, not with blanket permissions"?

Show answer

AgentCore Identity centers on a workload identity abstraction for the agent itself, separate from any individual end user's identity, and integrates with existing identity providers via OAuth so an agent can obtain scoped, short-lived access to external services on a specific user's behalf rather than running under one static, broad service credential. Under the hood, credentials for external services are stored in Secrets Manager under a dedicated AgentCore-managed prefix, and the SDK handles IAM role creation for the agent's own execution identity rather than requiring you to hand-wire trust policies.

The platform-engineering angle to emphasize: this is the same least-privilege instinct as IRSA on EKS or a scoped Lambda execution role — an agent is just another workload that shouldn't run with more access than the specific action it's performing needs, and shouldn't be able to silently act as "any user" just because it has a valid credential for one.

Q5.5MemoryMulti-tenant

AgentCore Memory has short-term, long-term, and episodic tiers — why would a platform team care about that distinction operationally?

Show answer

Because each tier has a different retention, cost, and isolation profile that the platform — not the agent developer — usually ends up governing. Short-term memory is scoped to a single session (the current conversation's working context); long-term and episodic memory persist across sessions, meaning they need the same data-governance thinking as any other persistent store: retention policy, per-tenant isolation, and a deletion path for compliance (a user asks to be forgotten — can you actually purge their episodic memory?).

For multi-tenant platforms specifically, memory namespaces are hierarchical and scoped by IAM role per tenant, so one tenant's agent can't read another's memory even though they may share the same underlying Runtime infrastructure — a "pool" deployment model shares infrastructure across tenants with logical isolation via these scoped namespaces, while a "silo" model gives each tenant fully dedicated Runtime/Gateway/Memory resources for the strictest isolation, at higher cost. Which model fits is exactly the kind of trade-off question a governance-focused interviewer would expect you to reason through, not just recite.

Q5.6ObservabilityCloudWatch

How do you observe an agent's behavior — not just "is it up," but "what did it actually decide to do"?

Show answer

AgentCore Observability ships built-in metrics for Runtime, Memory, Gateway, built-in tools, and Identity straight into CloudWatch with no extra instrumentation — request counts, latencies, error rates, the same shape as any other AWS service's default metrics. The deeper layer — actually seeing an agent's reasoning trace, which tools it called, in what order, with what inputs — requires instrumenting the agent code with the AWS Distro for OpenTelemetry (ADOT) SDK, which surfaces as traces and dashboards, not just numeric metrics.

This is worth contrasting explicitly with traditional microservice observability in an interview answer: a normal service's trace shows you a deterministic call graph — this endpoint calls that database, always. An agent's trace shows you a call graph the model chose at runtime — which tool it decided to invoke, and it can genuinely differ run to run for the same input. Good agent observability has to capture that decision path, not just latency and error codes, or you can't debug "why did it do that" after the fact.

Q5.7HarnessCurrent

What's AgentCore Harness, and why might it come up if the interviewer is genuinely current on this space?

Show answer

Harness is a newer addition — a managed, configuration-driven agent execution loop that sits alongside Runtime, Memory, Gateway, and Identity, reaching general availability in mid-June 2026. Where Runtime alone hosts whatever agent loop your framework code implements, Harness gives you a managed loop you largely configure rather than hand-build — lowering the amount of custom orchestration code a team has to own and operate.

Worth knowing as context even if not asked directly: AWS also moved Bedrock Agents Classic into maintenance mode for new customers around the same time (new Classic agent creation closing roughly six weeks after Harness's GA), signaling AgentCore is now the default recommended path for any new agent build on AWS, not an alternative track. If an interviewer asks "would you use Bedrock Agents or AgentCore for a new project," the current, defensible answer is AgentCore — Classic is legacy for net-new work.

Q5.8OperationsInterview Angle

What's genuinely different about operating an agentic workload vs. a traditional microservice — from a platform engineer's chair, not a data scientist's?

Show answer

This is the question most likely to actually get asked, even more than AgentCore trivia — interviewers care whether you can reason about it, not just name the product. A strong answer covers:

  • Non-determinism — the same input can produce a different tool-call sequence run to run, which breaks the usual assumption that identical requests are safe to retry blindly or that a passing test today guarantees the same behavior tomorrow if the underlying model changes.
  • Cost is per-token, not per-request — a single "simple" user request can silently balloon into dozens of model calls and tool invocations if the agent gets into a reasoning loop; cost monitoring needs to track token/tool-call volume per session, not just request count.
  • Blast radius of a tool call is different — a traditional service's API surface is fixed and reviewed; an agent can, in principle, choose to call any tool it's been granted, which is exactly why Gateway-level policy enforcement and Identity-level scoping matter so much more here than "which endpoints does this microservice expose."
  • Guardrails are a runtime concern, not just an input-validation one — you need to bound what the agent can do (and say) at multiple points in the loop, not just validate the initial request payload.
Q5.9IaCAgentCore

Can AgentCore resources be provisioned with Terraform, or is this a console/SDK-only service?

Show answer

Yes — treat this the same as any other AWS service the JD asks you to manage as code: AgentCore Runtime, Gateway, Identity, and Memory resources are provisionable through Terraform's AWS provider like any other resource type, which matters because it means agentic workloads don't have to be a special, hand-clicked exception to your normal IaC discipline. If asked to sketch it, the honest framing is: define the Runtime resource (pointing at your container image or code artifact), a Gateway resource with its target definitions (the APIs/Lambdas it exposes as tools), and wire IAM roles for the workload identity the same way you would for any other IAM-Roles-for-a-workload pattern — conceptually closer to defining an ECS service + IAM role than anything exotic.

Q5.10HonestyAgentCore

If you're asked "have you worked with AgentCore in production" and the honest answer is no — how do you handle that?

Show answer

Given how recently parts of this platform reached GA, most candidates — possibly including some interviewers — haven't run it in production either. Don't overclaim. A credible answer: name what you do know precisely (the five components, the Gateway/Lambda connection, the governance angle), be direct that hands-on production experience is limited given how new it is, and pivot to the transferable pattern — "the IAM-scoping, tool-governance, and observability problems AgentCore solves are the same class of problem I've solved for EKS workloads via IRSA and for Lambda via execution roles; the primitives are new, the platform-engineering instincts aren't."

06 GitHub Actions CI/CD

JD names GitHub Actions specifically (not "a CI/CD tool of your choice") twice — once in required skills, once in responsibilities. OIDC federation to AWS is the single highest-value topic here; it's the modern-vs-legacy signal interviewers use to gauge whether your CI/CD knowledge is current.

Q6.1OIDCAWSHigh-Value

Walk through GitHub Actions authenticating to AWS via OIDC — why is this the right answer instead of storing an access key as a repo secret?

Show answer

Long-lived IAM access keys stored as repo secrets are a standing liability — they don't expire on their own, they're exfiltratable if a workflow or dependency is compromised, and rotating them is a manual process someone has to remember to do. OIDC federation removes the credential entirely: GitHub's Actions runner requests a short-lived OIDC token scoped to that specific workflow run, AWS's IAM OIDC identity provider validates it against a trust policy, and issues temporary STS credentials that expire automatically — nothing long-lived ever exists to leak.

# One-time setup: IAM OIDC provider trusting token.actions.githubusercontent.com

# Workflow step:
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/gha-deploy-role
    aws-region: ap-south-1

The trust policy on gha-deploy-role should be scoped tightly on the sub claim — e.g. restricted to a specific repo and branch (repo:acme/platform:ref:refs/heads/main) — so a workflow on a feature branch or a fork can't assume a production deploy role just because the OIDC provider trusts the GitHub org generally.

Q6.2Core

Reusable workflows vs. composite actions — both let you avoid copy-pasting YAML. What's the actual difference?

Show answer

A composite action bundles a sequence of steps into something you call as a single step inside a job — it runs in the context of the calling job, sharing that job's runner and environment. A reusable workflow is invoked with uses: at the job level (jobs.build.uses: ./.github/workflows/build.yml) — it runs as its own job (or set of jobs), can define its own permissions, secrets, and even matrix strategy, and can itself call other reusable workflows.

Rule of thumb: composite action for "these 4 steps always go together" (checkout, setup language, install deps, run linter); reusable workflow for "this entire build-test-push pipeline should be identical across 15 microservice repos" — the latter is what actually enforces platform-wide standardization, since teams call the central workflow rather than maintaining their own copy that quietly drifts.

Q6.3Governance

How do GitHub Environments give you deployment governance, not just secret scoping?

Show answer

An Environment (e.g. production) attached to a job via environment: production gates that job behind rules you configure once: required reviewers (a human must approve before the job runs — the closest GitHub-native equivalent to a change-approval-board gate), a wait timer, and branch restrictions (only main can deploy to this environment). Secrets and variables scoped to that environment are only exposed to jobs that reference it — meaning a production database credential simply doesn't exist in the context of a job targeting staging, rather than relying on workflow logic to "remember" not to use it there.

For this JD's governance emphasis specifically: environments are the natural place to enforce "prod deploys require a second approver" as a platform-level control rather than a per-repo convention someone can forget to add.

Q6.4Runners

When do you need self-hosted runners instead of GitHub-hosted ones, and what security implications come with that choice?

Show answer

Self-hosted runners earn their operational overhead when a job needs to reach something with no public path — an internal EKS API server, an on-prem system, a private VPC resource without exposing it publicly just for CI — or when you need specific hardware/licensing GitHub-hosted runners don't offer.

⚠ The security angle interviewers actually probe: a persistent self-hosted runner that also picks up workflow runs triggered by pull requests from forks is a real, well-documented attack path — a malicious PR can get arbitrary code executed on your runner, in your network, with whatever credentials that runner has cached. Mitigations: run pull_request_target workflows (which have access to secrets) with extreme care and minimal checkout of untrusted code, prefer ephemeral self-hosted runners (spun up per-job, destroyed after, so nothing persists to be compromised across runs), and never let fork PRs trigger workflows with write access to secrets without a required-approval gate first.
Q6.5Performance

A pipeline's dependency install step is the slowest part of every run. How do you speed it up?

Show answer

actions/cache, keyed off a hash of the lockfile so the cache invalidates exactly when dependencies actually change, not on every run:

- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('requirements.txt') }}
    restore-keys: pip-${{ runner.os }}-

The restore-keys fallback matters — even if the exact lockfile hash changed (one new dependency added), a partial-match cache from the previous key still saves most of the download/build time versus a fully cold cache. For container-based builds, layer caching via docker/build-push-action's built-in cache-from/cache-to (backed by GitHub Actions cache or a registry) does the equivalent for image builds — skip rebuilding layers whose inputs haven't changed.

Q6.6Supply ChainTrap

Why do security-conscious pipelines pin third-party actions to a commit SHA instead of a version tag like @v4?

Show answer

A tag is mutable — the maintainer (or an attacker who compromises the maintainer's account) can repoint v4 at different code at any time, and your workflow silently starts running whatever that tag now points to on its next trigger, with whatever permissions and secrets that workflow has. This is a real, materialized supply-chain attack class, not a theoretical one. Pinning to a full commit SHA — uses: aws-actions/configure-aws-credentials@e3dd6a... — means the exact code that runs can't change without you deliberately bumping the pin (ideally with Dependabot opening a PR for each update, so it's reviewed rather than silent).

⚠ Pair this with least-privilege permissions: blocks at the workflow or job level (permissions: {contents: read} as a default, only elevating specific jobs that need id-token: write for OIDC or packages: write to publish) — the default GITHUB_TOKEN permissions are broader than most jobs actually need.
Q6.7GitOps

Where's the line between what GitHub Actions should do and what Argo CD/Flux should do in a GitOps pipeline?

Show answer

GitHub Actions owns CI — build, test, scan, and produce an artifact (a container image pushed to a registry, tagged with the commit SHA), then update a manifest or Helm values file in a separate GitOps config repo (bump the image tag). It should stop there for anything running on Kubernetes.

Argo CD/Flux owns CD — it continuously reconciles the cluster's actual state against that GitOps repo, pulling the change rather than Actions pushing it. This split matters for two real reasons: the cluster's deploy credentials never need to exist in CI at all (Actions never talks to the cluster directly, only to git and a registry), and the cluster is always reconcilable to a known-good state from git even if CI is down or compromised. For non-Kubernetes targets (Lambda, ECS) this separation is less rigid and Actions commonly does drive the deploy directly via the AWS CLI/SDK — worth being explicit in an interview that the GitOps pull model is a Kubernetes-specific pattern, not a universal rule.

Q6.8Reliability

Someone pushes 4 commits to a branch in quick succession and 4 full pipeline runs kick off, racing each other. How do you prevent that?

Show answer

Concurrency groups — scope a group key to the branch/ref, and cancel superseded runs automatically:

concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true

Only the latest push's run survives; earlier in-flight runs for the same ref are cancelled rather than racing to deploy. Worth a caveat in an interview answer: cancel-in-progress: true is right for build/test stages, but you generally do not want it on a job that's mid-deploy to production — cancelling a deploy halfway through can leave infrastructure in a partially-applied state, so that specific job is often better left to run to completion (or given a separate, non-cancelling concurrency group) even while earlier build stages get cancelled freely.

Q6.9ScenarioSecrets

A workflow deploys fine when you push directly, but fails with "credentials not found" on pull requests from forks. Why?

Show answer

By design — GitHub does not expose repository secrets (or grant write-scoped GITHUB_TOKEN permissions, or allow OIDC id-token: write) to workflows triggered by a pull_request event from a fork, precisely because a fork's workflow file could be attacker-controlled. This is a security feature, not a bug to route around casually.

If forked-PR contributions genuinely need CI to run against real credentials (e.g. deploying a preview environment), the sanctioned pattern is splitting the workflow: a pull_request-triggered job with no secrets does build/lint/unit-test only, and a separate, more carefully gated pull_request_target or workflow_run-triggered workflow — which runs in the base repo's context with secrets, but should checkout and execute as little of the untrusted fork's code as possible — handles anything that needs real credentials, often behind a required-reviewer approval first.

07 Governance, IAM & Compliance

This is the JD's own phrase: "governance, compliance, and security controls across cloud infrastructure and CI/CD pipelines" — notice it's not just "secure the infra," it explicitly extends governance into the pipeline itself. Expect this to be a genuinely heavy section of the real interview.

Q7.1IAMTrap

Walk through IAM policy evaluation order when SCPs, permission boundaries, and identity policies are all in play.

Show answer

This is asked precisely because it's counter-intuitive and everyone gets it wrong at least once in production. The mental model: every layer that applies must independently allow the action, and any explicit deny anywhere wins regardless of what else allows it.

  1. Organization SCPs — a hard ceiling at the account level; if the SCP doesn't allow it, nothing inside that account can grant it, full stop, no matter what IAM says.
  2. Resource-based policies (e.g. an S3 bucket policy) — evaluated alongside identity policies, not after.
  3. Identity-based policies attached to the user/role.
  4. Permission boundaries — a ceiling on a specific IAM principal (not the whole account) that even an admin-granted identity policy can't exceed.
  5. Session policies — passed at assume-role time, a further ceiling for just that session.
⚠ The single most common real-world mistake this tests: someone grants a permission via identity policy, it still doesn't work, and they spend an hour debugging the identity policy — when an SCP or permission boundary was the actual blocker the whole time. Knowing to check "is anything capping this from above" first is the practical skill being tested, not reciting the order from memory.
Q7.2IAM

SCPs vs. permission boundaries — both look like "ceilings" on permissions. What's the actual difference in scope?

Show answer

SCPs live in AWS Organizations and apply to an entire account (or OU) — every principal in that account, including the account's own root user, is bounded by them. You use SCPs for org-wide non-negotiables: "no account may disable CloudTrail," "no resources outside these approved regions."

Permission boundaries are an IAM feature attached to a specific user or role — a ceiling on just that one principal, set by whoever administers IAM in that account. The classic use case: a platform team lets application teams create their own IAM roles for their services (self-service, less bottleneck), but every role they create is required to have a permission boundary attached — so even if an app team accidentally (or maliciously) writes an overly broad identity policy, the boundary caps what that role can actually do, capping delegation without capping the whole account.

Q7.3IAMPractice

"Least privilege" is easy to say. How do you actually right-size an overly broad IAM role in practice?

Show answer

IAM Access Analyzer has a policy generation feature that watches a role's actual CloudTrail activity over a chosen window and generates a policy scoped to only the actions genuinely used — a much better starting point than guessing. Process: run the role broad-but-monitored for a representative period (long enough to capture batch jobs, monthly tasks, not just daily traffic), generate the least-privilege policy from real usage, review it against known-but-rare paths that might not have fired during the window (disaster recovery procedures, annual processes), then tighten and deploy — ideally to a non-prod copy of the role first, watching for `AccessDenied` errors before cutting prod over.

Ongoing discipline matters more than the one-time exercise: Access Analyzer's unused access findings surface permissions granted but never exercised, on a rolling basis, so scope creep gets caught rather than accumulating silently for years.

Q7.4Compliance

How do you translate a compliance framework requirement (SOC 2, PCI-DSS) into something enforced by the platform, not just documented in a wiki?

Show answer

The pattern that actually holds up in an audit: map each control to a technical, continuously-evaluated check rather than a point-in-time manual attestation. AWS Config with managed and custom Config Rules (or a pre-built conformance pack for a specific framework) continuously evaluates resources against a rule — encrypted-at-rest required, no public S3 buckets, MFA required for IAM users — and flags or auto-remediates drift the moment it happens, rather than an auditor discovering a misconfigured bucket during an annual review.

Layer this with what's already covered in the Terraform chapter (policy-as-code gating the plan before anything's even created) and this becomes defense in depth: policy-as-code stops a non-compliant resource from being created, Config continuously catches anything that slips through or drifts afterward, and CloudTrail provides the audit evidence trail an assessor actually asks for. Being able to describe this three-layer story (prevent → detect → prove) is usually worth more than naming any single tool.

Q7.5Cross-Account

Team A's Lambda in Account 1 needs to read from an S3 bucket in Account 2. What are the actual mechanics?

Show answer

Two policies have to agree, on both sides of the account boundary. The Lambda's execution role in Account 1 needs an identity policy allowing s3:GetObject on that specific bucket ARN. The bucket's resource-based policy in Account 2 needs to explicitly grant that same principal (the Account 1 role's ARN) access — S3 bucket policies are one of the resource types that support cross-account grants directly, without needing a full assume-role hop.

For anything beyond simple read access — actions that need broader cross-account operation, or resources that don't support resource-based policies at all — the alternative is a dedicated cross-account IAM role in Account 2 with a trust policy naming Account 1's role as a trusted principal, which Account 1's Lambda then calls sts:AssumeRole against before acting. Both patterns show up constantly in multi-account AWS Organizations setups; know when each applies (resource policy when the target resource type supports it and you just need specific actions; assume-role when you need broader or more dynamic access).

Q7.6Secrets

Secrets Manager vs. Parameter Store (SecureString) — when do you actually need the more expensive option?

Show answer

Parameter Store SecureString is free (standard tier), simple, and fine for config values and secrets that don't need automatic rotation. Secrets Manager earns its per-secret cost specifically for automatic rotation — built-in rotation Lambda templates for RDS, DocumentDB, and Redshift credentials that rotate on a schedule with zero manual intervention, updating the secret and coordinating the database-side password change together. If a secret is a database credential that should rotate every 30/60/90 days without a human touching it, that's Secrets Manager; if it's a static API key or a feature flag that changes rarely and doesn't need automated rotation, Parameter Store is the more cost-effective default.

Q7.7CI/CD Governance

The JD explicitly extends governance into CI/CD pipelines, not just infrastructure. What does that mean in concrete GitHub controls?

Show answer

Beyond the OIDC/least-privilege token scoping already covered: branch protection rules requiring status checks (tests, security scans) to pass and a minimum number of approving reviews before merge to main; required signed commits or verified commit signatures for repos where provenance matters; CODEOWNERS so changes to sensitive paths (Terraform for prod, IAM policy files) automatically require review from the specific team that owns that risk, not just any reviewer; and org-level rulesets that apply these consistently across every repo rather than trusting each team to configure their own repo correctly.

The audit-trail half matters as much as the prevention half: who approved this deploy, what did the plan show before it was approved, what commit actually shipped — GitHub's own audit log plus environment protection-rule history gives you that evidence trail, which is exactly what a SOC 2 change-management control is checking for.

Q7.8Tagging

Why would a governance-focused platform team enforce mandatory resource tagging, and how do you actually enforce it rather than just asking nicely?

Show answer

Tags are how cost allocation, ownership, and compliance scoping actually get answered at scale — "which team owns this untagged EC2 instance that's been running for 8 months" is an unanswerable question without them, and it's the question that comes up during every cost review and every security incident. Enforcement that actually holds: an SCP or a Config rule (required-tags) that denies resource creation missing mandatory tags (Owner, Environment, CostCenter) — enforced at creation time, not caught later — plus a policy-as-code check in the Terraform pipeline (Checkov/OPA) that fails the plan before it ever reaches AWS. "Ask nicely in the wiki" tagging policies decay within a quarter; enforced-at-creation tagging doesn't.

Q7.9ScenarioIncident

A security team asks you to confirm whether a specific IAM role was used to access a sensitive S3 bucket in the last 30 days. Walk through how you'd actually answer that.

Show answer

Start with whether the ingredients even exist: an org-wide CloudTrail trail logging management and, critically, data events for that bucket specifically (data events — object-level S3 access — aren't logged by default and have to be explicitly enabled, since they're higher volume/cost; this is worth stating proactively, since a huge number of real incident investigations hit a wall exactly here because nobody enabled S3 data events ahead of time).

Assuming it's enabled: query CloudTrail (directly, or via Athena against the log bucket for a 30-day range, which is far more practical than paging through the console) filtered by that role's ARN as the identity and the bucket's ARN as the resource, looking at event names like GetObject. If data events weren't enabled, be honest that the specific answer isn't reconstructible after the fact — and recommend enabling them going forward plus checking whatever secondary signal might exist (VPC Flow Logs if access was from a known network path, S3 server access logging if that was separately enabled) rather than guessing.

08 Observability

Listed as preferred, not required — likely a shorter portion of the actual interview than Terraform/AWS/CI-CD, but still worth being fluent across both the native-AWS and open-source stacks since the JD names both explicitly.

Q8.1CloudWatchPrometheusDecision

CloudWatch or Prometheus/Grafana — how do you actually decide, given the JD lists both?

Show answer

They're not fully interchangeable — different collection models. CloudWatch is push-based: services and agents publish metrics to it, it's zero-setup for native AWS service metrics (Lambda duration, ALB 5xx count, RDS CPU all show up automatically), and it's the natural home for anything that needs to trigger AWS-native actions (a CloudWatch alarm driving Auto Scaling, or feeding directly into AWS Chatbot/SNS).

Prometheus is pull-based — it scrapes /metrics endpoints on a schedule — and is the standard for Kubernetes-native application and cluster metrics precisely because the whole ecosystem (kube-state-metrics, node-exporter, most Helm charts' built-in exporters) assumes it. Grafana then gives richer, more customizable dashboarding than native CloudWatch dashboards. Pragmatic answer for an interview: CloudWatch for AWS-service-level metrics and anything that needs to drive AWS-native automation; Prometheus/Grafana for Kubernetes workload and cluster-internal metrics — and CloudWatch Container Insights or the Prometheus remote-write integration to get a unified view rather than forcing a single tool to do both jobs badly.

Q8.2Prometheus

How does a new microservice on EKS actually get scraped by Prometheus, end to end?

Show answer

Assuming the kube-prometheus-stack (Prometheus Operator) is already running: the service exposes a /metrics endpoint (typically via a client library like prometheus_client in Python), then you create a ServiceMonitor CRD pointing at that service's label selector and port. The Prometheus Operator watches for ServiceMonitors matching its own selector and automatically reconfigures Prometheus's scrape targets — no manual edit to a static prometheus.yml, which is the whole point of running the Operator instead of vanilla Prometheus on Kubernetes.

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: orders-api
spec:
  selector:
    matchLabels: { app: orders-api }
  endpoints:
    - port: metrics
      interval: 30s
Q8.3Logging

How do container logs typically get from an EKS pod into an ELK/OpenSearch stack?

Show answer

Standard shape: a log-forwarding agent — Fluent Bit is the common choice on EKS for its low resource footprint — runs as a DaemonSet, one per node, tailing container stdout/stderr logs from the node's filesystem, enriching each line with Kubernetes metadata (pod name, namespace, labels) via the Kubernetes filter plugin, then shipping to OpenSearch/Elasticsearch (or Logstash first, if transformation logic lives there instead). CloudWatch Logs can sit in this pipeline too — either as the sole destination for simpler setups, or as a parallel/interim destination while ELK is the long-term searchable store, since CloudWatch Logs Insights query syntax and retention pricing are quite different from OpenSearch's.

Q8.4Fundamentals

Metrics, logs, and traces — what does each actually answer that the others can't?

Show answer

Metrics answer "is something wrong, and roughly how bad" — cheap to store long-term, great for alerting and trend lines, but tell you nothing about a single specific request. Logs answer "what exactly happened" for a specific event — full detail, but expensive to store at scale and slow to search without good structure/indexing. Traces answer "where in a multi-service call chain did the time go, or the error originate" — the only one of the three that shows causality across service boundaries.

A real incident typically walks all three in order: an alarm on a metric fires (latency p99 spike) → you pull a trace for a slow request to find which downstream service is the bottleneck → you pull that service's logs at the exact timestamp for the specific error detail. Being able to narrate that flow, rather than just defining the three terms, is what actually distinguishes someone who's run on-call from someone reciting a glossary.

Q8.5AlertingTrap

Your on-call rotation is drowning in alerts, most of which nobody acts on. How do you actually fix that?

Show answer

Audit every existing alert against one question: "if this fires at 3am, does it require a human to do something right now?" If the answer is no, it's either not an alert (route it to a dashboard/ticket instead) or it's set to the wrong severity. The deeper fix is shifting from static threshold alerts ("CPU > 80%") to SLO-based alerting — alert on error-budget burn rate against a defined SLO (e.g. 99.9% success rate) rather than on a raw resource metric that may or may not actually be affecting users. A fast burn-rate alert (you'll exhaust a month's error budget in hours) is genuinely urgent; a slow burn (you'll exhaust it in weeks) can be a next-business-day ticket, not a page. This single change — alerting on user-facing impact via burn rate instead of raw thresholds — is usually what actually kills alert fatigue, more than tuning individual thresholds forever.

Q8.6Cost

Observability tooling can become one of the largest line items in a cloud bill. What actually drives that cost, and how do you control it?

Show answer

Three usual culprits: custom CloudWatch metrics (each metric × dimension combination is billed individually — an unbounded label like a per-user-ID dimension can silently create thousands of billed metric streams), log ingestion + retention volume (verbose DEBUG-level logging left on in production, or indefinite retention on logs nobody ever queries past 30 days), and high-cardinality trace/metric labels in general (a Prometheus label with unbounded cardinality, like a raw request ID, can blow up both memory and cost).

Controls: set log retention deliberately per log group rather than the default-forever, sample traces rather than capturing 100% of high-volume endpoints, audit custom metric dimensions for unbounded cardinality, and route genuinely low-value verbose logs to cheaper storage (S3 + Athena for occasional forensic queries) instead of a hot, expensive search index that assumes everything needs to be instantly queryable.

Q8.7Scenario

An alarm fires for elevated error rate, but every dashboard you pull up shows all-green. How do you reconcile that?

Show answer

First suspect: the dashboards and the alarm aren't actually looking at the same slice of traffic. Common causes — the alarm evaluates a shorter/different time window than the dashboard's default range, so a brief spike already rolled off the dashboard's view by the time you looked; the alarm is scoped to one dimension (a specific Availability Zone, a specific target group, a specific API route) while the dashboard shows an aggregate that dilutes a localized problem into invisibility; or the alarm and dashboard are genuinely reading from different data sources entirely (one from ALB access logs, another from application-emitted metrics) that can disagree during a partial outage.

Practical move: don't trust either view blindly — go straight to the alarm's own metric, at its exact evaluation period and dimension, and only then reconcile against the dashboard. "The dashboard looks fine so the alarm must be noisy" is exactly the instinct that causes real incidents to get dismissed early.

09 Microservices & Event-Driven Architecture

Preferred, not required — but ties directly into the Lambda and governance chapters, since most of AWS's event-driven primitives (SQS/SNS/EventBridge) are exactly what Lambda's async/poll event sources are built on.

Q9.1MessagingDecision

SQS, SNS, and EventBridge all move messages around. How do you actually pick between them?

Show answer

SQS: point-to-point, one consumer group processes each message (competing consumers), the message is retained until explicitly deleted — the right primitive for work queues and decoupling a producer's rate from a consumer's processing rate. SNS: pub-sub fan-out — one message, delivered to every subscriber (multiple SQS queues, Lambdas, HTTP endpoints) simultaneously — the right primitive when several independent systems all need to react to the same event. EventBridge: an event bus with content-based routing rules and a schema registry — the right primitive once you have many event types from many sources and need selective routing ("only route OrderCancelled events where region = eu-west-1 to this target") rather than every subscriber getting everything.

Rule of thumb that tends to land well: SQS for "one team's queue of work," SNS for "broadcast this one thing to everyone who cares," EventBridge for "we have a real event-driven platform with many producers and consumers and need routing/filtering as a first-class concept," not just fan-out.

Q9.2Design

Choreography vs. orchestration for a multi-step business process — what's the trade-off?

Show answer

Choreography: each service reacts to events and emits its own, with no central coordinator — service A finishes and publishes "OrderPlaced," service B reacts to that and publishes "PaymentCharged," and so on. Loosely coupled and easy to add a new reactive service without touching existing ones, but the overall business process isn't written down anywhere — reconstructing "what's the current state of order #4521" means correlating events across many services' logs.

Orchestration (Step Functions is the AWS-native tool for this): one central workflow explicitly calls each step in sequence and owns the state machine. Easier to see the whole process, easier to add compensating logic for a failure at step 3, but that orchestrator becomes a central dependency and a natural place for coupling to creep back in. Reasonable default: choreography for genuinely independent domain reactions ("when an order ships, both the analytics service and the loyalty-points service should know" — neither needs to block the other), orchestration for an actual multi-step transaction with defined success/failure/compensation semantics.

Q9.3Resilience

A downstream service starts responding slowly, not failing outright. How does that take down services that call it, and what pattern prevents it?

Show answer

Slow-but-not-failing is often worse than a clean failure — callers keep threads/connections open waiting, connection pools exhaust, and the problem propagates upstream even though the root-cause service technically never returned an error. A circuit breaker tracks failure/timeout rate per downstream dependency and, once it crosses a threshold, "opens" — failing fast locally without even attempting the call — for a cooldown period, then allows a small number of trial requests through ("half-open") to test recovery before fully closing again.

Pair with bulkheads (isolate connection pools/thread pools per downstream dependency, so one slow dependency can't exhaust the pool shared by calls to a completely unrelated one) and sensible timeouts with jittered exponential backoff on retries — a retry storm with no jitter, all clients retrying in lockstep, can itself take down a service that was only mildly struggling.

Q9.4Data Consistency

You can't use a single database transaction across microservices. How do you keep a multi-service operation consistent?

Show answer

The saga pattern — a sequence of local transactions, each in its own service's own database, where every step has a defined compensating action to undo it if a later step fails. Book the flight (local transaction) → charge the card (local transaction) → if hotel booking then fails, run the compensating actions in reverse: refund the card, cancel the flight. Nothing is ever atomic across the whole chain the way a single SQL transaction would be — briefly, the system can be in a state where the flight is booked but the trip overall will end up cancelled — which is why sagas are a genuine trade-off (eventual consistency, real complexity in writing correct compensations) and not a free replacement for a transaction, worth saying explicitly rather than presenting it as a strictly-better alternative.

Q9.5Evolution

How do you change an event's schema without breaking every consumer that's already subscribed to it?

Show answer

Treat event schemas with the same discipline as a public API contract, because that's effectively what they are once multiple teams consume them. Additive changes (a new optional field) are safe by default if consumers are built to ignore unknown fields. Anything that changes or removes an existing field's meaning needs versioning — either a version field in the event envelope with consumers explicitly checking it, or, more robustly, publishing to a new event type/schema version and running both old and new in parallel until every known consumer has migrated off the old one, rather than mutating the existing schema under consumers' feet. EventBridge's schema registry can track this formally and even generate consumer-side bindings from the registered schema, which helps catch a breaking change at development time rather than at 2am in production.

Q9.6Scenario

One service goes down and, within minutes, four unrelated-looking services also start failing. What's the likely architectural root cause, and what would you check first?

Show answer

Classic sign of a synchronous dependency chain masquerading as "microservices" — if service D calls C, which calls B, which calls A synchronously and blocks waiting for a response, A going down cascades through the whole chain within minutes as each layer's connection pools and timeouts get exhausted. First check: pull the actual call graph (from traces, not the architecture diagram someone drew eight months ago — diagrams drift) for the failing services and look for synchronous, blocking calls between services that "shouldn't" be tightly coupled.

The fix is rarely just "add a circuit breaker" as a band-aid — it's worth asking in the interview answer whether that dependency needed to be synchronous at all. A lot of these chains exist because a request-response call was the easiest thing to write initially, when the actual business requirement ("service D eventually needs to know what happened in A") could have been an async event instead, decoupling the failure domains entirely rather than just failing faster once coupled.

10 Kubernetes Administration & Cluster Management

The JD's preferred bullet says "administration and cluster management" specifically — distinct from workload-level troubleshooting, which your other Kubernetes handbooks already cover in depth. This chapter stays on the cluster-governance layer: who can do what, how tenants are isolated, and how the cluster itself is kept healthy.

Q10.1RBAC

How do you design RBAC for a cluster shared by multiple application teams?

Show answer

Role + RoleBinding for anything namespace-scoped — a team gets a Role granting get/list/watch/create/update on the resource types they actually need (pods, deployments, configmaps) within their own namespace(s), bound via RoleBinding to their team's group (synced from your identity provider, not individual usernames hardcoded). ClusterRole + ClusterRoleBinding is reserved for genuinely cluster-scoped needs — reading nodes, managing CRDs, anything the platform team itself needs — and should almost never be handed to an application team wholesale.

Practical discipline: avoid binding the built-in cluster-admin ClusterRole to anyone routinely; if a team insists they need broad access "to debug," that's usually a signal for better tooling (a read-only ClusterRole for cross-namespace visibility, or a proper observability stack) rather than a reason to hand out admin.

Q10.2Multi-tenancy

Three teams share one cluster via namespaces. What actually enforces that isolation, beyond the namespace boundary itself?

Show answer

A namespace alone is just a naming/RBAC scope — it does not isolate network traffic or resource consumption by default. Real isolation needs three things layered together: a ResourceQuota per namespace capping total CPU/memory/object counts so one team can't starve the cluster; a LimitRange setting default and max per-container requests/limits so a single misconfigured pod without explicit limits doesn't consume unbounded resources; and a default-deny NetworkPolicy per namespace so pods can't reach other teams' pods unless explicitly allowed — without that last one, any pod on the cluster can talk to any other pod on the pod network regardless of namespace.

Q10.3Pod Security

How do you stop teams from deploying pods that run as root or with a privileged security context?

Show answer

Pod Security Admission (the built-in successor to the deprecated PodSecurityPolicy) enforces one of three predefined levels — privileged, baseline, or restricted — via a namespace label, evaluated by the API server itself at admission time with no separate controller to deploy or maintain.

apiVersion: v1
kind: Namespace
metadata:
  name: orders
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted

restricted blocks root, privilege escalation, host namespace access, and non-default capabilities — the right baseline default for most application namespaces. For anything needing finer-grained custom policy than the three built-in levels offer — "images must come from this specific registry," "every pod must set resource limits" — that's where an external policy engine like Kyverno or OPA Gatekeeper comes in as a validating (or mutating, for auto-injecting defaults) admission webhook layered on top.

Q10.4Maintenance

How do you take a node out of service for maintenance without causing an outage for the workloads on it?

Show answer

kubectl cordon <node> first — marks it unschedulable so no new pods land there, but doesn't touch what's already running. Then kubectl drain <node> evicts existing pods so the scheduler places them elsewhere, respecting any PodDisruptionBudget defined for those workloads — a PDB says "never evict more than N pods (or below M% availability) of this deployment at once," so drain will wait/retry rather than take down every replica of a service simultaneously just because they all happened to be on the same node.

The part that trips people up: drain honors PDBs and will simply stall if a PDB can't be satisfied (e.g. a single-replica deployment with a PDB requiring at least 1 available) — that's correct, protective behavior, not a bug, and the fix is either temporarily scaling that deployment up first or accepting the brief unavailability deliberately, not force-deleting the PDB to make drain proceed.

Q10.5EtcdEKS Context

What's your etcd backup and disaster recovery strategy — and does that answer change on EKS specifically?

Show answer

On self-managed Kubernetes, etcd backup is squarely your responsibility — regular etcdctl snapshot save to durable storage off-cluster, tested restore procedures (a backup nobody has ever restored from isn't a real backup), and awareness that etcd is quorum-based, so losing a majority of members without a snapshot means real, unrecoverable data loss for the entire cluster state.

On EKS specifically, this is abstracted away — AWS operates and backs up the control plane, including etcd, as part of the managed service; you don't have (or need) direct etcd access at all. Worth stating this explicitly if asked, rather than describing self-managed etcd procedures as if they apply on EKS — it signals you actually understand what "managed control plane" means rather than reciting generic Kubernetes admin knowledge without adapting it to the platform in front of you.

Q10.6ScenarioMulti-tenancy

You've set ResourceQuotas on every namespace, but one team's workload is still degrading performance for everyone else on shared nodes. What's missing?

Show answer

A ResourceQuota caps the sum of requests/limits a namespace can declare — it doesn't guarantee isolation of actual resource usage on a shared node if individual pods don't set requests/limits correctly, or if limits are set far above requests ("limit overcommit"). A pod with a low CPU request but no limit can burst and consume most of a node's available CPU the moment it's under load, starving CPU-hungry-but-well-behaved neighbors on that same node even though the offending namespace is technically still under its quota's aggregate ceiling.

Fixes: a LimitRange enforcing that every container gets an explicit limit (not just a request) by default; for genuinely noisy or untrusted tenants, dedicating a separate node group/taint so their workloads physically can't share nodes with anyone else regardless of what quotas say; and checking whether Quality of Service class matters here — Guaranteed QoS pods (requests == limits) are the last to be evicted under node pressure, while the noisy tenant's pods, if Burstable or BestEffort, should arguably be the first.

11 DevSecOps & Security Automation

Preferred skill, but overlaps heavily with the governance chapter's CI/CD emphasis — expect it to surface as "how do you automate security" follow-ups on Chapter 07 and 06 answers rather than as a fully separate block of questions.

Q11.1Shift-Left

Where in the pipeline does each type of security scan belong, and why does the order matter?

Show answer

Roughly fastest-and-cheapest to slowest-and-most-realistic, and each stage should fail fast before the next runs:

  • Pre-commit / IDE — secrets scanning (gitleaks) so a credential never even reaches a commit, let alone a remote repo.
  • SAST (Semgrep, CodeQL) on every PR — static analysis of your own code for known-bad patterns (SQL injection shape, hardcoded credentials, insecure deserialization) — fast, no running environment needed.
  • SCA / dependency scanning (Dependabot, Snyk) — known CVEs in third-party packages, also on every PR.
  • IaC scanning (Checkov/tfsec, from the Terraform chapter) — before any plan touches real infrastructure.
  • Container image scanning (Trivy, ECR native scanning) at build time, before push to a registry — catches OS-package and base-image CVEs the SAST/SCA layers above don't see.
  • DAST against a running staging environment — the only layer that finds issues only visible at runtime (misconfigured headers, actual exploitable auth flows) — necessarily the slowest and latest stage.

The ordering principle: put the cheapest, fastest checks first so a developer gets feedback in seconds, not after a 20-minute DAST run — failing fast on a secrets leak shouldn't require waiting for the full pipeline to reach the end.

Q11.2Container Security

Where should container image scanning run — build time, registry, or runtime — and why not just pick one?

Show answer

All three catch different windows of exposure, which is why mature pipelines run more than one: build-time scanning (Trivy in the CI pipeline) stops a known-vulnerable image from ever being pushed in the first place — the cheapest place to block it. Registry scanning (ECR's native scan-on-push, or a periodic rescan) matters because CVE databases update continuously — an image that was clean when built can become "vulnerable" the next day when a new CVE is published against a package already baked into it, and only a rescan catches that without a new build. Runtime scanning/monitoring (checking what's actually running in the cluster right now against current CVE data) is the backstop for images that were already deployed before either of the earlier gates existed, or before a policy was tightened.

Q11.3SBOM

What's an SBOM, and why would a governance-focused role care about generating one for every build?

Show answer

A Software Bill of Materials is a machine-readable inventory of every component — direct and transitive dependencies, OS packages, their exact versions — that went into a build artifact, typically in SPDX or CycloneDX format. The governance payoff shows up the day a new critical CVE drops in some widely-used library: instead of every team manually checking "do we even use this package, and where," you query your SBOM inventory and get an authoritative answer in minutes across every service, which is exactly the kind of capability that turned a chaotic multi-week scramble into a bounded, auditable response during real large-scale incidents in the industry (the Log4Shell response being the canonical example of why this now gets asked in interviews at all). Generating one is usually a single extra step in the build pipeline (syft or similar against the final image), attached to the build as an artifact alongside the image itself.

Q11.4PolicyTrap

Should a security scan finding automatically fail the build, or just warn? How do you decide?

Show answer

Blanket "fail on any finding" policies get bypassed — developers find the fastest workaround (disabling the check, adding a blanket ignore file) the first time a false positive or a low-severity finding blocks an urgent fix, and once that workaround pattern exists, it gets reused for real findings too. The pattern that actually holds: gate on severity threshold, not presence of any finding — fail the build on Critical/High with no fix available differently than on Medium/Low, which can be tracked as a ticket with an SLA instead of blocking; and offer an explicit, logged, time-bound exception process (a documented waiver with an owner and expiry, reviewed by security) for the rare legitimate case, rather than an undocumented ignore-comment that quietly becomes permanent.

⚠ Interviewers sometimes frame this as "should security block a deploy, ever" specifically to see if you'll say an absolute yes or no — the stronger answer is threshold- and context-based, with an explicit, auditable exception path rather than either extreme.
Q11.5Culture

You've rolled out security scanning across every pipeline. Six months later, most findings are being ignored. What went wrong, and what do you actually do about it?

Show answer

Usually a signal-to-noise problem, not a culture problem people default to blaming first. If findings routinely include low-severity noise or a high false-positive rate, developers stop reading them entirely — including the real ones buried in the same list. Fixes that actually change behavior: tune the tool's ruleset down to what's genuinely actionable for this codebase before rolling out broadly (a scanner with sane defaults out of the box is rare), surface findings where developers already work (a PR comment with a specific fix suggestion, not a separate dashboard nobody checks), and track a "mean time to remediate" metric by team as a visible signal rather than only measuring "number of findings" — the latter can even perversely reward teams for having less mature code that generates fewer findings because it's simpler, not more secure.

Q11.6Scenario

A critical CVE is published against a base image that ~40 production services are built on. Walk through your response.

Show answer

First, scope the actual blast radius before reacting broadly — query your SBOM/registry scan data for exactly which of those 40 services are actually vulnerable (the CVE might be in a package path that's present but never invoked, which some scanners can distinguish via reachability analysis) rather than treating all 40 as equally urgent on assumption alone. Prioritize by exposure: internet-facing services with the vulnerable code path reachable first, internal-only or unreachable-path services later.

Then: patch the base image once centrally, rebuild affected service images against it (this is where a GitOps/reusable-workflow setup pays for itself — a base image bump can trigger rebuilds across many repos via a single coordinated change rather than 40 manual PRs), and roll out via your normal progressive deployment path rather than a simultaneous force-push everywhere, which risks turning one CVE into a self-inflicted outage. Communicate a timeline to security/compliance stakeholders with the prioritized list, since "we're patching, in this order, done by this time" is a materially better answer during an audit than silence followed by "it's fixed now."

12 Scenarios & Troubleshooting

Cross-cutting incidents that pull from several chapters at once — the format senior/AVP-level rounds actually use to see judgment, not recall. Each one is laid out as: the setup, your first move, and what you're actually checking for.

Q12.1Incident

3 AM page: a production EKS-hosted service is returning 5xxs to customers. Walk through your first 15 minutes.

Show answer
First move

Confirm scope before touching anything — is this one service, one AZ, or cluster-wide? Pull the alarm's exact dimension and a top-level dashboard (error rate, latency, traffic) for the affected service specifically. Scope determines urgency and who else needs to be pulled in; don't start debugging pods before you know if this is actually a single-service problem or a symptom of something bigger (a node group issue, a shared dependency).

What you're checking

kubectl get pods -n <ns> for CrashLoopBackOff/pending state, kubectl describe and recent events for anything that just changed, and — critically — whether a deploy went out recently. A huge fraction of real 3am pages are "the last deploy broke something," so check the deployment's rollout history and recent commits before assuming it's an infrastructure fault. If a recent deploy is the likely cause, rolling back is almost always faster than root-causing forward under pressure.

Judgment signal

Mitigate first, root-cause after — roll back or scale out to stop customer impact, then investigate why with the pressure off. Trying to find the exact root cause while customers are actively affected, when a rollback would resolve it in two minutes, is the mistake this question is designed to surface.

Q12.2IncidentTerraform

A shared Terraform module update is queued to merge, and the plan shows it will touch 60 resources across 8 services — far more than expected for what looked like a small change. What do you do before approving?

Show answer
First move

Stop and read the plan output carefully rather than trusting the PR description — specifically distinguish update in-place from replace (force-new) in the plan. A small-looking change to a shared module (e.g. changing an argument that's actually immutable on the underlying resource) can silently force replacement of every resource built from it — that's the difference between "60 minor updates" and "60 resources destroyed and recreated," including possibly stateful ones.

What you're checking

Whether any of the affected resources are stateful/hard-to-recreate (databases, resources holding data or identity that matters — an ALB whose DNS name downstream systems depend on). If replacement is real and touches anything like that, this isn't a normal merge — it needs a maintenance window, explicit sign-off from affected service owners, and likely a staged rollout (apply to one service's copy of the module first, verify, then the rest) rather than one big-bang apply across 8 services simultaneously.

Judgment signal

The instinct to actually read a large plan diff line-by-line before approving — not just check that CI is green — is exactly what this question tests. "Terraform plan passed" and "this plan is safe to apply" are not the same statement.

Q12.3IncidentCost

Finance flags that yesterday's AWS bill is roughly double the daily average, with no known change deployed. How do you find the cause quickly?

Show answer
First move

Cost Explorer, grouped by service, filtered to yesterday specifically — this narrows "the whole bill doubled" to "which specific service's spend actually doubled" in under a minute, which is nearly always faster than guessing based on what changed recently.

What you're checking

Once the service is identified, the usual suspects in rough order of frequency: an Auto Scaling Group or Karpenter that scaled way up and never scaled back down (a stuck scale-in, or a runaway job that kept triggering scale-out); a Lambda function stuck in a retry loop against a failing downstream, burning invocations; a misconfigured cross-region data transfer (someone pointed traffic at the wrong region, incurring transfer charges that don't exist for same-region traffic); or, if no deploy happened, check whether a scheduled job (a nightly batch, a cron-triggered Step Function) simply processed an unusually large input that day — sometimes it's not a bug, it's real, valid usage that needs a capacity conversation, not a fix.

Judgment signal

Don't assume "no known change deployed" means no change happened — check for autoscaling events and scheduled/triggered jobs specifically, since those are exactly the kind of change that doesn't show up in a deploy log.

Q12.4IncidentIAM

A service that's worked fine for months suddenly can't assume a cross-account role — right after the security team rolled out new org-wide SCPs. Where do you look?

Show answer
First move

Given the timing, treat the new SCP as the prime suspect before re-checking IAM policies that haven't changed — this connects directly back to the policy-evaluation-order question: SCPs are a hard ceiling that can silently block an action even though the role's own identity policy and the target's trust policy are both still perfectly correct and unchanged.

What you're checking

sts:AssumeRole (or the specific action now failing) against the new SCP's explicit denies and allow-list conditions for both the source and destination accounts — a common real cause is a new SCP restricting sts:AssumeRole to specific role-name patterns or requiring a condition (like an org ID check) that this particular cross-account trust relationship doesn't satisfy.

Judgment signal

Resist the instinct to "fix" it by loosening the service's own IAM policy — if the policy hasn't changed and the SCP has, widening the identity policy won't fix an SCP-level block and just adds unnecessary permissions. Correlating the timing to the actual change that happened is the whole answer here.

Q12.5IncidentCI/CD

GitHub Actions shows the deploy job succeeded and green, but the production behavior clearly hasn't changed. What's your investigation order?

Show answer
First move

Verify what actually got deployed where — confirm the image tag/commit SHA that's actually running in production right now (via the running task/pod's image, not the workflow log's claim that it deployed) matches the commit you expect. A "successful" deploy job can still have deployed to the wrong target, or deployed correctly but a caching layer (CDN, ALB connection reuse, browser cache during testing) is masking the change.

What you're checking

Common real causes: the workflow deployed to the correct ECS service/EKS namespace but the wrong environment (staging config accidentally pointed at what you thought was prod); a rolling deployment is still mid-rollout and old + new versions are both serving traffic, so what you're testing against happened to hit an old replica; or the change is real but sits behind a feature flag that wasn't flipped as part of this deploy.

Judgment signal

"Green in CI" only proves the pipeline's steps returned exit code 0 — it proves nothing about whether the deployed artifact is correct or whether it's actually serving the traffic you're testing. Treating pipeline success as equivalent to "verified in production" is the gap this question is probing.

Q12.6IncidentLambda

An SQS-triggered Lambda has silently stopped processing — the queue depth is climbing, but there are no Lambda errors in the logs at all.

Show answer
First move

No errors at all, combined with a growing queue, points away from "the function is failing" and toward "the function isn't being invoked in the first place" — check the event source mapping's state first (aws lambda get-event-source-mapping), not the function's own logs.

What you're checking

An event source mapping can be silently Disabled (someone paused it during a prior incident and forgot to re-enable it) or stuck in a failed state if it can no longer assume the execution role's permissions to poll the queue (an IAM change broke sqs:ReceiveMessage/sqs:DeleteMessage access without touching the function's own logs at all, since it never got invoked to log anything). Also check whether reserved concurrency was set to 0 on the function — a common "temporarily pause processing" move during an incident that's easy to forget to revert.

Judgment signal

Recognizing that "zero errors" is itself a data point, not the absence of one — it should redirect your investigation toward the invocation layer instead of the function's internal logic.

Q12.7IncidentAgentCore

A newly-launched AgentCore-based internal assistant is generating a much higher AWS bill than projected within its first week. How do you investigate an agent workload's cost, specifically?

Show answer
First move

Pull per-session tool-call and token counts from AgentCore Observability, not just the aggregate bill — for agentic workloads the useful unit of cost analysis is "cost per session/conversation," analogous to "cost per request" for a normal API, and that view will show you immediately whether cost is spread evenly or concentrated in a small number of runaway sessions.

What you're checking

The most common real cause: an agent stuck in a reasoning loop — repeatedly calling the same tool, or the model second-guessing itself across many turns for a single user request, multiplying both model-token cost and Gateway/tool-invocation cost per session far beyond what a well-scoped interaction should need. Check whether there's a hard cap on tool calls or turns per session at all — if the agent has no bounded retry/loop limit, one confused session can run essentially unbounded.

Judgment signal

This is the "cost is per-token, not per-request" operational difference from Chapter 5 showing up as a real incident — recognizing that traditional per-request cost intuition doesn't transfer directly to agentic workloads, and that the fix is often a guardrail (max tool calls, max turns, a timeout) rather than an infrastructure-level cost optimization.

Q12.8IncidentGovernance

A compliance audit flags an IAM role that has far more permissions than the service using it appears to need. How do you tighten it without risking an outage?

Show answer
First move

Never edit the live role's policy directly first — pull its actual usage history via IAM Access Analyzer's policy generation (or CloudTrail directly) over a window long enough to capture infrequent-but-legitimate paths, not just typical daily traffic.

What you're checking

Specifically look for monthly/quarterly/annual jobs that might not have fired during a short observation window — a permission that looks "unused" over two weeks might be exercised by a month-end batch job or an annual DR test, and removing it based on a too-short window is how "least privilege cleanup" causes an outage weeks later that's hard to trace back to this change.

Judgment signal

Deploy the tightened policy to a copy of the role (or in monitor-only/audit mode if the tooling supports it) first, watch for AccessDenied events, and only cut the actual role over once you're confident — treating "reduce this role's permissions" as a change with real regression risk, not a pure cleanup task with no downside.

Q12.9Design

Sketch a disaster recovery plan for an EKS + RDS stack that needs to survive a full region outage.

Show answer
First move

Establish the actual requirement before designing anything — RTO/RPO drive cost and complexity enormously, and "survive a region outage" means very different architectures depending on whether minutes of downtime and data loss are acceptable versus effectively none.

What you're checking / designing

For RDS: cross-region read replica (async, some replication lag = non-zero RPO) promotable to primary on failover, or Aurora Global Database for tighter RPO (typically sub-second lag) with a faster managed failover path. For EKS: since the control plane itself is regional, DR means a second cluster already running (or ready to be stood up quickly from IaC) in the DR region, with application manifests/Helm values already in the GitOps repo ready to sync — not something built from scratch during the actual incident. Route 53 health-check-based failover routing (or a global accelerator) shifts traffic once the DR region is confirmed healthy.

Judgment signal

The strongest answer states the RTO/RPO trade-off explicitly and ties the architecture to it, rather than reflexively describing the most expensive/complex option (active-active everywhere) as if it's always correct — and mentions that none of this counts as a real DR plan until it's actually been tested with a real failover exercise, not just documented.

Q12.10Incident

You're paged for elevated p99 latency. Every individual dashboard — CPU, memory, error rate — looks completely normal. First 15 minutes?

Show answer
First move

Normal resource metrics with elevated latency points away from "something is overloaded" and toward "something is waiting" — go straight to traces for a slow request rather than continuing to stare at metrics that have already told you they're not the answer.

What you're checking

A trace for one of the actually-slow requests usually shows the answer directly: a downstream dependency (a database, an external API, another internal service) taking longer than usual even though its own dashboards look fine too — a common cause is connection pool exhaustion (requests queueing for a free connection, which shows up as latency, not as an error, and doesn't move CPU/memory at all) or a slow query that's within "normal" CPU usage but is newly slow due to a changed query plan, missing index, or data growth crossing some threshold.

Judgment signal

Recognizing when to stop trusting aggregate dashboards and go straight to a trace of one specific slow request is the actual skill — dashboards answer "is the service healthy on average," traces answer "why was this one request slow," and this scenario is deliberately built so only the second question has the answer.

Q13.1Role Fit

Your certifications are AZ-104 and SC-300 — Azure. This JD is entirely AWS. How do you handle that if it comes up?

Show answer

Don't wait for them to ask this as a gotcha — a brief, confident, proactive line early in the technical conversation removes it as a lingering doubt instead of leaving it as an unspoken question they're privately weighing throughout the interview. The honest framing: certifications reflect which platform you formally validated at a point in time, not the ceiling of your hands-on depth — and the deeper Terraform, Kubernetes, IAM, and CI/CD concepts this JD actually tests are the same underlying discipline regardless of which cloud's specific API you're calling.

Then let the rest of the interview do the actual proving — if your AWS answers throughout (ECS/EKS specifics, IAM policy evaluation order, GitHub Actions OIDC) are genuinely fluent, the cert mismatch becomes a non-issue in practice. If pushed further, it's fair and honest to say AWS certification is a reasonable next step and name a timeline, the same way you'd approach any skill gap directly rather than deflecting.

Q13.2OwnershipHigh-Value

"Did you design this architecture, or did you operate something someone else designed?" How do you answer this without it sounding like a weakness?

Show answer

This is the exact question that cost you ground in the Quantiphi round 2 — worth having a deliberate answer ready rather than improvising it live again. The instinct to avoid: "I didn't do that" or "the platform team handled that" stated flatly, which reads as low ownership even when it's true and honest.

🎯 The reframe that actually works: "The platform team owned the initial design; my role was operating, troubleshooting, and evolving it" — then immediately back it with a specific example of something you changed, tuned, or fixed within that architecture. That single sentence does three things at once: stays completely honest about the org structure, claims real ownership over what you actually did, and gives them a concrete example to probe deeper into — which is usually where you can show genuine depth even on a system you didn't originally design.

If you're being asked this repeatedly across a loop, it's also a legitimate signal worth reflecting on honestly for yourself: it may mean this specific role expects more architecture-authorship than your recent experience has given you, which is worth weighing against the role level, not just worth better-scripting your way past.

Q13.3Seniority

You have 14+ years of experience against a role asking for 7+. How do you frame that without sounding overqualified or like a flight risk?

Show answer

Interviewers ask versions of this because they're genuinely worried about two things: will you be bored/disengaged, and will you leave the moment something more senior appears. Address both directly rather than hoping they don't ask. On engagement: be specific about what's genuinely interesting to you in this particular role — the AgentCore/agentic-AI angle is a legitimately good, true answer here, since it's new enough that even someone with 14 years of experience is learning it fresh alongside everyone else, which naturally explains why a broader, more senior role wouldn't feel like a step down.

On flight risk: be honest that you're targeting AVP/architect-level roles as the longer-term direction, but frame this specific opportunity on its own terms — what about it (team, scope, the technical mix, the company) makes it a genuine fit right now, not just a placeholder. Vague reassurance ("I'm just looking for a good team") reads as evasive; a specific, honest reason reads as someone who actually evaluated the role rather than applying broadly and hoping.

Q13.4STAR

"Tell me about a time you disagreed with a security or architecture decision." What makes an answer here land well vs. poorly?

Show answer

Weak versions of this answer are either "I just complied" (reads as no judgment/backbone) or "I was right and they eventually agreed" told as a pure vindication story (reads as difficult to work with, especially for a role explicitly built around collaborating with architecture and security teams). The version that actually lands: state the disagreement specifically and technically (not "I thought it was too slow," but the actual trade-off — e.g. a security team wanted a control that would have added real latency to a critical path, and you had a specific concern about that), show that you understood their reasoning before pushing back, describe the actual conversation or data you brought to resolve it, and land on the outcome honestly — including if the outcome was "they were right and I updated my view," which is a perfectly strong answer too and often more credible than always being the one who was right.

Q13.5STAR

"Tell me about a production incident you were responsible for." How do you talk about a mistake you made without either minimizing it or over-flagellating?

Show answer

Pick a real incident with genuine stakes — a story where nothing actually went wrong isn't credible at 14 years of experience, and interviewers notice when a candidate visibly picks the safest, lowest-consequence example available. Structure: what happened and your specific role in it, stated plainly with no hedging language ("I applied a change that..." not "a change was made that..."), how you diagnosed and resolved it, and — the part that actually differentiates a senior answer — what changed afterward as a direct result: a new safeguard, a process change, a piece of automation that makes the same class of mistake structurally harder to make again, not just "I was more careful after that."

The tone to land: matter-of-fact ownership, not self-flagellation and not defensiveness — the same register you'd want from someone on your own team debriefing an incident with you.

Q13.6Collaboration

The JD says you'll "collaborate with architecture, security, and engineering teams to enforce cloud standards." How do you talk about enforcing a standard on a team that doesn't want to follow it?

Show answer

A platform role without any formal authority over other teams' roadmaps has to earn compliance rather than mandate it in most organizations — the strongest answers describe making the compliant path the easy path (a golden-path Terraform module, a reusable GitHub Actions workflow that already has the security scanning and tagging built in, so opting in is less work than opting out) rather than relying purely on policy documents or escalation. Where a hard technical gate genuinely is appropriate (the governance chapter's SCP/Config-rule enforcement), be able to describe how you introduced it without blindsiding teams — advance notice, a grace period with warnings before hard-blocking, and a clear escalation/exception path for legitimate edge cases — since a governance rollout that feels punitive tends to generate workarounds instead of compliance.

Q13.7Leadership

At 14+ years of experience, expect some version of "how do you help less experienced engineers grow" even in an IC-titled role. What makes a strong answer?

Show answer

Avoid the generic "I do code reviews and pair programming" answer — true, but so generic it doesn't differentiate you from anyone. A specific, memorable answer names an actual mechanism you've used repeatedly: turning a recurring type of incident into a documented runbook so the next person doesn't need you specifically to resolve it, deliberately pairing a junior engineer on an on-call shift rather than shielding them from it, or writing something once (a style of the interview handbooks you build for yourself, generalized) that scales your knowledge beyond one-on-one conversations. The signal being tested for a senior IC role: does this person make the people and systems around them better, not just their own individual output — that's what separates a senior IC from a mid-level one at 7+ years, and it's a fair question even without a formal management title.
