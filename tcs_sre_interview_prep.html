Part 1 · Round 1 Prep

Questions 1–30

Kubernetes — Highest Priority

Q1–10
Question 1

A production pod is in CrashLoopBackOff. How do you troubleshoot?

Answer

I first check the pod status and events:

kubectl get pods -n <namespace>
kubectl describe pod <pod-name> -n <namespace>

Then I check the current and previous container logs:

kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous

I specifically look for:

  • Application exceptions
  • Configuration errors
  • Missing environment variables
  • Secret/configmap issues
  • Failed health probes
  • OOMKilled
  • Dependency/database connectivity problems

Then I check the deployment configuration:

kubectl get deployment <deployment> -o yaml

If the container is being killed because of memory, I check:

kubectl describe pod <pod-name>

and look for OOMKilled.

I don't immediately restart the pod. I first identify the root cause and then fix the underlying issue.

Question 2

A pod is stuck in Pending. What will you check?

Answer

I start with:

kubectl describe pod <pod-name>

The Events section usually tells me why scheduling failed.

I check:

  • CPU/memory availability
  • Node selectors
  • Node affinity
  • Taints and tolerations
  • Resource requests
  • Availability zones
  • PVC binding
  • Node readiness

Then:

kubectl get nodes
kubectl describe node <node-name>

For example, if the pod requests 4 CPU but no node has 4 allocatable CPUs, the scheduler cannot place it.

If it is a taint issue, I check:

kubectl describe node <node-name> | grep -i taint

I fix the scheduling constraint rather than manually forcing the pod onto a node.

Question 3

Production pods are getting OOMKilled. How do you troubleshoot?

Answer

First:

kubectl describe pod <pod-name>

I check the container's memory limit and the termination reason.

Then I inspect resource usage:

kubectl top pod -n <namespace>
kubectl top node

I compare actual memory consumption with:

resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"

Possible causes include:

  • Application memory leak
  • Incorrect memory limit
  • Large workload
  • JVM heap configuration
  • Traffic spike

I would correlate this with application metrics and historical memory utilization.

Short-term, I may increase the limit if justified. Long-term, I would investigate the application memory behavior and right-size resources.

Question 4

Kubernetes service is running, but users cannot access the application. What do you check?

Answer

I troubleshoot layer by layer.

First:

kubectl get pods -n <namespace>
kubectl get svc -n <namespace>
kubectl get endpoints -n <namespace>

I verify that the Service has healthy endpoints.

Then:

kubectl describe svc <service>

I verify the Service selector matches the pod labels.

For example:

selector:
  app: payment

must match:

labels:
  app: payment

Then I test connectivity from inside the cluster:

kubectl run test --rm -it --image=curlimages/curl -- sh
curl http://<service>:<port>

If internal connectivity works, I move outward to:

Pod → Service → Ingress/LoadBalancer → DNS → External client
Question 5

Pods are healthy but Service has no endpoints. Why?

Answer

The most common reason is a label-selector mismatch.

I check:

kubectl get pods --show-labels
kubectl describe svc <service>
kubectl get endpoints <service>

Suppose Service has:

selector:
  app: backend

but pods have:

app: backend-v2

The Service won't select those pods.

I would correct the selector or pod labels through the deployment configuration and verify the endpoints afterward.

Question 6

Pods are running, but readiness probe is failing. What do you do?

Answer

I first inspect:

kubectl describe pod <pod-name>

Then check application logs:

kubectl logs <pod-name>

I verify:

  • Probe endpoint
  • Port
  • HTTP status
  • Initial delay
  • Timeout
  • Failure threshold
  • Application startup time

For example:

readinessProbe:
  httpGet:
    path: /health
    port: 8080

I test the endpoint inside the pod:

kubectl exec -it <pod> -- curl localhost:8080/health

If the application needs 60 seconds to start but the probe begins after 5 seconds, I adjust the probe configuration appropriately.

Question 7

ImagePullBackOff occurs in production. How do you troubleshoot?

Answer

First:

kubectl describe pod <pod-name>

I inspect Events.

Typical causes:

  • Incorrect image name/tag
  • Image doesn't exist
  • Registry unavailable
  • Authentication failure
  • imagePullSecrets missing
  • Network/DNS problem

I verify:

kubectl get deployment <deployment> -o yaml

If using a private registry, I verify:

kubectl get secrets

and check the imagePullSecrets.

I don't simply change the image tag without confirming what was actually deployed.

Question 8

One Kubernetes node suddenly becomes NotReady. What do you check?

Answer

I check:

kubectl get nodes
kubectl describe node <node>

Then investigate:

  • Kubelet
  • Container runtime
  • CPU/memory pressure
  • Disk pressure
  • Network connectivity
  • Node conditions

On the node:

systemctl status kubelet
journalctl -u kubelet

I also check:

df -h
free -m

If it is a production node and workloads are affected, I may cordon/drain it depending on the situation:

kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets

Then I restore the node or replace it depending on the infrastructure design.

Question 9

Production deployment caused errors. How would you rollback?

Answer

First I confirm whether the deployment is actually responsible using logs, metrics and deployment timing.

Then:

kubectl rollout status deployment/<deployment>
kubectl rollout history deployment/<deployment>

If rollback is required:

kubectl rollout undo deployment/<deployment>

Then:

kubectl rollout status deployment/<deployment>

I verify:

  • Error rate
  • Latency
  • Pod health
  • Business transactions

After stabilization, I investigate the failed release through RCA.

Question 10

Kubernetes pods are restarting continuously, but there is no OOMKilled. What could be wrong?

Answer

I check:

kubectl describe pod <pod>
kubectl logs <pod>
kubectl logs <pod> --previous

Potential causes:

  • Application crash
  • Liveness probe failure
  • Configuration issue
  • Dependency failure
  • Incorrect command/entrypoint
  • Missing Secret/ConfigMap
  • Network connectivity problem

I specifically check the container exit code and Events to determine whether Kubernetes is killing the container or the application itself is exiting.

Terraform — Production Scenarios

Q11–15
Question 11

Terraform deployment is failing in production. What is your approach?

Answer

I don't immediately run terraform apply.

First:

terraform init
terraform validate
terraform fmt
terraform plan

I examine the plan carefully.

Then I check:

  • Provider authentication
  • State file
  • State locking
  • Resource dependencies
  • Variables
  • Backend
  • Recent code changes

For production, Terraform should normally run through a controlled CI/CD pipeline with plan approval.

Question 12

Terraform says the resource already exists. What do you do?

Answer

This usually means the resource exists in the cloud but is not present in Terraform state.

I first verify the resource.

Then I can import it:

terraform import <resource-address> <resource-id>

Then:

terraform plan

I make sure Terraform configuration matches the actual infrastructure before applying changes.

I would not recreate a production resource blindly.

Question 13

Terraform state is locked. How do you troubleshoot?

Answer

First I determine whether another Terraform operation is actually running.

If another pipeline is executing, I wait for it.

If the lock is stale, I investigate the backend and lock information.

Only after confirming that no valid Terraform operation is running would I consider:

terraform force-unlock <LOCK_ID>

Force-unlock is risky because removing a legitimate lock can cause concurrent state modifications.

Question 14

Terraform plan wants to recreate a production resource. What will you do?

Answer

I stop and investigate.

I identify why Terraform thinks replacement is necessary:

terraform plan

I check whether an attribute has changed that requires replacement.

I also check:

terraform state show <resource>

Possible causes:

  • Configuration drift
  • Changed immutable property
  • Provider behavior
  • Incorrect state
  • Resource renamed without terraform state mv

I would not approve the plan until I understand the replacement impact.

Question 15

Terraform deployment partially failed. What do you do?

Answer

First I inspect the Terraform error and state.

Terraform generally records successfully created resources in state even if a later resource fails.

I run:

terraform plan

to understand the remaining changes.

I fix the root cause and then apply again.

I avoid manually changing infrastructure unless necessary because that can introduce state drift.

Jenkins / CI-CD

Q16–19
Question 16

Jenkins pipeline suddenly starts failing. How do you troubleshoot?

Answer

I identify the failing stage first.

For example:

Checkout → Build → Test → Scan → Docker Build → Push → Deploy

I inspect Jenkins console logs.

Then check:

  • Git connectivity
  • Credentials
  • Agent availability
  • Disk space
  • Tool versions
  • Maven/Java versions
  • Docker daemon
  • Artifact repository
  • Network connectivity

On the Jenkins agent:

df -h
free -m
docker info
java -version
mvn -version

I compare the failure with the last successful build to identify what changed.

Question 17

Jenkins agent is offline. What do you check?

Answer

I check the Jenkins node status first.

Then:

  • Agent connectivity
  • Network
  • SSH
  • Disk
  • CPU/memory
  • Java process
  • Jenkins agent logs

For Linux agents:

systemctl status ssh
df -h
free -m
ps -ef | grep java

If it is a Kubernetes-based Jenkins agent, I check the corresponding pod:

kubectl get pods -n <jenkins-namespace>
kubectl describe pod <agent-pod>
Question 18

Jenkins pipeline is taking 40 minutes instead of 10. How do you investigate?

Answer

I compare stage-level execution times.

I determine whether the bottleneck is:

  • Git checkout
  • Dependency download
  • Unit tests
  • Security scanning
  • Docker build
  • Artifact upload
  • Deployment

Then I look at Jenkins historical builds.

For example, if Docker build time increased significantly, I investigate:

  • Dockerfile changes
  • Build context
  • Cache
  • Base image
  • Network

I would optimize the specific bottleneck instead of randomly increasing Jenkins resources.

Question 19

Jenkins deployment succeeded, but application is not working. What do you do?

Answer

A successful pipeline doesn't necessarily mean a successful deployment.

I verify the deployment target.

For Kubernetes:

kubectl rollout status deployment/<deployment>
kubectl get pods
kubectl get svc

Then check application logs and health endpoints.

I also verify:

  • Configuration
  • Secrets
  • Environment variables
  • Database connectivity
  • Service connectivity
  • Ingress
  • DNS

I correlate deployment time with application errors.

SRE / Production Incident Management

Q20–25
Question 20

Production API latency suddenly increases. How do you troubleshoot?

Answer

I first determine the scope:

  • Is it all APIs or one API?
  • All users or a subset?
  • One region or all regions?

Then I check the four golden signals:

Latency, Traffic, Errors, Saturation.

I check:

  • CPU
  • Memory
  • Network
  • Application response time
  • Database latency
  • Dependency latency
  • Load balancer metrics

For Kubernetes:

kubectl top pods
kubectl top nodes

I correlate application logs, Prometheus metrics and traces if available.

Then identify whether the bottleneck is application, infrastructure, database or external dependency.

Question 21

Error rate suddenly jumps to 20%. What is your response?

Answer

First, I declare/acknowledge the incident according to the incident-management process.

I check:

  • When did it start?
  • Which service?
  • Which endpoint?
  • Which deployment happened before it?
  • Which region?
  • HTTP status codes

I check dashboards and logs.

If there was a recent deployment and evidence points to it, I consider rollback.

At the same time, I communicate impact and mitigation status to stakeholders.

After recovery, I perform RCA and define preventive actions.

Question 22

CPU utilization is 95% on production servers. What do you do?

Answer

First I identify which processes consume CPU:

top
ps aux --sort=-%cpu | head

Then I determine whether it is:

  • Traffic spike
  • Application issue
  • Infinite loop
  • Batch job
  • Memory pressure causing CPU overhead
  • Insufficient capacity

I correlate with monitoring data.

If capacity is the issue, I scale horizontally or vertically depending on architecture.

If a process is abnormal, I investigate the application rather than simply killing it.

Question 23

Disk usage reaches 95%. What do you do?

Answer

First:

df -h

Then identify large directories:

du -sh /* 2>/dev/null | sort -h

Find large files:

find /var -type f -size +1G -ls

Common causes:

  • Application logs
  • Core dumps
  • Temporary files
  • Docker images
  • Old artifacts

I safely clean or rotate files according to retention policy.

For logs:

journalctl --disk-usage

Long-term solution would include log rotation, retention policies and monitoring disk utilization before it becomes critical.

Question 24

A production application cannot connect to the database. How do you troubleshoot?

Answer

I troubleshoot from the application outward.

First:

kubectl logs <pod>

Then verify DNS:

nslookup <db-host>

Test connectivity:

nc -vz <db-host> <port>

I check:

  • DNS
  • Security groups/firewall
  • Network ACL
  • Route tables
  • Database availability
  • Credentials
  • Connection pool
  • TLS certificates

If the DB is reachable but authentication fails, I investigate credentials.

If the DB is unreachable, I investigate networking and database availability.

Question 25

Users are reporting intermittent 502/503 errors. How do you troubleshoot?

Answer

I correlate the 502/503 timestamps with:

  • Load balancer logs
  • Ingress logs
  • Application logs
  • Kubernetes pod restarts
  • Readiness probes
  • Backend endpoint health

I check:

kubectl get endpoints
kubectl get pods
kubectl describe pod <pod>

Possible causes:

  • Backend pods unavailable
  • Readiness probe failures
  • Connection timeout
  • Overloaded application
  • Load balancer health-check failures
  • Network issue

I determine whether the error is generated by the load balancer, ingress or application.

Advanced Kubernetes Production Scenarios

Q26–30
Question 26

A deployment has 10 replicas, but only 7 are running. What do you check?

Answer

I check:

kubectl get deployment
kubectl get replicasets
kubectl get pods

Then:

kubectl describe deployment <deployment>

and:

kubectl describe pod <failed-pod>

I investigate whether the remaining pods are:

  • Pending
  • CrashLoopBackOff
  • ImagePullBackOff
  • Failing probes
  • Unable to schedule
  • Resource constrained

I also check ReplicaSet events.

The objective is to determine why desired replicas differ from available replicas.

Question 27

Kubernetes node is running out of disk. Pods are being evicted. What do you do?

Answer

I check:

kubectl describe node <node>
df -h

I look for DiskPressure.

Then investigate:

  • Container images
  • Container logs
  • Ephemeral storage
  • Deleted-but-open files

For example:

docker system df

depending on the container runtime.

I clean up safely and restore capacity.

Long term, I implement:

  • Log rotation
  • Ephemeral-storage requests/limits
  • Node monitoring
  • Proper image cleanup
  • Capacity planning
Question 28

A Kubernetes application works inside the cluster but not from outside. What is your troubleshooting flow?

Answer

I follow:

Pod → Service → Ingress/LoadBalancer → DNS → Internet

First:

kubectl get pods
kubectl get svc
kubectl get endpoints

Then test internally:

curl http://<service>:<port>

If internal access works, check:

kubectl get ingress
kubectl describe ingress <ingress>

Then investigate:

  • Load balancer
  • Security groups
  • Firewall
  • DNS
  • TLS certificate
  • Ingress controller

This isolates the failing network layer rather than troubleshooting everything simultaneously.

Question 29

A new Kubernetes release is causing production failures. How do you handle it?

Answer

My first priority is service restoration, followed by root-cause analysis.

I compare:

  • Current version
  • Previous version
  • Deployment timestamp
  • Error rate
  • Logs
  • Metrics
  • Configuration changes

If the release is clearly responsible and rollback is safe:

kubectl rollout undo deployment/<deployment>

Then verify:

kubectl rollout status deployment/<deployment>

After stabilization, I investigate the release.

For prevention, I would consider:

  • Canary deployment
  • Blue/green deployment
  • Automated smoke tests
  • Progressive delivery
  • Automated rollback based on SLO/error-rate thresholds
Question 30

Tell me how you would troubleshoot a complete production outage.

Answer

I would use a structured incident-response approach.

Step 1 — Confirm the incident

Check monitoring:

  • Availability
  • Error rate
  • Latency
  • Traffic
  • Infrastructure health

Step 2 — Determine scope

I identify:

  • Which service?
  • Which region?
  • All users or some users?
  • When did it start?

Step 3 — Check recent changes

I immediately look for:

  • Application deployment
  • Infrastructure changes
  • Terraform changes
  • Configuration changes
  • Certificate changes
  • DNS changes

Step 4 — Check infrastructure

For Kubernetes:

kubectl get nodes
kubectl get pods -A
kubectl get svc -A

Then inspect unhealthy workloads.

Step 5 — Check dependencies

I verify:

  • Database
  • Cache
  • Message queues
  • External APIs
  • DNS
  • Load balancers

Step 6 — Mitigate

Depending on the root cause:

  • Rollback deployment
  • Scale application
  • Remove unhealthy node
  • Restore service
  • Fail over to another region
  • Disable problematic feature

Step 7 — Verify recovery

I don't consider the incident resolved merely because pods are Running.

I verify:

  • HTTP success rate
  • Latency
  • Business transactions
  • Logs
  • SLOs
  • Customer impact

Step 8 — RCA

After recovery:

Root cause → Contributing factors → Why monitoring didn't catch it → Corrective actions → Preventive actions

One important interview technique

For almost every troubleshooting question, don't jump directly to the fix.

Instead say:

"First I will understand the scope and impact, then check monitoring and recent changes. After that I will isolate whether the issue is at the application, Kubernetes, infrastructure, network, database, or external dependency layer. Once I identify the root cause, I will mitigate the issue, validate recovery, and then work on RCA and preventive actions."

That answer demonstrates SRE thinking, rather than just Kubernetes command knowledge.

For TCS specifically, I would also prepare live command-based follow-ups such as "Give me the exact command you would run", because after today's telephone round, they may drill down into whether you have actually performed these activities in production.

Part 2 · Additional TCS SRE Questions

Questions 31–60

🔴 Kubernetes — Very High Priority

Q31–40
Question 31

What happens when you run kubectl apply -f deployment.yaml?

Answer

Be ready to explain the complete flow:

kubectl → API Server → Authentication/Authorization → Admission → etcd → Controller Manager → ReplicaSet → Scheduler → Kubelet → Container Runtime → Pod

This is a very common senior-level question.

Question 32

What happens when a Kubernetes pod is deleted?

Answer

Expected answer:

  • API Server receives deletion request.
  • Deployment/ReplicaSet controller detects desired state mismatch.
  • ReplicaSet creates a replacement pod.
  • Scheduler assigns a node.
  • Kubelet creates the container.
  • Readiness probe succeeds.
  • Service sends traffic to the new pod.
Question 33

Difference between liveness, readiness and startup probes?

Answer

You should be able to explain this without hesitation.

  • Liveness: Is the application alive?
  • Readiness: Can it receive traffic?
  • Startup: Has the application finished starting?

A particularly good production example:

"If my Java application takes 90 seconds to start, I would use a startup probe so the liveness probe doesn't restart the application during initialization."

Question 34

How would you troubleshoot Kubernetes DNS issues?

Answer

Commands:

kubectl get pods -n kube-system
kubectl get svc -n kube-system
kubectl logs -n kube-system <coredns-pod>

Then launch a temporary test pod:

kubectl run dns-test --rm -it \
  --image=busybox -- sh

Inside:

nslookup kubernetes.default
nslookup <service-name>

Check:

  • CoreDNS
  • kube-dns Service
  • NetworkPolicy
  • /etc/resolv.conf
  • CNI/networking
Question 35

How do you troubleshoot a Kubernetes networking problem?

Answer

Use a layered approach:

Pod → Pod → Pod → Service → Ingress → External

Check:

kubectl get pods -o wide
kubectl get svc
kubectl get endpoints
kubectl get networkpolicy

Then test connectivity with curl, wget, nc, nslookup.

You should mention CNI as well.

Question 36

What is the difference between requests and limits?

Answer

Example:

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"

Requests influence scheduling.

Limits restrict maximum resource consumption.

A strong follow-up answer:

"Incorrect requests can cause poor scheduling, while inappropriate memory limits can cause OOMKilled."

Question 37

How do you perform zero-downtime deployment in Kubernetes?

Answer

Mention:

  • RollingUpdate
  • Readiness probes
  • Multiple replicas
  • PodDisruptionBudget
  • Proper termination grace period
  • maxUnavailable
  • maxSurge

Example:

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
Question 38

How do you troubleshoot a slow Kubernetes application?

Answer

Don't say only kubectl top.

Explain:

Client → Load Balancer → Ingress → Service → Pod → Application → Database

Check latency at every layer.

Use:

kubectl top pods
kubectl top nodes
kubectl logs

Then Prometheus/Grafana and distributed tracing if available.

Question 39

How would you scale an application during a sudden traffic spike?

Answer

Possible approaches:

Immediate:

kubectl scale deployment <deployment> --replicas=10

Long-term:

HPA:

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

Also discuss:

  • CPU/memory metrics
  • Custom metrics
  • Cluster Autoscaler
  • Load balancing
  • Capacity planning
Question 40

HPA is not scaling pods. What do you check?

Answer

This is a very good real-world question.

Check:

kubectl get hpa
kubectl describe hpa <hpa>

Then:

kubectl top pods

Potential issues:

  • Metrics Server unavailable
  • Incorrect resource requests
  • Wrong target
  • CPU metrics unavailable
  • HPA configuration issue

🔴 Terraform

Q41–45
Question 41

Explain Terraform state and why it is important.

Answer

Be ready to explain:

Configuration → State → Actual Infrastructure

State tells Terraform what resources it manages and their attributes.

For production:

  • Remote backend
  • State locking
  • Encryption
  • Access control
  • Versioning
  • Backup/recovery
Question 42

What is Terraform drift?

Answer

Example:

Terraform says:

EC2 instance size = t3.medium

Someone manually changes it to:

t3.large

Terraform detects the difference during:

terraform plan

That's configuration drift.

Question 43

How do you prevent Terraform changes from being made directly in production?

Answer

Strong answer:

"I would use a CI/CD-based Terraform workflow where engineers submit changes through Git, run validation and plan automatically, perform peer review, and require approval before production apply. Production credentials should also be restricted."

Question 44

What is the difference between terraform plan and terraform apply?

Answer

Simple, but interviewers may ask it.

plan: Calculates proposed changes.

apply: Actually makes those changes.

Question 45

What happens if Terraform state is accidentally deleted?

Answer

Don't say "run terraform apply."

Explain:

  • Check remote backend.
  • Check state version history/backups.
  • Restore state if possible.
  • If unavailable, carefully reconstruct/import resources.
  • Run terraform plan.
  • Verify there is no destructive replacement before applying.

🔴 Jenkins / CI-CD

Q46–49
Question 46

Explain your Jenkins pipeline from code commit to production.

Answer

Give them a production flow:

Developer commit → GitHub → Jenkins webhook → Checkout → Build → Unit Test → SonarQube → Security Scan → Docker Build → Image Scan → Push Registry → Deploy → Kubernetes → Smoke Test → Monitoring

Then explain where approvals exist.

Question 47

How do you secure Jenkins?

Answer

Mention:

  • RBAC
  • Credentials Manager
  • Secrets
  • Agent isolation
  • Least privilege
  • HTTPS
  • Plugin updates
  • Pipeline-as-code
  • Avoid hardcoded credentials
  • Audit logs
  • Restricted network access

Never say you store passwords directly in Jenkinsfile.

Question 48

Jenkins pipeline exposes a password in console logs. What do you do?

Answer

Immediate actions:

  • Rotate the credential.
  • Stop further exposure.
  • Remove the secret from logs.
  • Check whether logs were accessed.
  • Move the secret to Jenkins Credentials Manager.
  • Mask credentials.
  • Audit the pipeline.

This is an excellent security + SRE incident question.

Question 49

Docker image builds successfully but Kubernetes cannot start it. What do you check?

Answer

Check:

  • Image exists in registry
  • Correct image tag
  • Registry authentication
  • imagePullSecrets
  • Architecture compatibility
  • Container entrypoint
  • Environment variables
  • Ports
  • Application startup

Commands:

kubectl describe pod <pod>
kubectl logs <pod>

🔴 SRE / Incident Management

Q50–55
Question 50

Explain SLA, SLO and SLI with a real example.

Answer

Use something like:

SLI:

API availability = successful requests / total requests

SLO:

99.9% monthly availability

SLA:

Customer contract guarantees 99.9% availability with defined consequences.

Then explain error budget:

For a 99.9% SLO, approximately 0.1% downtime/error budget is available over the measurement period.

Question 51

What is an error budget and how do you use it?

Answer

Strong answer:

"Error budget represents the amount of unreliability we can tolerate while still meeting the SLO. If we are consuming the budget too quickly, we reduce risky releases and prioritize reliability work. If we have sufficient budget, the team can move faster with controlled changes."

This sounds much more senior than simply defining SLO.

Question 52

What is the difference between monitoring and observability?

Answer

Monitoring: tells you something is wrong.

Observability: helps you understand why it is wrong.

Mention:

  • Metrics
  • Logs
  • Traces

And the four golden signals:

Latency, Traffic, Errors, Saturation.

Question 57

How do you decide whether to rollback or fix forward?

Answer

Good answer:

"I consider customer impact, severity, confidence in the root cause, rollback safety, data compatibility and time to recovery. If a recent deployment clearly caused a severe outage and rollback is safe, I prefer rollback because restoring service is the priority. If rollback could cause data inconsistency or the issue is infrastructure-related, I may fix forward."

Excellent senior-level answer.

Question 58

How would you troubleshoot an issue when there are no obvious errors in logs?

Answer

This is very important.

"I don't rely only on logs. I correlate metrics, traces, infrastructure metrics, Kubernetes events, deployment history and dependency health."

Check:

Metrics → Logs → Traces → Events → Recent changes → Dependencies

Sometimes the application is healthy but the database, network or external dependency is slow.

Question 59

How do you perform RCA after a production incident?

Answer

Structure:

  • 1. Incident summary
  • 2. Customer impact
  • 3. Timeline
  • 4. Detection
  • 5. Root cause
  • 6. Contributing factors
  • 7. Why existing monitoring didn't prevent/detect it
  • 8. Mitigation
  • 9. Corrective actions
  • 10. Preventive actions

And importantly:

"The RCA should be blameless and focused on system/process improvement."
