§1

Slow query detection

PostgreSQL

Top offenders by average execution time — needs the pg_stat_statements extension enabled. This is the first place to look, not individual EXPLAINs.

SELECT query, calls, mean_exec_time, total_exec_time, rows
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 15;

If the extension isn't enabled: shared_preload_libraries = 'pg_stat_statements' in postgresql.conf, then a restart — worth naming in an interview as something you'd turn on by default, not react to.

What's running right now — no extension needed, useful mid-incident.

SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
  AND now() - query_start > interval '5 minutes'
ORDER BY duration DESC;

Why a specific query is slow — compare actual vs estimated rows; a big gap means stale statistics or a missing index.

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

Red flags in the output: Seq Scan on a large table you'd expect to be indexed, a high "Rows Removed by Filter", or actual time far above the planner's estimate — that last one usually means ANALYZE mytable; hasn't run since a big data change.

MySQL

Top offenders by average latency — via performance_schema, so no log parsing or restart required.

SELECT DIGEST_TEXT,
       COUNT_STAR AS exec_count,
       AVG_TIMER_WAIT/1000000000 AS avg_ms,
       SUM_TIMER_WAIT/1000000000 AS total_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY AVG_TIMER_WAIT DESC
LIMIT 15;

What's running right now — the classic, still the fastest mid-incident check.

SHOW FULL PROCESSLIST;

-- or, filterable:
SELECT id, user, host, db, time, state, info
FROM information_schema.processlist
WHERE command != 'Sleep'
ORDER BY time DESC;

Is the slow log even on? — check before you go looking for a log file that doesn't exist.

SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
§2

Connection pool saturation

PostgreSQL

Current vs max connections — the headline number.

SELECT count(*) AS current_connections,
       (SELECT setting FROM pg_settings WHERE name='max_connections') AS max_connections
FROM pg_stat_activity;

Break it down by state — the count alone doesn't tell you why it's high.

SELECT state, count(*)
FROM pg_stat_activity
GROUP BY state
ORDER BY count(*) DESC;

idle in transaction sitting for minutes is almost never the database's fault — it's an app holding a connection open after an error path that never committed, rolled back, or released it.

Find the actual leak — longest-held idle-in-transaction sessions, with the query that started them.

SELECT pid, usename, now() - state_change AS idle_duration, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY idle_duration DESC
LIMIT 10;
MySQL

Connection usage vs limit

SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';

The early-warning signals people miss — churn and failed connects matter more than the raw count once you're past 70–80%.

SHOW STATUS LIKE 'Threads_created';   -- high & climbing = pool not reusing connections
SHOW STATUS LIKE 'Aborted_connects';  -- clients failing to even connect
SHOW STATUS LIKE 'Aborted_clients';   -- clients disconnecting uncleanly (timeout, killed)
Proxy layer — PgBouncer / app-side pools

Architecture that actually prevents this: N microservices × a pool of 20 each × M replicas explodes fast against a single Postgres max_connections. Put PgBouncer in front in transaction mode so hundreds of app-side connections share a small real pool to Postgres.

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 25

Check PgBouncer's own health via its admin console: SHOW POOLS; and SHOW STATS; — cl_waiting climbing in SHOW POOLS means clients are queueing for a backend connection right now.

The root cause, regardless of engine Almost every real pool-exhaustion incident traces back to one code path: a connection is acquired, an exception is thrown, and the release never runs because it wasn't in a finally / using / context-manager block. Fix the leak first; resizing the pool just delays the same failure at a higher load.

Dashboards to actually keep up

Scrape with postgres_exporter / mysqld_exporter into Prometheus, visualize in Grafana — same stack, same golden-signals framing you already use for services.

SignalPanelWhy it matters
SaturationConnections used / max_connectionsThe pool-exhaustion leading indicator — alert well before 100%
SaturationReplication lag (seconds)Stale reads on replicas; feeds read-your-writes bugs
SaturationBuffer/cache hit ratioDropping hit ratio means more disk I/O per query — early sign of undersized memory
SaturationDisk usage % + growth rateWAL/binlog and table bloat both show up here first
LatencyQuery duration p50 / p95 / p99p99 catches the tail that averages hide
LatencyLock wait timeThe metric most people forget — high p99 with low CPU almost always means lock contention, not slow queries
ErrorsAborted_connects / Aborted_clients (MySQL)Clients failing to connect or dropping mid-session
ErrorsDeadlocks / rollbacks per minuteSudden spike usually correlates with a specific deploy
TrafficQueries/sec, Transactions/secBaseline for "is this actually more load, or the same load handled worse"
One habit that reads senior in an interview Don't just say "I'd check CPU and memory." Say you'd correlate the lock-wait and idle-in-transaction panels against a deploy-marker annotation on the same dashboard — CPU/memory look fine in most real DB incidents, because the database usually isn't the bottleneck, contention is.
