01 Troubleshooting Toolkit & Methodology start here

0/4

The habit that matters more than any single command: work outward in layers, and always look at Events before logs.

Cluster healthy?→ Nodes healthy?→ Pod status→ Events→ Logs→ Exec/network test 
kubectl get componentstatuses 2>/dev/null; kubectl get --raw='/healthz'   # control plane alive?
kubectl get nodes -o wide                                                  # nodes Ready?
kubectl get pods -A -o wide | grep -v Running                              # what's actually broken?
kubectl describe pod <pod> -n <ns>                                        # Events section — read this BEFORE logs
kubectl logs <pod> -n <ns> --previous                                     # then logs, including the crash before this one

The single most common mistake under interview pressure (and in real incidents) is jumping straight to kubectl logs. Events from describe almost always tell you the category of problem — scheduling, image pull, probe failure, volume — before you've read a single log line. Narrate it in that order out loud; it's also just the fastest path to the actual fix.

kubectl get events -A --sort-by='.lastTimestamp' | tail -30    # cluster-wide recent events, newest last
kubectl top pod -A --sort-by=cpu                                # who's actually using resources right now
kubectl top node                                                 # node-level pressure
kubectl get pods -A -o wide --field-selector=status.phase!=Running
kubectl describe node <node> | grep -A5 Conditions               # node health at a glance
kubectl get pods -n <ns> -o jsonpath='{.items[*].status.containerStatuses[*].restartCount}'
kubectl rollout status deployment/<name> -n <ns>
kubectl get endpoints <svc> -n <ns>                              # is the Service actually backed by anything?
# Ephemeral debug container attached to an existing pod (K8s 1.23+, no restart needed)
kubectl debug -it <pod> -n <ns> --image=nicolaka/netshoot --target=<container>

# Debug a node itself (spawns a privileged pod with the node's filesystem mounted at /host)
kubectl debug node/<node> -it --image=busybox

# Standalone throwaway debug pod for network/DNS testing
kubectl run debug --image=nicolaka/netshoot --rm -it -- bash

netshoot is the one worth having memorized — it bundles dig, curl, tcpdump, nslookup, mtr, and iproute2 in one image, which covers almost every network/DNS troubleshooting need without hunting for the right tool mid-incident. kubectl debug with --target is the modern answer to "the container has no shell, distroless image" — it attaches a sidecar sharing the same process namespace instead of needing to exec into the broken container itself.

kubectl logs only works while the pod (or its immediately-previous instance) still exists — once a pod is deleted or a node is gone, those logs are gone with it, and it doesn't correlate across multiple pods/replicas at all. Centralized logging (Loki, ELK/OpenSearch, CloudWatch Logs, Azure Monitor Logs) via a node-level agent (Fluent Bit/Fluentd/Promtail as a DaemonSet) solves both: logs survive pod deletion, and you can query across every replica of a service at once by label, which is usually the actual question during an incident ("show me every 500 across all 12 replicas in the last 10 minutes") rather than one pod's logs at a time.

02 Pod & Container Issues universal

0/8

The highest-frequency category in real incidents and in interviews. Same platform-agnostic root causes whether the node is an EC2 instance, an Azure VM, or a rack in a data center.

kubectl get pod <pod> -n <ns>                  # RESTARTS count, growing?
kubectl describe pod <pod> -n <ns>             # Events: OOMKilled? probe failure? image error?
kubectl logs <pod> -n <ns> --previous           # the crash BEFORE this restart — the real clue

Root causes, most to least common: missing/wrong config or env var causing immediate exit; an overly aggressive livenessProbe killing a slow-starting app before it's ready; OOMKilled — confirm via Last State: Terminated, Reason: OOMKilled in describe, then compare memory limits to actual usage; a downstream dependency (DB, API) unreachable at startup causing the app to fail its own startup checks and exit.

Trap: a fresh restart may show empty current logs — always check --previous before concluding "no logs, no clue."
  • Wrong tag or typo — the most common cause by far; kubectl describe pod Events show the exact image string being pulled.
  • Private registry with no imagePullSecret attached to the pod/ServiceAccount, or an expired one — registry tokens (ECR tokens especially) expire and need refreshing if not handled by an IRSA-integrated credential helper.
  • Network path issue reaching the registry — from a private subnet/air-gapped node, missing NAT/VPC endpoint/proxy config.
  • Rate limiting from the upstream registry (Docker Hub's anonymous pull limits are a classic surprise cause in busy clusters).

kubectl describe pod Events state the scheduler's exact reason:

  • "Insufficient cpu/memory" — no node has room; needs autoscaling to add capacity, or the request is oversized for the fleet.
  • Unbound PVC — see Chapter 5 for the full storage diagnostic path.
  • Taints without a matching toleration, or nodeSelector/affinity matching no node's labels.
  • Too many pods per node — hit the node's pod-count ceiling (this is IP-address-driven on EKS with the VPC CNI — see Chapter 9).
kubectl describe pod <pod> -n <ns> | grep -A3 "Last State"
kubectl top pod <pod> -n <ns> --containers

The kernel's OOM killer fires when the container exceeds its memory limit — this is a hard cgroup boundary, not a soft warning. Two distinct scenarios: (1) the limit is genuinely too low for legitimate usage — check actual usage trend via Prometheus/kubectl top over time and raise the limit or fix the memory leak; (2) a real leak — usage climbs steadily over hours/days rather than settling at a plateau, which points at application code, not sizing. Compare requests vs limits vs actual usage as three separate numbers — conflating them is the most common analysis mistake here.

Init containers run sequentially, to completion, before any app container starts — if one fails or hangs, the whole pod never progresses past it, and the app container's logs won't even exist yet.

kubectl logs <pod> -n <ns> -c <init-container-name>      # -c is required, default logs won't show init containers
kubectl describe pod <pod> -n <ns>                          # which init container, and why

Common causes: an init container waiting on a dependency (DB migration, config fetch) that never becomes available; a permissions/mount issue specific to the init step; or the init container's own image pull failing silently while the pod just sits in PodInitializing.

The pod's been scheduled (unlike Pending) but something in the sandbox setup is stalling: a volume that won't mount (check the Events for mount timeout errors — usually a storage/CSI issue, Chapter 5), a CNI plugin failing to assign a pod IP (check the node's CNI/kubelet logs — journalctl -u kubelet), or a slow/stuck image pull that hasn't yet flipped to an explicit ImagePullBackOff state. kubectl describe pod Events almost always name which of the three it is.

Almost always one of: a finalizer that never completes (something is supposed to clean up external state — a cloud LB, a volume detach — before the pod is allowed to fully delete, and that cleanup is stuck or the controller that should remove the finalizer is down), or the node itself is unreachable so the kubelet can never confirm the container actually stopped.

kubectl get pod <pod> -n <ns> -o jsonpath='{.metadata.finalizers}'
kubectl delete pod <pod> -n <ns> --grace-period=0 --force   # last resort, not a real fix
Trap: --force only removes the API object — it does not guarantee the container process on the node actually stopped. Understand and fix why the finalizer/node is stuck rather than reaching for force-delete as step one; it can leave orphaned resources (volumes, LB target registrations) behind.

The kubelet's eviction manager removed the pod because the node was under resource pressure (disk, memory, or PID) — this is different from OOMKilled, which is the container hitting its own limit. kubectl describe pod shows the eviction reason directly (e.g. "The node was low on resource: ephemeral-storage").

Common on-prem/self-managed cause: logs or temp files filling a node's local disk with no rotation policy — the kubelet starts evicting pods well before the disk is literally full, based on configurable eviction thresholds. Fix at the node level (log rotation, ephemeral-storage limits on pods) rather than just deleting the evicted pod, or it recurs.

03 Node Issues universal

0/5

Node-level problems cascade — one bad node can look like ten different pod problems until you check the node itself.

kubectl get nodes                     # confirm NotReady + how long
kubectl describe node <node>          # Conditions: MemoryPressure / DiskPressure / PIDPressure / NetworkUnavailable
# on the node itself (SSH / SSM / on-prem console):
systemctl status kubelet
journalctl -u kubelet -f
systemctl status containerd           # or crio / docker
df -h                                  # disk pressure?
ip addr; ping <control-plane-endpoint> # node-to-control-plane connectivity

The control plane marks a node NotReady after missing heartbeats for node-monitor-grace-period (default 40s), then starts evicting its pods after pod-eviction-timeout (default 5 min) if it stays unreachable — worth naming explicitly, since it's exactly why "one node down" doesn't mean instant pod loss on a healthy cluster.

These are kubelet-reported conditions, distinct from a pod hitting its own limit — the node as a whole is running low on a resource, and the kubelet starts proactively evicting lower-priority pods to relieve it before things get worse. DiskPressure is the most common in practice, usually from unrotated container logs, orphaned image layers, or a filled ephemeral-storage volume. docker/crictl system df or du -sh /var/lib/containerd/* on the node quickly narrows down what's actually consuming the disk.

journalctl -u kubelet --no-pager | tail -50
cat /var/lib/kubelet/config.yaml           # config errors are a common cause
crictl info                                 # can kubelet even reach the container runtime socket?

Frequent causes: a bad kubelet.conf/config.yaml edit, a mismatched or expired client certificate for talking to the API server (very common on-prem after cert rotation is missed — Chapter 11), or the container runtime socket (containerd/CRI-O) being unreachable — kubelet depends entirely on that runtime being healthy first.

Check, in order: is the container runtime actually running post-boot (systemctl status containerd, often not enabled on boot after a manual install); did the node's IP change (common on DHCP-configured on-prem nodes) causing a mismatch with what the control plane has cached; are the kubelet's client certificates still valid; and — for EKS/AKS managed node groups specifically — did the node's IAM role/managed identity attach correctly on boot. A node stuck NotReady post-reboot is disproportionately likely to be a bootstrap-ordering problem (something starting before its dependency is ready) rather than anything wrong with the workloads.

kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
# ... perform maintenance ...
kubectl uncordon <node>

--ignore-daemonsets is mandatory or drain hangs indefinitely — DaemonSet pods aren't meant to be evicted this way. If drain still hangs, it's almost always a PodDisruptionBudget whose minAvailable can't be satisfied while removing pods from this node, or a bare pod with no owning controller, which drain refuses to touch without an explicit --force.

04 Networking & DNS Issues universal

0/7

Networking failures are rarely where the symptom appears — a "database timeout" is very often a DNS or NetworkPolicy problem wearing a different costume.

kubectl get endpoints <service> -n <ns>      # empty? → selector problem, most common cause
kubectl get pods --show-labels -n <ns>        # compare labels against the Service's selector exactly
kubectl describe svc <service> -n <ns>        # confirm targetPort matches the container's actual listening port

The number-one cause is a label mismatch — the Service selector doesn't match the pod's labels (often introduced by a template change), leaving Endpoints silently empty. Second most common: targetPort pointing at the wrong container port, or the app listening on a different interface (127.0.0.1 instead of 0.0.0.0) than the pod IP the Service actually forwards to.

kubectl run debug --image=busybox:1.36 --rm -it -- sh
# inside: nslookup my-service.my-namespace.svc.cluster.local

kubectl get pods -n kube-system -l k8s-app=kube-dns    # CoreDNS pods Running?
kubectl logs -n kube-system -l k8s-app=kube-dns         # errors, SERVFAIL, throttling?
kubectl get svc -n my-namespace my-service               # does the Service exist / right name/namespace?
cat /etc/resolv.conf                                       # inside the pod — nameserver pointing at kube-dns ClusterIP?

Common root causes, roughly by frequency: wrong namespace in the query (forgetting the FQDN across namespaces), CoreDNS under resource pressure or CrashLooping, a NetworkPolicy silently blocking egress to port 53, or (self-managed clusters specifically) CoreDNS's upstream resolver misconfigured for external DNS lookups.

kubectl logs -n kube-system -l k8s-app=kube-dns — the most common cause is a DNS forwarding loop: CoreDNS's Corefile forwards to the node's /etc/resolv.conf, and if that node resolver points back at CoreDNS itself (common misconfiguration on self-managed nodes, or after a systemd-resolved change), CoreDNS detects the loop and refuses to start, logging exactly that. Fix by correcting the Corefile's forward target to a real upstream resolver rather than the node's own stub resolver. Second cause: OOMKilled from an undersized memory limit under high query volume — CoreDNS should scale with cluster size, not stay pinned at default replica count forever.

NetworkPolicy is only as real as the CNI enforcing it — the object can be perfectly correct and still do nothing if the CNI doesn't implement policy enforcement at all (this is genuinely platform-dependent; see Chapter 12 for the exact breakdown across EKS/AKS/on-prem). Confirm the policy engine's own pods are actually running (kubectl get pods -n kube-system for Calico/Azure NPM/Cilium) before assuming the policy YAML itself is wrong. Second cause: selector scope — a policy only starts enforcing deny-by-default for pods it actually selects; a pod not matched by any policy remains fully open regardless of other policies existing in the namespace.

  • 502 Bad Gateway: the backend closed the connection or returned something the proxy couldn't parse — check the backend pod's own logs, not just the ingress controller's.
  • 503 Service Unavailable: the ingress controller has no healthy backend to route to at all — check kubectl get endpoints for that Service (empty again points back to Chapter 4, Q1).
  • 504 Gateway Timeout: the backend is reachable but too slow to respond within the proxy's timeout — an application performance problem, not a routing problem; check readiness probe timing and backend latency, not the ingress config.

Always check the ingress controller's own logs (nginx-ingress-controller pod, or the ALB/AGIC's target group/backend health in the cloud console) alongside the app's — the error surfaces at the ingress layer but the cause is usually one layer behind it.

First confirm it's actually a policy problem and not a naming one — cross-namespace calls need the fully-qualified DNS name (svc.namespace.svc.cluster.local), not the short form. If FQDN also fails, check for a default-deny NetworkPolicy in namespace B that only allows ingress from pods with specific namespace labels — a very common "secure by default" setup that quietly blocks legitimate cross-namespace traffic until an explicit allow rule references the calling namespace's label.

kubectl get pods -n B --show-labels
kubectl get networkpolicy -n B -o yaml   # look for namespaceSelector rules that exclude namespace A

Layered check, cloud-agnostic order: (1) egress NetworkPolicy blocking outbound traffic by default; (2) node-level egress path — on EKS/AKS this means NAT Gateway/NAT rules on private subnets (Chapter 9/10), on-prem this means the node's own default route and any perimeter firewall; (3) DNS resolution for the external hostname specifically (internal DNS may work fine while external forwarding is broken — see Q3); (4) proxy requirements — some locked-down environments require an explicit HTTP(S) proxy env var in the pod spec for any external call.

05 Storage Issues universal

0/5

Storage failures are where "universal" starts to bend — the concepts (PVC, PV, StorageClass) are identical everywhere, but the provisioner underneath is completely platform-specific.

kubectl describe pvc <name> -n <ns>             # Events give the exact reason
kubectl get storageclass                          # does the referenced class actually exist?
kubectl get pods -n kube-system | grep csi         # is the CSI provisioner running at all?
  • No StorageClass exists / wrong name referenced — trivially checked, surprisingly common typo source.
  • No dynamic provisioner running — the CSI driver pods themselves are down or never installed. This is the single most common on-prem gotcha: unlike EKS/AKS, a bare cluster has no default StorageClass at all until you install one (Rook-Ceph, Longhorn, NFS provisioner) — a PVC just sits Pending forever with no error beyond "no persistent volumes available."
  • AZ/zone mismatch — the provisioner created a volume in a zone with no schedulable node for the pod (very common with topology-aware provisioning across all three platforms).

Almost always an ownership/UID mismatch between the container's running user and the volume's filesystem ownership. Fix with securityContext.fsGroup on the pod spec, which tells the kubelet to chown the volume to that group on mount (works for most CSI drivers, though behavior and speed vary — very large volumes can make this recursive chown noticeably slow on first mount).

securityContext:
  fsGroup: 2000
  runAsUser: 1000

Block storage (EBS, Azure Disk, most on-prem block volumes) is typically ReadWriteOnce — attachable to exactly one node at a time. This fires most often when a pod is rescheduled to a different node (a deploy, a node drain, a crash) before the old node has finished detaching the volume — the new pod tries to attach while the old attachment hasn't cleared yet. Usually self-resolves within a minute or two once the CSI driver completes the detach; if it hangs longer, check the CSI controller pod's logs for a stuck detach operation, and confirm the old pod is actually fully terminated, not stuck (Chapter 2, Q7).

CSI drivers run as a DaemonSet (node plugin) plus a controller Deployment — check both separately, since they fail differently. Node-plugin crashes are usually a permissions issue talking to the underlying storage API (IAM/Managed Identity/on-prem storage credentials); controller crashes usually mean it can't reach the cloud API or on-prem storage backend at all. "No volume plugin matched" typically means the driver was never installed/registered, or the StorageClass references a provisioner string that doesn't match any installed CSI driver's name exactly.

A PV with persistentVolumeReclaimPolicy: Retain deliberately survives its PVC's deletion — that's not a bug, it's the policy protecting data from accidental loss, and it needs manual cleanup (or manual rebinding to a new PVC) once you've confirmed the data isn't needed. If it's set to Delete and still stuck, the underlying CSI delete-volume call is failing — check the CSI controller logs; a stale reference to already-deleted cloud storage is a common cause after manual out-of-band cleanup on the cloud side.

06 Scheduling Issues universal

0/5

The scheduler is honest about why it won't place a pod — the Events almost always say exactly what's wrong, if you read them before guessing.

kubectl describe node <node> | grep Taints
kubectl get pod <pod> -o jsonpath='{.spec.tolerations}'

A taint on a node repels pods unless they carry a matching toleration — commonly used to dedicate nodes (GPU pools, high-memory pools) to specific workloads. If the pod isn't landing there, the toleration is missing, or its effect (NoSchedule/PreferNoSchedule/NoExecute) doesn't match the taint's effect exactly — these are matched precisely, not loosely.

Check whether podAntiAffinity is set to requiredDuringScheduling (hard constraint — pods will stay Pending rather than co-locate) versus preferredDuringScheduling (soft — the scheduler will co-locate them anyway if it has to). A common real incident: switching from preferred to required without enough nodes/zones to satisfy it, which silently turns "nice to have spread" into "half my replicas are stuck Pending." topologySpreadConstraints is generally the more modern, more precise tool for even distribution across zones than anti-affinity rules.

Confirm the autoscaler (Cluster Autoscaler/Karpenter on EKS, the AKS autoscaler, or whatever's configured on-prem — often nothing, since bare metal has no elastic capacity to add at all) is actually running and not maxed at its own max node-count ceiling. A frequent false alarm: the pending pod's resource request is larger than any available instance type in the autoscaler's configured node pools — no amount of scaling adds a node that big, and the pod will stay Pending forever until the request is reduced or a larger instance type is added to the pool.

kubectl get pdb -n <ns>
kubectl describe pdb <name> -n <ns>   # ALLOWED DISRUPTIONS column — 0 means fully blocked right now

Usually one of: the PDB's minAvailable is set at (or above) the current replica count, so any voluntary disruption is mathematically impossible to satisfy; or replicas are already degraded for an unrelated reason (a few already CrashLooping) so the PDB is correctly refusing to remove any more and drop below its floor. Fix the underlying pod health first — don't just loosen or delete the PDB to force it through, that defeats the exact protection it exists for.

PriorityClass lets higher-priority pending pods preempt (evict) lower-priority running pods to make room, when the cluster is otherwise full. Check kubectl get priorityclass and each pod's assigned class — this is by design once configured, but a very common surprise when a new high-priority workload is introduced onto a cluster that's already near capacity, and existing "normal" workloads start getting bumped without an obvious deploy or config change on their own side to explain it.

07 Control Plane & Cluster-Wide Issues universal

0/6

Managed platforms (EKS/AKS) hide most of this from you — until something slips through. On-prem, this entire chapter is squarely your responsibility.

kubectl cluster-info
curl -k https://<api-server-endpoint>:6443/healthz
kubectl config view --minify   # confirm you're pointed at the right context/cluster at all

Split the diagnosis by layer: is this a local problem (wrong kubeconfig context, expired client cert/token, VPN not connected for a private cluster) or a cluster problem (API server actually down)? Ninety percent of "the cluster is down" reports from a laptop are actually the first kind — check kubectl config current-context before assuming the worst.

On EKS/AKS this chapter effectively doesn't exist — etcd is fully managed and invisible. On self-managed/on-prem clusters it's the single most critical, least forgiving component (full detail in Chapter 11) — the short version: etcd needs a majority of members alive to keep serving writes ((n/2)+1, so a 3-node cluster tolerates exactly 1 failure), and it's extremely sensitive to disk write latency, not just capacity — slow disks cause leader elections and API timeouts long before anything looks "full."

x509: certificate has expired or is not yet valid is the exact error text to recognize immediately. On managed platforms this is essentially never the control plane's own cert (AWS/Azure handle that) — it's almost always a stale local kubeconfig token/cert on your machine. On self-managed/kubeadm clusters, this is a very real and very common incident: control plane certs expire after 1 year by default and don't auto-renew (Chapter 11 has the exact recovery commands) — treat this as a scheduled maintenance item, not something to discover during an outage.

kubectl auth can-i get pods -n <ns> --as=<user-or-sa>
kubectl get rolebinding,clusterrolebinding -A -o wide | grep <user-or-sa>

kubectl auth can-i --as is the fast path — it tells you definitively whether the permission exists before you go hunting through Role/RoleBinding YAML by hand. Common causes: the binding references the wrong namespace (a RoleBinding in namespace A doesn't grant anything in namespace B, even referencing the same ClusterRole), a typo in the subject name, or the ServiceAccount the pod actually runs as isn't the one that was granted access (defaulting to the namespace's default SA instead of the intended one).

A Mutating or ValidatingWebhookConfiguration (OPA Gatekeeper, Kyverno, a custom webhook, cert-manager's own injector) is unreachable or timing out, and — depending on its failurePolicy — is blocking every single API write cluster-wide, not just the one that seemingly triggered it. This is a genuinely scary cluster-wide symptom with a narrow cause: check kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations and confirm the webhook's backing pod/Service is actually healthy. A webhook with failurePolicy: Fail that goes down can take the whole cluster's write path down with it — failurePolicy: Ignore on non-critical policy webhooks is a deliberate, common mitigation for exactly this blast radius.

First suspect: a removed/deprecated API version that a manifest, Helm chart, or third-party controller still uses — this is by far the most common post-upgrade break, and it's exactly why checking the K8s deprecation guide and running a scanner (Pluto/kube-no-trouble) before upgrading is standard practice, not optional. Second suspect: a version-pinned add-on (CNI, CSI driver, ingress controller) that's incompatible with the new control-plane version and needs its own coordinated bump.

08 Deployment & Rollout Issues universal

0/4

A stuck rollout is a scheduling problem, a probe problem, or a PDB problem wearing a deployment-shaped costume — the fix usually lives in an earlier chapter.

kubectl rollout status deployment/<name> -n <ns>
kubectl get rs -n <ns> -l app=<name>              # which ReplicaSet is trying to scale up, and to what
kubectl describe pod <new-pod> -n <ns>             # apply Chapter 2's pod diagnostic flow here

A "stuck rollout" is rarely its own root cause — it's almost always one of Chapter 2's pod problems (image pull, scheduling, crash loop) blocking the new ReplicaSet from ever reaching Ready, combined with maxUnavailable/maxSurge settings that won't let old pods scale down until new ones are healthy. Diagnose the new pod directly rather than staring at the Deployment object.

kubectl rollout history deployment/<name> -n <ns>
kubectl rollout undo deployment/<name> -n <ns>                    # back one revision
kubectl rollout undo deployment/<name> -n <ns> --to-revision=4     # back to a specific one

If the deployment is GitOps-managed (ArgoCD/Flux), a raw kubectl rollout undo works as an immediate mitigation but will be silently reverted on the next sync — always follow up with a git revert in the source repo, or the fix disappears the moment reconciliation runs again.

Check for a readiness gate — an extra condition beyond the standard readiness probe that must also become true before the pod counts as fully Ready for rollout purposes. This is exactly how the AWS Load Balancer Controller confirms a pod is actually registered and healthy in the target group (not just passing its own liveness/readiness probe) before letting the rollout proceed to the next pod — a very common EKS-specific stuck-rollout cause that looks identical to a normal probe issue until you check kubectl get pod -o yaml for the readinessGates and conditions sections specifically.

kubectl describe hpa <name> -n <ns>   # Events + current/target metrics
kubectl top pod -n <ns>                # is metrics-server even reporting numbers?

"Unknown" current-value metrics almost always means metrics-server isn't installed, isn't healthy, or the pods being measured don't have resource requests set — HPA's percentage-based CPU target is calculated against the request, so a pod with no CPU request has nothing to calculate a percentage of. Confirm kubectl top pod returns real numbers before debugging the HPA object itself.

09 EKS-Specific Troubleshooting AWS

0/7

Everything here is a layer on top of Chapters 1–8, not a replacement for them — an EKS problem is a Kubernetes problem plus one extra AWS-shaped thing to check.

kubectl get sa <name> -n <ns> -o yaml | grep role-arn        # annotation present and correct?
kubectl describe pod <pod> -n <ns> | grep AWS_                # AWS_ROLE_ARN / AWS_WEB_IDENTITY_TOKEN_FILE injected?
aws sts get-caller-identity                                     # run FROM inside the pod — who does AWS actually think this is?
  • The pod isn't actually using the annotated ServiceAccount (defaulted to default instead of the intended one) — the single most common cause.
  • The IAM role's trust policy condition doesn't exactly match the SA's namespace/name (the sub claim is namespace- and name-specific, not just cluster-wide).
  • The OIDC provider isn't associated with the cluster at all, or its thumbprint is stale after a cluster recreation.
  • The pod identity webhook itself isn't running — check kubectl get pods -n kube-system | grep pod-identity-webhook; if it's down, no pod gets the env vars/token volume injected regardless of how correct everything else is.

The node has run out of ENI-attached secondary IPs to hand out to pods — a hard ceiling driven by instance type (each EC2 type supports a fixed max ENIs × IPs per ENI), not by CPU/memory capacity, which is why this can happen on a node with plenty of spare compute. Fix: enable prefix delegation (ENABLE_PREFIX_DELEGATION=true on the VPC CNI) to allocate /28 IP prefixes instead of individual IPs, dramatically raising pod density per node — or move to larger instance types, or size subnets with real headroom from the start.

kubectl describe node <node> | grep -A5 Allocatable
aws ec2 describe-network-interfaces --filters Name=attachment.instance-id,Values=<id>

aws-node is the VPC CNI's own pod — when it's unhealthy, new pods on that node can't get IPs at all (pods stuck in ContainerCreating, Chapter 2 Q6). Check its logs directly: usually an IAM permissions gap on the node role (missing AmazonEKS_CNI_Policy, or the CNI policy was moved to IRSA on the aws-node SA and that's misconfigured), or an add-on version incompatible with the current cluster's Kubernetes version after an upgrade.

The classic EKS gotcha: the node's IAM role isn't mapped in the aws-auth ConfigMap (or the newer EKS access entries), so it can boot, run kubelet, and still never be allowed to register with the API server. Second cause: security group rules blocking node-to-control-plane traffic on the required ports (443 and the kubelet ports). Newer clusters using EKS access entries instead of aws-auth remove this specific trap, but plenty of clusters still run the ConfigMap-based approach.

kubectl get configmap aws-auth -n kube-system -o yaml
aws eks list-access-entries --cluster-name <cluster>   # if using the newer access-entry model
  • Subnets missing the required tags (kubernetes.io/role/elb=1 public, kubernetes.io/role/internal-elb=1 private, plus kubernetes.io/cluster/<name>=shared) — the controller can't auto-discover subnets to place the ALB in without these.
  • The controller's own IRSA role missing a required IAM permission — check its pod logs for the exact denied action, they're usually explicit.
  • Missing or wrong ingressClassName/annotation, so the controller never picks up the Ingress object as one it should manage.
kubectl logs -n kube-system deployment/aws-load-balancer-controller

EBS volumes are zonal — if the pod got rescheduled to a node in a different AZ than the volume actually lives in, it will never attach, full stop, no amount of waiting fixes it. Confirm with aws ec2 describe-volumes against the node's AZ. This is exactly what topology-aware provisioning (volumeBindingMode: WaitForFirstConsumer on the StorageClass) is meant to prevent by delaying volume creation until a node is actually chosen — if it's still happening, check that setting is actually in place on the StorageClass being used.

No Fargate profile matches the pod's namespace/labels — Fargate scheduling is entirely profile-driven; without a matching profile, the pod just sits Pending with no node to land on at all (there's no fallback to EC2 nodes automatically). Also worth knowing for interview purposes: Fargate has no DaemonSet support, so any cluster-wide agent pattern (log shippers, node-level monitoring) needs a different approach — typically sidecar containers per-pod instead of a node-level DaemonSet, since there's no persistent node to run one on.

10 AKS-Specific Troubleshooting Azure

0/7

Same principle as EKS — Chapters 1–8 first, then check what's Azure-shaped on top.

The Azure equivalent of IRSA — and it fails for almost identical reasons: the pod's ServiceAccount isn't labeled/annotated for workload identity, the federated credential on the Managed Identity doesn't exactly match the SA's namespace/name/issuer, or the workload identity webhook itself isn't running so the token volume never gets projected into the pod. Check kubectl describe pod for the projected service account token volume, and confirm the federated credential's subject claim matches system:serviceaccount:<namespace>:<sa-name> exactly.

Under (full) Azure CNI, every pod consumes a real IP from the VNet subnet — an under-sized subnet planned for node count alone, without accounting for pod density, runs out fast as the cluster scales. Azure CNI Overlay (or Kubenet) avoids this by keeping pods on a separate private CIDR, decoupled from the VNet subnet size — but remember from the earlier prep round: this choice is locked in at cluster creation and can't be changed after the fact, so a subnet-exhaustion problem on full Azure CNI generally can't be fixed by reconfiguring the existing cluster — it means planning a new node pool or cluster with more headroom.

AGIC needs its own identity with specific RBAC roles on both the Application Gateway resource and the subnet it lives in — a permissions gap there means the Ingress objects exist in Kubernetes but nothing ever appears on the Gateway side. Check the AGIC pod's own logs first (kubectl logs -n kube-system -l app=ingress-appgw); it's generally explicit about permission errors. Separately, if rules exist but return errors, check the Application Gateway's backend health probe status directly in the Azure portal — a probe path/port mismatch there looks identical to an AGIC misconfiguration from the Kubernetes side.

Same zonal constraint as EKS/EBS (Chapter 9, Q6) — Azure Disk is zone-bound, and a pod scheduled outside the disk's zone will never attach. Confirm volumeBindingMode: WaitForFirstConsumer is set on the StorageClass so provisioning waits for scheduling instead of racing it. Azure Files (rather than Azure Disk) is the better default choice specifically when ReadWriteMany is actually needed — Disk fundamentally can't do multi-node read-write, and reaching for it there is a design mistake, not a bug to troubleshoot.

Check the node pool's max surge setting first — a low surge value means very few nodes upgrade in parallel, which is slow by design for safety, not actually stuck. If it's genuinely stuck rather than slow: a PodDisruptionBudget blocking eviction from the node being replaced (Chapter 6, Q4), or a subscription-level vCPU quota limit preventing the surge node from provisioning at all — the latter fails silently from Kubernetes' point of view and only shows up as an Azure-side quota error in the node pool's operation history.

A private cluster has no public API server endpoint by design — access requires being on the VNet (via VPN/ExpressRoute) or through a jumpbox inside it; this is expected behavior, not a fault. If you are connected and it still fails, check private DNS zone resolution for the cluster's private FQDN specifically — a private-endpoint DNS record that isn't correctly linked to the VNet is a very common setup gap, and it presents as a generic connection timeout that looks identical to a plain network problem.

AAD-integrated (non-admin) AKS clusters require the kubelogin plugin to handle the AAD device-code/interactive auth flow — a kubeconfig generated without it, or run on a machine that doesn't have the binary installed, fails with an exec-plugin-not-found style error rather than a normal auth error. This is a very common day-one confusion point distinct from any real cluster health problem: az aks get-credentials followed by confirming kubelogin is on the PATH resolves it in the overwhelming majority of cases.

11 On-Premise / Self-Managed Cluster Troubleshooting bare metal / kubeadm

0/8

Nothing here is managed for you — every problem EKS/AKS hides is now squarely your responsibility. This is also the chapter that most reliably separates "used a managed cluster" from "actually run Kubernetes."

ETCDCTL_API=3 etcdctl endpoint health --cluster \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
ETCDCTL_API=3 etcdctl endpoint status --cluster -w table

etcd needs a strict majority of members alive to keep accepting writes — (n/2)+1. A 3-member cluster tolerates exactly one failure; a 5-member cluster tolerates two. Lose quorum and the entire API server goes read-only-at-best, effectively down for any change. Recovery is either bringing enough members back online, or — worst case — restoring from a snapshot backup onto a fresh single-member cluster and re-adding members from there. This is precisely why etcd backups (etcdctl snapshot save) on a schedule are not optional for a self-managed control plane.

The detail most people miss: etcd is extremely sensitive to disk write latency, not capacity — a disk with high fsync latency causes leader elections and API timeouts under load long before you'd see any "disk full" symptom. Slow storage under etcd looks like a flaky cluster, not a storage problem, until you specifically check etcd's own latency metrics.
  • Token expired — join tokens default to a 24-hour TTL; generate a fresh one with kubeadm token create --print-join-command rather than reusing an old one from documentation/scripts.
  • discovery-token-ca-cert-hash mismatch — usually a stale hash copy-pasted from an old join command after the cluster's CA changed.
  • Control-plane join specifically also needs a --certificate-key, which has its own much shorter default TTL (2 hours) — re-upload with kubeadm init phase upload-certs --upload-certs if it's expired.
  • Connectivity — port 6443 (API server) and 10250 (kubelet) blocked by a firewall between the new node and the control plane is a very common last-mile cause after everything else checks out.
kubeadm certs check-expiration     # run this proactively, on a schedule — don't wait for the outage
kubeadm certs renew all
systemctl restart kubelet          # on each control-plane node, after renewal

This is the single most well-known on-prem "silent time bomb": kubeadm-generated control plane certificates expire 1 year after cluster creation (or after the last renewal) by default, and there's no automatic rotation out of the box. A cluster that's been stable and untouched for a year can go down all at once, cluster-wide, with no warning beyond what a proactive check-expiration cron job would have caught. Naming this specific gotcha unprompted is one of the strongest signals of genuine on-prem experience versus managed-platform-only experience — it simply doesn't exist as a concern on EKS/AKS.

On-prem HA for multiple API servers typically means HAProxy load-balancing across control-plane nodes, fronted by a floating virtual IP managed via keepalived (VRRP) — there's no cloud load balancer to do this automatically. If the VIP doesn't move to a healthy node when one fails: check keepalived's own logs for VRRP election issues (often a network config problem — multicast/broadcast blocked between nodes, or a priority misconfiguration), and separately confirm HAProxy's backend health checks are actually correctly detecting the failed API server (a health check hitting the wrong port/path will keep routing to a dead backend indefinitely).

Calico (BGP-based): calicoctl node status shows BGP peering state directly — a peer stuck "down" or "start" means routes aren't being exchanged between those nodes, and pods on them can't reach each other. Check the underlying network allows BGP (TCP 179) between nodes.

Flannel (VXLAN overlay): the classic on-prem gotcha is an MTU mismatch — VXLAN encapsulation adds overhead (typically 50 bytes), so if the physical network's MTU isn't accounted for, large packets get silently dropped rather than cleanly failing. This shows up as maddening intermittent connectivity — small requests work fine, larger payloads mysteriously hang or time out — which makes it one of the more painful on-prem networking issues to pin down without knowing to check MTU specifically as a first-class suspect.

There's no cloud controller manager on-prem to satisfy a LoadBalancer-type Service by default — without MetalLB (or an equivalent) installed, the external IP simply never gets assigned, indefinitely, with no error. Once MetalLB is installed: in Layer2 mode, check that its speaker pods are running and that the requested IP pool isn't already exhausted or conflicting with another device on the network (ARP conflicts are a real, painful failure mode here); in BGP mode, check peering status the same way as Calico BGP above — a route not being advertised looks identical to "nothing happened."

Rook-Ceph: ceph status (via the toolbox pod) is the starting point — an OSD down usually means a disk failure or a node outage; a MON quorum loss is the etcd-equivalent problem for Ceph's own metadata layer and just as serious. Longhorn: check replica health in its UI/CRDs directly — a volume with all replicas on nodes currently under DiskPressure (Chapter 3, Q2) will degrade even though nothing about Longhorn itself is misconfigured; the root cause is one layer down at the node level.

No path to the public internet means every image — including base images referenced deep inside third-party Helm charts — has to be mirrored into an internal registry (Harbor/Nexus/JFrog) in advance, and every manifest has to actually reference that internal registry rather than the public one. The most common failure mode isn't the registry itself being broken — it's an overlooked image reference (an init container, a sidecar injected by a mutating webhook, an operator's own controller image) that nobody remembered to mirror, which surfaces as a completely ordinary-looking ImagePullBackOff (Chapter 2, Q2) that's easy to misdiagnose as a typo instead of a missing mirror entry.

13 Interview Scenario Questions — Exact Phrasing how they'll actually ask it

0/23

Chapters 1–12 are organized like a reference — by symptom or error message. This chapter is organized the way an interviewer actually talks: as a scenario, in one or two sentences, waiting to see your diagnostic order. Every answer here leans on the deeper detail already in earlier chapters rather than repeating it — cross-references point back to the exact card if you want the full depth on any one step.

Deployment & Rollout Scenarios

First question back to yourself, out loud if it helps frame the answer: all pods of this one app, or all pods cluster-wide? That single distinction sends the investigation in completely different directions, and stating it up front is itself a good signal to the interviewer.

Scope: one app or cluster-wide?→ describe pod → Events→ logs --previous→ What changed in the deploy?→ Rollback if correlated

If it's scoped to the one app that was just deployed (the far more common version of this question), kubectl describe pod on a crashing replica almost always names the category immediately — then match it to what actually changed in this deploy:

  • Bad image — broken build, wrong tag, a missing binary/dependency baked into the new image.
  • Bad config/env var — a required setting missing or wrong, very often because a ConfigMap/Secret wasn't updated in lockstep with app code that now expects a new key.
  • Probe misconfiguration — the app's health-check path or port changed in this release but the livenessProbe/readinessProbe config wasn't updated to match, so a perfectly healthy new pod fails its probe and gets killed immediately (Chapter 2, Q1) — this one especially is very easy to mistake for "the code is broken" when it's actually just a probe pointing at the wrong place.
  • Undersized resources for the new version — a heavier startup routine in the new release now exceeds the existing memory limit → OOMKilled (Chapter 2, Q4).
  • A missing migration — new code expects a DB schema change that hasn't actually been applied yet, so every replica crashes on its first query.

If it's genuinely cluster-wide (unrelated apps crashing too, not just the one just deployed), this stops being a "deployment" question and becomes Chapter 7 territory — an admission webhook blocking cluster-wide (Ch. 7, Q5), a DNS/CoreDNS outage taking down anything with a startup dependency lookup, or an expired credential (IRSA/Managed Identity/Vault token) that many pods share and all lose at once.

Either way, say this part explicitly: mitigate first, root-cause in parallel — kubectl rollout undo (or a GitOps revert) to restore service, while continuing to dig into the actual cause. Restoring availability always outranks fully understanding it in the moment.

This is a stuck rollout, and the inconsistent behavior is simply both versions genuinely serving traffic at once — that part is expected during any rolling update, not itself the bug. The actual question is why it's stuck rather than completing: apply the Chapter 8, Q1 flow directly — kubectl rollout status, then kubectl describe pod on one of the new pods specifically. It's almost always one of Chapter 2's pod problems (image pull, crash loop, failing readiness) preventing the new ReplicaSet from ever reaching enough Ready replicas to let the old ones scale down.

Same diagnostic entry point as any pod problem — kubectl describe pod on one of the new replicas — but two causes are specifically common with a fresh scale-up rather than a normal deploy: insufficient cluster capacity for the extra replicas (Chapter 3, Q3/Chapter 6, Q3 — the new pods are actually stuck Pending, not failing readiness at all, and it's worth confirming which one it is before assuming a readiness problem), and a shared dependency hitting its own limit under the new load — a database connection pool sized for the old replica count, now exhausted by the extra connections, causing the new pods to fail their own readiness checks against that dependency.

  • It was never actually an app-code problem — a bad ConfigMap/Secret, a downstream dependency outage, or a data issue (a bad row, a corrupted cache entry) persists across a code rollback because rolling back the Deployment doesn't touch any of those.
  • GitOps reverted it right back — if the environment is ArgoCD/Flux-managed, a manual kubectl rollout undo is only temporary; the next reconciliation re-applies whatever Git still says, silently undoing your fix within minutes (Chapter 8, Q2). Always pair a manual rollback with an actual Git revert in GitOps-managed environments.
  • Client-side or CDN caching serving the old (broken) response regardless of what the backend now returns — worth explicitly ruling out before concluding the rollback itself failed.

Almost always one of: the image tag didn't actually change (a mutable tag like :latest reused, or a CI step that built successfully but pushed the old tag by mistake) so Kubernetes correctly sees no diff and does nothing — kubectl get pod -o jsonpath='{.spec.containers[0].image}' confirms exactly what's actually running versus what you think you deployed. Second cause: the manifest change applied to the wrong namespace/cluster context entirely — a very easy mistake with multiple environments and worth ruling out with kubectl config current-context before assuming anything about the app itself.

Cluster-Wide & Node Scenarios

Multiple nodes failing together is a strong signal to stop thinking "node problem" and start thinking "shared dependency problem" — the individual node checks from Chapter 3 still apply, but the more efficient starting point is whatever those nodes have in common: the same AZ/rack (an infra-provider outage or a physical network segment down), the same underlying host if they're VMs sharing a hypervisor, or a control-plane-side issue (an overloaded API server failing health checks cluster-wide, more a Chapter 7 problem than a node problem at all). Check one node's kubelet logs, but check the cloud provider's status page and the control plane's own health in parallel rather than sequentially — on a multi-node failure, serial single-node debugging wastes time you don't have.

API server latency→ etcd health→ Node resource pressure→ DNS/CoreDNS latency→ One noisy workload?

"Slow cluster" almost always traces to one of a small number of shared choke points, checked roughly in this order: API server response latency itself (kubectl get --raw='/healthz' timing, or just noticing every kubectl command feels sluggish); etcd health if self-managed (Chapter 11, Q1 — etcd latency degrades the entire control plane, not just one API); widespread node resource pressure rather than one bad node; CoreDNS under load, since DNS latency quietly compounds into every service call that depends on it; and finally, one specific noisy-neighbor workload starving shared node resources for everything else on that node. Start at the control plane and work outward to individual workloads, not the other way around — starting with individual pods on a cluster-wide slowness report usually wastes the most time.

kubectl top nodes --sort-by=cpu
kubectl top pods -A --sort-by=cpu | head -15

Immediately establish whether this is legitimate traffic growth (check request-rate dashboards alongside CPU — if both climbed together, this is a scaling conversation, not an incident) or one runaway workload dragging the average up (the sorted top pods output usually makes an outlier obvious at a glance). Those two are entirely different responses — traffic growth needs HPA/Cluster Autoscaler tuning, a runaway pod needs profiling and a scale-out mitigation — and conflating them wastes the first, most valuable minutes of the page.

journalctl -b -1 (logs from the previous boot, i.e. right up to the moment it went down) is the single most useful command here — check the very last entries before the gap for an OOM-killer log line from the kernel itself (the node's own memory exhausted, distinct from a single pod's OOMKill), a hardware/kernel panic message, or — on cloud platforms — a Spot/Preemptible reclaim notice (this is expected, not a fault, if the node pool intentionally uses Spot capacity). On-prem specifically, also check for a hardware watchdog reset or a scheduled patching job that wasn't communicated. A well-designed workload (multiple replicas, PodDisruptionBudgets, anti-affinity) survives this kind of event without an actual outage — which is often the more important half of the answer than the root cause of the reboot itself.

Networking & Connectivity Scenarios

"Intermittent" is the key word — it points at a subset of backends being unhealthy rather than the whole service being down, so go straight to backend health rather than the ingress config itself (Chapter 4, Q5 has the full 502/503/504 breakdown). Check the ingress controller's/ALB's target group health for individual unhealthy targets among an otherwise-healthy pool; if only some replicas are bad, check whether they correlate with a specific node (node-level issue) or came up around the same time (a bad subset from a rolling deploy that hasn't fully finished, Scenario isq-2 above). Genuinely random-looking intermittency across all replicas more often points at a shared downstream dependency (DB, cache) occasionally timing out under load, propagating up as an occasional 502 rather than a clean, consistent failure.

"Nobody deployed anything" doesn't mean nothing changed — widen the search past application deploys specifically: a certificate expired overnight (Chapter 7, Q3 — especially worth checking first on self-managed clusters, and also for any TLS cert on an Ingress/service mesh with a short rotation window); a credential/token expired (an IAM role's temporary credentials, a database password rotated by policy); a scheduled/automated change that isn't a "deploy" in the usual sense — a cluster autoscaler scale-down over a quiet night removing a node a pod depended on, a scheduled cron job that mutated shared config, or a cloud-provider-side change (a security group edited by someone else, a DNS record TTL expiring and re-resolving somewhere new). kubectl get events -A --sort-by='.lastTimestamp' and the cloud provider's own audit log (CloudTrail/Azure Activity Log) both cover far more "what changed" ground than checking recent app deploys alone.

This is the classic NetworkPolicy footgun, and it's worth naming the mechanism directly: a NetworkPolicy's podSelector can be broader than intended — a label meant to scope the policy to "just this app" can accidentally also match pods belonging to something else entirely, pulling them into a deny-by-default posture they were never meant to be in. Confirm with kubectl get networkpolicy -o yaml and cross-check the selector against every pod's labels cluster-wide, not just the intended target — kubectl get pods -A --show-labels | grep <the-label-you-used> is the fast way to see everything actually caught by it. This is also the strongest practical argument for narrow, explicit label schemes (e.g. app.kubernetes.io/name: exact-app-name) over broad, reused labels like a generic tier: backend that many unrelated services might share.

Rather than debugging production in isolation, diff the two environments directly — that's usually faster than fresh root-causing:

  • NetworkPolicy — does production have a stricter default-deny policy staging doesn't (very common — staging is often deliberately looser)?
  • Security Groups/NSGs/firewall rules — production DB tiers are frequently locked down harder than staging's.
  • DNS — is the app resolving the correct production endpoint at all, or accidentally still pointed at a staging-style hostname via a copy-pasted config?
  • Credentials/IAM — does the production ServiceAccount/IRSA role actually have the grant that staging's has, or was it never mirrored over?
  • Same subnet/AZ reachability — production infra is more likely to be split across multiple AZs/subnets with tighter routing than a simpler staging setup.

A debug pod (Chapter 1, Q3) run in production, attempting the exact same connection the app makes, isolates whether it's a networking/policy problem or an application-config problem in under a minute.

"Internal looks fine" is the tell — the problem lives specifically on the external path, which internal health checks never traverse: DNS resolution of the public hostname from outside your network (it can resolve fine internally via a different, internal-only record); a WAF rule or IP allowlist that changed and is now blocking legitimate partner traffic; a TLS certificate valid for the wrong hostname, or expired specifically on the public-facing listener while an internal one uses a different cert; or the external load balancer/ALB itself being misconfigured while internal ClusterIP traffic bypasses it entirely and looks completely healthy. Test from genuinely outside the network (not a debug pod inside the cluster) to actually reproduce what partners are seeing.

Config, Secrets & Access Scenarios

A ConfigMap update alone doesn't restart anything — if the app reads the value only at startup (an env var sourced from the ConfigMap, most common pattern), the running pods simply never re-read it; they need a rollout restart (kubectl rollout restart deployment/<name>) to actually pick up the change. The exception: a ConfigMap mounted as a volume does get live-updated on disk inside the pod (with a short kubelet sync delay, typically under a minute) — but the app still has to actually watch the file and reload it; most applications don't do this by default, so even a volume-mounted ConfigMap often still needs an explicit reload mechanism or a restart to take effect in practice.

Same root cause as the ConfigMap scenario above — env-var-sourced Secrets need a restart to pick up a rotation, so "rotated the Secret" and "pods are actually using the new value" are two different events unless something explicitly bridges them. For real production rotation, that bridge is normally either an automated rollout restart triggered as part of the rotation pipeline, or (the more robust answer, worth naming) an External Secrets Operator / Vault Agent sidecar pattern that actively re-injects and can trigger a reload without a full manual restart. If pods restarted and are still failing post-rotation, check for a propagation lag on the secret-store side itself (the new value hasn't actually finished replicating in Vault/Secrets Manager yet) before assuming the pod-side plumbing is broken.

"Nothing changed on their end" points the search at everything around them instead: an RBAC change (Chapter 7, Q4 — kubectl auth can-i --as confirms in seconds whether a permission was quietly revoked or a role binding changed), an admission policy update (Chapter 3's OPA/Kyverno content — a new cluster-wide policy can start rejecting previously-valid manifests with no code change involved at all), a CI/CD platform-side credential expiring (a service account token, a registry push credential), or — worth checking early since it's fast to rule out — whether this is actually affecting everyone or just this one developer, which immediately separates "something changed platform-wide" from "something specific to their access."

Resource & Capacity Scenarios

"Spare capacity" on a dashboard is usually a raw CPU/memory number — it doesn't account for several other real scheduling constraints that a pod can be blocked by even with plenty of headroom: taints without a matching toleration (Chapter 6, Q1), pod affinity/anti-affinity rules that are technically satisfiable but not on the specific nodes that have the spare capacity (Chapter 6, Q2), the max-pods-per-node ceiling being hit on otherwise-idle nodes (very much an EKS VPC-CNI IP-exhaustion pattern, Chapter 9 Q2 — a node can show 10% CPU used and still be completely full from a pod-count/IP perspective), or a PriorityClass situation where the pending pod's priority isn't high enough to preempt anything and the "spare" capacity is actually already reserved by pods with pending resource claims. kubectl describe pod Events name the specific one directly — always the fastest path here rather than guessing from the dashboard number alone.

Three realistic explanations, and the investigation differs for each: (1) traffic/data volume genuinely grew — check request-rate and payload-size trends over the same window; this is a capacity conversation, the fix is raising the limit or scaling out, not a bug. (2) a real memory leak — check the memory usage trend specifically: a leak shows steady, continuous growth within each pod's own lifetime that resets only on restart, versus usage that plateaus normally; Prometheus's per-pod memory graph over several days makes this visually obvious. (3) an unrelated recent deploy changed behavior even without deliberately touching memory settings — a new dependency version, a changed caching strategy, a new code path that holds more in memory than before. Correlate the exact timestamp OOMKills started against both deploy history and any traffic-pattern change before concluding which of the three it is — treating a genuine leak as a capacity problem (just raising the limit) delays the pod's inevitable crash rather than fixing anything.

Storage Scenarios

StatefulSets tie a pod identity to a specific PVC, and block storage is typically zone-bound — if the failed node's replacement (or the rescheduled pod) lands in a different AZ/zone than the existing volume, it can never attach, and the pod hangs indefinitely rather than failing loudly (Chapter 9 Q6 / Chapter 10 Q4 have the exact EKS/AKS versions of this). Confirm with kubectl describe pod for a stuck-attaching event, and check the volume's actual zone against the node it's now trying to schedule onto. Second cause specific to StatefulSets: ordered rolling recovery — a StatefulSet won't bring pod N+1 back until pod N is healthy again, so what looks like "the whole thing is stuck" can actually be one specific ordinal blocking everything behind it in the sequence.

Check I/O performance characteristics first, not just "does it mount" — a StorageClass migration (e.g. moving to a cheaper/slower tier) can silently degrade IOPS/latency enough that the database's own health checks or startup timeouts start failing under real load, even though the volume mounts and looks completely fine at rest. Compare the new class's guaranteed IOPS/throughput against the old one directly rather than assuming "storage" as a category is interchangeable. Second common cause specific to a class migration: a permissions/fsGroup mismatch on the new provisioner (Chapter 5, Q2) that the old one handled differently, causing the DB process to fail on file access rather than on mount itself.

GitOps & CI/CD Scenarios

"Synced" only means the live state matches whatever the manifest in Git currently says — it says nothing about whether that manifest itself points at the version you intended. The most common cause: the GitOps repo's image tag was never actually bumped by CI in the first place (a broken or skipped step in the tag-update automation), so ArgoCD is correctly, faithfully synced to a manifest that was simply never updated — this isn't an ArgoCD problem at all, it's upstream of it. Second cause: someone (or an automated process) committed directly to the GitOps repo bypassing the intended CI pipeline, and Auto Sync/Self Heal faithfully applied that unintended change. Always check the actual Git commit history of the manifest file itself, not just ArgoCD's UI, before assuming the deployment tooling is at fault.

A "successful" pipeline run just means every stage exited 0 — it doesn't guarantee the apply step targeted the right place. Check, in order: did the apply step actually run against the intended cluster/namespace/context (a misconfigured kubeconfig or context in the pipeline is a very common silent-no-op cause); did the manifest genuinely change at all, or did the pipeline rebuild and "redeploy" an identical spec that Kubernetes correctly recognized needed no changes (Scenario isq-5 above, same underlying pattern); and — for GitOps setups specifically — did CI only update the app repo without the separate step that pushes the new tag into the GitOps repo ArgoCD actually watches, meaning the "deploy" never reached the thing that would have applied it at all.
