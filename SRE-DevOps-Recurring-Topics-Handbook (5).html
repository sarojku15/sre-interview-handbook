AWS & Cloud Infrastructure

The baseline assumption in almost every round: can you actually run production on this, not just name the services.
Q1Walk me through how you'd design a highly available production architecture on AWS.
In one lineMulti-AZ everything, stateless compute behind a load balancer, a managed data layer with automated failover — nothing single-homed.
  • Route 53 with health checks in front, so DNS itself can route traffic away from a broken target.
  • ALB across two or more AZs in front of EC2/EKS nodes in an Auto Scaling Group, also spread across AZs.
  • RDS Multi-AZ (synchronous standby) plus read replicas for read-heavy paths.
  • S3 for static assets and backups — eleven nines durability by default, cross-region replication for DR.
  • IAM roles, not long-lived keys, scoped per service — least privilege from the start.
  • CloudWatch alarms and dashboards feeding the on-call rotation.
  • The whole stack defined in Terraform, so it's reproducible in a second region on demand.
Q2EC2 vs. EKS — how do you decide which to reach for?
In one lineEC2 when you own the whole stack and the workload is simple or stateful; EKS once you have several services that each need independent scaling, rolling deploys, and self-healing.
  • EC2 alone means you build your own orchestration — fine for a small number of long-running, stable services.
  • EKS earns its operational overhead once you have multiple independently-deployable services, need rolling or canary deploys, or want the scheduler handling bin-packing and self-healing for you.
  • Team maturity matters as much as the workload — EKS assumes the team already thinks in containers, manifests, and GitOps.
  • The EKS control plane cost is small and fixed; the real cost is the operational learning curve, not the bill.
Q3An ALB is throwing intermittent 502s and 504s in production — how do you troubleshoot?
In one line502 means the target refused or reset the connection — usually app-side. 504 means the target was too slow to respond — a timeout. Split the two before digging further.
  • Check target group health — are targets flapping between healthy and unhealthy around the same time as the errors?
  • TargetResponseTime in CloudWatch — a slow creep points at backend saturation, not a one-off blip.
  • App logs at the exact error timestamp — a restart, crash, or OOM right then?
  • Idle timeout mismatch: ALB defaults to 60s. If the app's own keep-alive is shorter, the app closes a connection the ALB still thinks is open — a classic 504 cause.
  • Deregistration delay during deploys — in-flight requests can land on a target that's already terminating.
  • Confirm the app drains in-flight requests on SIGTERM instead of dropping connections outright.
Q4How do you keep IAM least-privilege at scale without becoming the bottleneck every team waits on?
In one lineRole-based access per workload, hard guardrails at the org level, and let teams self-serve inside those guardrails instead of hand-writing every policy.
  • IAM roles per workload — IRSA for EKS pods, instance profiles for EC2 — never shared long-lived user keys.
  • Permission boundaries so a team can create their own roles without exceeding a ceiling you've already set.
  • AWS Organizations SCPs for hard limits that apply account-wide, regardless of what any individual IAM policy allows.
  • Policy-as-code reviewed in CI — Terraform plan output, an IAM linter — instead of console-clicked changes.
  • Scheduled access reviews to catch unused permissions before they become a finding.
Q5How do you approach AWS cost optimization?
In one lineRight-size before you commit to anything, commit once usage is stable, and make waste visible so it doesn't quietly come back.
  • Right-size compute from actual CloudWatch utilization, not the instance size someone picked two years ago.
  • Spot for stateless, interruption-tolerant workloads; Savings Plans / Reserved Instances for the steady baseline once the number is trusted.
  • S3 lifecycle policies moving cold data to IA/Glacier automatically.
  • Tagging discipline so cost is attributable to a team or service — you can't optimize what you can't attribute.
  • Budget alerts so a runaway resource gets caught in days, not at month-end.
Q6Beyond the strategy — walk through a hands-on cost audit. What would you actually go find and fix?
In one lineMost real savings hide in things nobody's actively using or a data-transfer path nobody priced out — not in the instances everyone's already watching.
  • Orphaned resources — unattached EBS volumes, EBS snapshots past their real retention need, unused Elastic IPs (billed while unattached), forgotten load balancers with no real traffic.
  • AWS Compute Optimizer / Trusted Advisor flag over-provisioned instances straight from utilization history — a faster starting point than eyeballing CloudWatch manually.
  • Graviton (ARM) instances for workloads that support them — meaningfully cheaper for the same performance, often close to a drop-in change for containerized workloads.
  • NAT Gateway is a classic hidden cost trap — per-hour plus per-GB processed. A VPC endpoint for S3/DynamoDB traffic keeps that traffic off NAT entirely; cross-AZ data transfer between services is another cost that rarely gets priced out until the bill arrives.
  • Old-generation instance families still running because nobody revisited them since the project started — usually a strict downgrade to move to current-generation, same or better performance for less.
Q7How would you implement autoscaling for an EC2-based workload?
In one lineAn Auto Scaling Group with a target-tracking policy on the metric that actually reflects load, built from a launch template so every new instance comes up identical.
  • Launch Template defines the AMI, instance type, and user-data bootstrap — every scaled instance is identical, no drift between a manually-launched box and one the ASG created.
  • Target tracking (e.g., hold average CPU at 50%) is the default choice — the ASG does the math, you just set the target.
  • Step scaling for workloads that need a more aggressive response than target-tracking's smoothing gives — e.g., scale out fast on a queue-depth spike.
  • Scheduled scaling for predictable patterns — a known daily or weekly traffic shape scales ahead of demand instead of reacting after a threshold is already crossed.
  • Health checks (EC2 + ELB) so the ASG replaces an unhealthy instance automatically, not just scales on load.
  • Cooldown period stops the ASG from thrashing — scaling out and immediately back in before the last change has even taken effect.

Terraform & IaC

Comes up as both a concept check and a build-it-live exercise — know the reasoning behind the structure, not just the syntax.
Q1How do you structure Terraform so it scales across dev, stage, and prod without copy-pasted resource blocks?
In one lineReusable modules plus one thin root config per environment — the only difference between environments is which variables get passed in.
  • modules/ holds generic, versioned building blocks (eks-cluster, vpc); envs/dev, envs/stage, envs/prod each just call those modules with different tfvars.
  • Remote state isolated per environment — a mistake in dev's state can't touch prod's.
  • Workspaces are fine for lightweight, ephemeral cases, but for prod-grade separation a dedicated root and state per environment gives a smaller, more deliberate blast radius than one state file split by workspace.
  • Prod applies gated behind CI approval; dev can apply on merge.
Q2How do you manage Terraform state safely across a team?
In one lineRemote backend with locking, never local state, never a manual edit.
  • S3 backend + DynamoDB lock table — two people running apply at once fails safely instead of corrupting state.
  • State encrypted at rest, access restricted — state can hold sensitive values in plaintext.
  • CI-gated applies with terraform plan as a required PR check, so every change is reviewed before it touches anything.
  • A scheduled drift-detection job comparing live infra back to state.
  • terraform state surgery only as a deliberate last resort, with a second person watching.
Q3count vs. for_each — when do you reach for which?
In one linefor_each when items have a stable identity; count when you just need N identical copies.
  • count indexes by position — removing item #2 of 5 can force-replace #3, #4, and #5 in state. Dangerous for anything stateful.
  • for_each keys by a stable string (a map or set), so removing one item only touches that one resource.
  • Default to for_each for anything you might resize or reorder later — which, in practice, is almost everything.
Q4How do you handle secrets in Terraform?
In one lineNever hardcode, never commit — pull from a secrets manager at apply time and mark the variable sensitive.
  • sensitive = true on a variable or output masks it in plan and apply logs — but state itself still stores the real value, so the backend must be encrypted too.
  • Pull actual values from AWS Secrets Manager, SSM Parameter Store, or Vault via a data source rather than a tfvars file.
  • Any tfvars file that does get committed stays free of real secrets — placeholders only.

Q6terraform apply hangs or fails with "Error acquiring the state lock" — what do you do?
In one lineSomeone or something else holds the lock — find out who and why before you ever force-unlock.
  • Check the DynamoDB lock table item directly — it names who holds the lock and since when.
  • Confirm no other plan/apply is genuinely mid-flight (another CI run, a teammate) before touching anything — force-unlocking a real, active operation can corrupt state.
  • A stale lock from a crashed or killed CI job is the common innocent cause.
  • terraform force-unlock <LOCK_ID> once you're confident it's safe — this is a deliberate last resort, not a first move.
  • Always run terraform plan immediately after unlocking to confirm state wasn't left partially applied.
Q7terraform plan shows changes you didn't make — how do you debug drift?
In one lineConfirm it's real drift — infra changed outside Terraform — before assuming Terraform itself is wrong.
  • terraform plan -refresh-only shows exactly what changed in real infra vs. state, without risking an accidental apply of unrelated config changes.
  • On AWS, CloudTrail shows who or what made the out-of-band change — a console click, an ASG action, or another pipeline entirely.
  • If the drift is legitimate and should be kept: terraform apply -refresh-only reconciles state to match reality without re-applying config.
  • If the drift was a mistake: a normal apply reverts real infra back to what's declared.
  • Rule out a provider version bump first — a new provider version changing its own defaults produces a diff that looks like drift but isn't; always check the diff against a pinned provider version before chasing a phantom cause.
Q8How would you use Terraform to drive cloud cost optimization, not just provisioning?
In one lineMake the optimization repeatable by encoding it in Terraform, rather than a one-time manual fix that quietly drifts back within a quarter.
  • Start with visibility, not random cuts — identify underutilized compute, oversized databases, idle environments, and unattached storage before touching anything.
  • Encode the right-sized configuration in Terraform so the improvement is version-controlled and repeatable, not a console click nobody remembers next quarter.
  • Enforce tagging and cost-center metadata at the module level, so spend is attributable to a team from day one instead of retrofitted later.
  • Non-production environments are the easiest win — a scheduled scale-down, still Terraform-managed, for the hours nobody's actually using them.
  • Always validate against SLOs and peak-load requirements before merging — a cost PR that quietly removes headroom is a reliability regression wearing a cost-savings label.
Q9Hands-on: write a reusable Terraform module for a baseline-secure S3 bucket, and explain how module reuse like this actually streamlines operations.
In one lineOne well-designed module means every team gets encryption, versioning, and public-access-blocking by default, instead of every team's bucket being a slightly different security review.
modules/secure-bucket/main.tf 
resource "aws_s3_bucket" "this" {
  bucket = var.bucket_name
  tags   = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = var.enable_versioning ? "Enabled" : "Suspended"
  }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "this" {
  bucket = aws_s3_bucket.this.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "aws:kms"
    }
    bucket_key_enabled = true
  }
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket                  = aws_s3_bucket.this.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_lifecycle_configuration" "this" {
  bucket = aws_s3_bucket.this.id
  rule {
    id     = "transition-to-ia"
    status = "Enabled"
    transition {
      days          = var.ia_transition_days
      storage_class = "STANDARD_IA"
    }
  }
}
modules/secure-bucket/variables.tf 
variable "bucket_name" {
  type = string
}

variable "enable_versioning" {
  type    = bool
  default = true
}

variable "ia_transition_days" {
  type    = number
  default = 90
}

variable "tags" {
  type    = map(string)
  default = {}
}
  • Every consumer of this module gets encryption, versioning, and public-access-blocking by default — a team can't accidentally ship a public bucket, because the module never exposes an option to turn that protection off.
  • Streamlining shows up in two places: new environments spin up faster because nobody's hand-writing bucket security config from scratch, and security review gets faster too — auditing "did they use the standard module" is a much smaller job than auditing bespoke S3 config in every repo.
  • Versioning and lifecycle transition are exposed as variables, not everything — the things that should never vary (encryption, public-access-block) are hardcoded into the module; the things that legitimately differ by use case are the only knobs left.

Kubernetes — Architecture & Troubleshooting

The heaviest-weighted topic across your recent rounds — architecture questions test understanding, troubleshooting questions test scar tissue.
Q1Walk me through the Kubernetes control plane — what does each component actually do?
In one lineAPI server is the front door, etcd is the source of truth, the scheduler places pods, the controller-manager reconciles desired vs. actual state — and on each node, kubelet, kube-proxy, and the container runtime do the real work.
  • kube-apiserver — validates and serves the REST API; every other component, including kubectl, talks through it.
  • etcd — the cluster's single consistent source of truth. Back it up, guard access to it.
  • kube-scheduler — watches for unscheduled pods and binds them to a node based on resource requests, affinity/anti-affinity, and taints/tolerations.
  • kube-controller-manager — runs the reconciliation loops (node, replication, endpoints, and more) that continuously drive actual state toward desired state.
  • kubelet — the node agent; makes sure containers described in a PodSpec are actually running and healthy.
  • kube-proxy — implements the Service abstraction via iptables/IPVS rules on each node.
  • Container runtime (containerd/CRI-O) — actually runs the containers.
Q2A pod is stuck in Pending — walk through your debugging.
In one linePending almost always means the scheduler can't place it — start with kubectl describe pod and read the Events.
  • kubectl describe pod → the Events section names the reason: insufficient CPU/memory across every node, an unsatisfied nodeSelector/affinity rule, or no node tolerating its taints.
  • kubectl top nodes / describe nodes to confirm actual remaining capacity, not assumed capacity.
  • A PVC that isn't bound — no matching StorageClass or the underlying volume can't provision — also parks a pod in Pending.
  • Check ResourceQuota / LimitRange on the namespace — a quota ceiling can block scheduling even when the cluster has room.
Q3A pod is in CrashLoopBackOff — how do you approach it?
In one lineRead the exit code and the previous container's logs before touching anything.
  • kubectl logs <pod> --previous — the crashed instance's logs, not the fresh restart's near-empty ones.
  • kubectl describe pod → Last State / Exit Code / Reason: 137 (128+SIGKILL) is almost always OOMKilled; 1 is a plain app error; 143 (128+SIGTERM) usually means something else killed it first.
  • If OOMKilled, compare resources.limits.memory against what the app actually uses under load.
  • A too-aggressive liveness probe (short initialDelaySeconds or timeout) can kill a slow-starting app before it's ready — this looks identical to a real crash from the outside. Add a startupProbe to buy slow-starting apps room.
  • A bad config map or secret mount causing startup failure is the other common non-obvious cause.
Q4How does service discovery and load balancing actually work inside the cluster?
In one lineCoreDNS gives every Service a stable DNS name; kube-proxy programs iptables/IPVS rules on every node so traffic to the Service's virtual IP load-balances across healthy pod IPs.
  • ClusterIP — internal only. NodePort — exposes a port on every node. LoadBalancer — provisions a cloud LB. Ingress — L7 routing in front of one or more Services.
  • EndpointSlices track which pods are actually ready — a failing readinessProbe pulls a pod out of rotation without killing it, distinct from liveness.
  • kube-proxy watches the API server and rewrites local iptables/IPVS rules whenever Endpoints change — there's no central load balancer inside the cluster, every node does this independently.
Q5A worker node goes NotReady in production — what do you do?
In one lineConfirm it's real, let normal pod eviction do its job, then dig into the node itself.
  • kubectl describe node → the node's Conditions name the actual reason: kubelet stopped reporting, disk pressure, network unreachable.
  • After the default 5-minute toleration on the NotReady/Unreachable taint, pods reschedule automatically if capacity exists elsewhere — verify a PodDisruptionBudget isn't blocking that.
  • SSH/SSM onto the node for kubelet and container-runtime logs, and to check disk/memory pressure directly.
  • Cordon and drain deliberately if pulling the node for maintenance, rather than waiting on auto-eviction.
  • For cloud ASG-backed node groups, it's often faster to let the ASG terminate and replace the node than to hand-debug it in place.
Q6How does pod networking actually work in EKS specifically — how do pods get real VPC IPs?
In one lineThe AWS VPC CNI attaches ENIs to each node and hands its secondary IPs directly to pods — pod IPs are real, routable VPC addresses, not an overlay network.
  • Unlike self-managed clusters that often run an overlay network (Flannel, Calico in overlay mode), EKS's default CNI attaches actual Elastic Network Interfaces to each worker node.
  • Each ENI carries a pool of secondary private IPs; the aws-node DaemonSet (the VPC CNI) hands one of those IPs directly to each pod as it schedules.
  • Because the pod IP is a real VPC IP, other VPC resources can reach it without NAT, and security groups can apply to it directly.
  • Trade-off: pod density per node is capped by how many ENIs and secondary IPs that instance type supports — not by CPU or memory. A small instance can run out of pod-networking room before it runs out of compute.
Q7You're seeing pods stuck in ContainerCreating or "no available IP addresses" on EKS — what's going on?
In one lineYou've hit the ENI/secondary-IP ceiling for that instance type — either the CNI hasn't warmed enough spare IPs, or the node is genuinely out of room.
  • kubectl describe pod → look for FailedCreatePodSandBox referencing IP allocation.
  • Check the aws-node DaemonSet logs on the affected node — the VPC CNI logs exactly why it couldn't assign an IP.
  • Confirm the subnet itself still has free IPs — a fully allocated subnet blocks new ENI/IP attachment even when the node has other room.
  • Tune WARM_IP_TARGET / WARM_ENI_TARGET if the CNI simply isn't pre-warming enough spare IPs for bursty scheduling.
  • Longer-term fix: enable prefix delegation (ENABLE_PREFIX_DELEGATION=true) — it assigns /28 IP prefixes instead of individual IPs per ENI slot, multiplying usable pod-IP capacity per node without a bigger instance.
  • If genuinely out of room: move to a larger instance type (more ENIs/IPs) or add nodes.
Q8How do you actually expose an EKS workload to the internet — walk through an ALB Ingress.
In one lineThe AWS Load Balancer Controller watches Ingress objects and provisions a real ALB for you — the Ingress spec is the only thing you touch.
  • The AWS Load Balancer Controller runs as pods in-cluster and needs IAM permissions via IRSA (see the next question).
  • An Ingress resource with the right annotations (alb.ingress.kubernetes.io/scheme: internet-facing, target-type ip or instance) is all a developer writes — the controller reconciles it into an actual ALB, listener, target group, and rules.
  • Target-type ip registers pod IPs directly with the ALB — a natural fit with the VPC CNI, since pod IPs are already real VPC IPs. Target-type instance routes through the NodePort instead, an extra hop.
  • TLS terminates at the ALB via an ACM certificate referenced in the annotations — the app itself never handles certs.
  • Health-check annotations and the pod's own readiness probe need to agree, or you'll see flapping ALB targets that look like an app problem but aren't.
Q9How do pods get AWS permissions securely — say, a pod that needs to read from S3?
In one lineIRSA — IAM Roles for Service Accounts — maps a Kubernetes ServiceAccount to a scoped IAM role via the cluster's OIDC provider, so the pod gets exactly the permissions it needs and nothing more.
  • The EKS cluster exposes an OIDC identity provider; a ServiceAccount annotated with an IAM role ARN lets any pod using that ServiceAccount assume the role via short-lived, auto-rotated tokens — no static credentials anywhere.
  • This replaces the older, much broader pattern of granting the whole node's instance role S3 access — under IRSA, a pod on the same node without that ServiceAccount gets nothing.
  • Least privilege moves from the node level to the pod level, which matters once multiple teams' workloads share the same node pool.
  • Newer clusters can use EKS Pod Identity instead of IRSA — same goal, simpler setup — worth mentioning if asked which you'd reach for today.
Q10Walk through the different layers of autoscaling in Kubernetes — HPA, VPA, and Cluster Autoscaler/Karpenter. How do they work together?
In one lineThree independent layers, each scaling a different thing: HPA changes pod count from live metrics, VPA changes each pod's resource requests, and Cluster Autoscaler/Karpenter changes node count when pods can't be scheduled.
  • HPA (Horizontal Pod Autoscaler) — watches a metric (CPU/memory by default, or a custom/external metric via the metrics adapter) against a target, and changes replica count on a Deployment or StatefulSet. Reactive, fast — the one most people mean by "autoscaling."
  • VPA (Vertical Pod Autoscaler) — watches actual usage over time and recommends, or auto-applies, better CPU/memory requests per container, instead of the guessed-at values everyone starts with. Right-sizing, not scaling out.
  • Cluster Autoscaler / Karpenter — watches for pods stuck Pending due to insufficient node capacity, adds nodes, and removes underutilized ones. This is the layer that actually changes the AWS bill.
  • They compose in sequence: HPA decides more pods are needed → if existing nodes have no room, those pods go Pending → Cluster Autoscaler/Karpenter notices and adds a node → the pods schedule.
  • Don't run HPA and VPA on the exact same resource dimension for the exact same container — they'll fight each other over the same number.
  • Karpenter over classic Cluster Autoscaler — it provisions right-sized nodes per pending pod's actual requirements instead of picking from a fixed, pre-defined node group shape. Usually faster and tighter-packed, which is also a direct cost lever.
Q11How do you approach cost optimization specifically for a Kubernetes cluster, beyond the general cloud tactics?
In one lineMost Kubernetes cost waste is requests set far above real usage — fix that first, then let bin-packing and Spot do the rest.
  • Requests, not limits, drive the bill — the scheduler reserves node capacity based on requests, so an over-requested pod wastes capacity even if it never actually uses it. VPA's recommendation mode, even without auto-apply, is the fastest way to find the gap between requested and actual.
  • Karpenter (or a well-tuned Cluster Autoscaler) for bin-packing — consolidating workloads onto fewer, better-fitted nodes instead of running a fixed set of node groups sized for peak.
  • Spot for interruption-tolerant workloads, at 60–90% off on-demand — needs graceful handling of the 2-minute interruption notice (drain and reschedule, not just die).
  • Namespace ResourceQuotas so one team's misconfigured request doesn't silently reserve capacity meant for everyone else.
  • Scale-to-zero for genuinely idle workloads (dev/staging namespaces overnight) — Cluster Autoscaler or KEDA can take a node group or workload to zero when nothing's actually running.
  • Cost visibility — Kubecost/OpenCost, or cost-allocation tags per namespace/label — same principle as the general cloud answer: you can't optimize what you can't attribute to a team.
Q12Difference between readiness, liveness, and startup probes — and when would misconfiguring one actually hurt you in production?
In one lineReadiness decides if a pod gets traffic, liveness decides if it gets restarted, and startup protects a slow-starting app from being killed before it's even up.
  • Readiness probe — controls whether the pod is in the Service's endpoint list. A failure pulls it from traffic without killing it; the pod stays up and can recover on its own.
  • Liveness probe — controls whether Kubernetes restarts the container. Repeated failures mean a restart, even if the process is technically still running but stuck — deadlocked, wedged.
  • Startup probe — holds off liveness checks until the app reports it's actually initialized. Without one, an aggressive liveness probe can kill a slow-starting app before it ever gets the chance to become healthy.
  • Production example: a Java service with a 2-minute startup time and a 30-second liveness timeout will crash-loop forever without a startup probe — it looks exactly like CrashLoopBackOff, but the real bug is probe configuration, not the app.
  • The two failure modes look very different in practice: a misconfigured readiness probe causes silent traffic loss to a struggling pod; a misconfigured liveness probe causes an unnecessary restart storm.
Q13An AKS/EKS application suddenly starts returning 503 — walk the full troubleshooting path, not just "check the pods."
In one lineFollow the actual request path — client → DNS/LB → ingress → service → endpoints → pod → app → dependency — because "pods are running" only answers one hop out of eight.
  • Establish the exact start time first, and whether it's every user, one endpoint, or one region — that scopes the search before touching anything.
  • Correlate that timestamp against Grafana metrics, recent deployments, and Splunk logs in parallel with the live investigation, not after.
  • At the Kubernetes layer: pod status is necessary but not sufficient — running doesn't mean ready. Check that the Service's selector actually matches the pod labels, and that the Endpoints object is actually populated with healthy pod IPs.
  • If pods and endpoints check out, move outward: ingress rules, TLS, and load-balancer target health — a bad ingress rule or an LB health-check misconfiguration produces the exact same symptom as a broken pod.
  • If everything upstream is clean, the app itself may not be listening on the expected port, or a downstream dependency (DB, cache, another service) is timing out and the app is surfacing that as a 503.
  • Once the cause is identified, stabilize first — rollback, scale, or restore the dependency — and run RCA after the customer is unblocked, not before.
Q14HPA isn't scaling even though load has clearly increased. What do you check?
In one lineConfirm the metrics pipeline is actually delivering data to the HPA before assuming the policy or the app is wrong.
  • kubectl describe hpa — shows current vs. target metric value, and any error events; "unable to get metrics" is very often the whole story.
  • Confirm metrics-server (or the custom/external metrics adapter, for anything beyond CPU/memory) is actually running and healthy — HPA is only as good as the metric feeding it.
  • Check that the target Deployment's pods actually declare resource requests — HPA's CPU/memory percentage math is relative to the request value; no request means no percentage to scale on.
  • Confirm the HPA is pointed at the correct scaleTargetRef — a typo'd Deployment name means the HPA is quietly evaluating against nothing.
  • Check minReplicas/maxReplicas and the scaling stabilization window — a maxed-out ceiling or an overly cautious stabilization window looks identical to "HPA is broken" but isn't.

Docker & Deployment Manifests

Usually a quick check that you've shipped containers to production, not just run one locally.
Q1What separates a "works on my machine" Docker image from a production-grade one?
In one lineSmall, immutable, non-root, and it fails loudly and fast if something's wrong.
  • Multi-stage builds — build-time dependencies never ship in the final image.
  • A minimal base (slim/alpine or distroless) instead of a full OS image.
  • A non-root USER — a container running as root is one escape away from being root on the host.
  • .dockerignore to keep build context and layers lean.
  • Layer order matters: rarely-changing steps (installing dependencies) go above frequently-changing ones (app code) so the cache actually gets used.
  • An explicit HEALTHCHECK, and no secrets baked into any layer — they persist in image history even if a later layer deletes the file.

Q3Readiness vs. liveness probes — why do you need both?
In one lineLiveness answers "is it stuck, restart it." Readiness answers "is it ready for traffic, hold off routing to it." Confusing them causes real outages.
  • A hung process needs a restart — that's liveness.
  • A healthy-but-still-warming-up process (loading a cache, connecting to a DB) should be pulled from the Service's endpoints without being killed — that's readiness.
  • A too-strict liveness probe with no startupProbe kills slow-starting apps mid-deploy — a classic false-alarm CrashLoopBackOff that isn't actually a crash.

CI/CD & GitOps

Interviewers listen for the reasoning behind your pipeline choices as much as the tool names.
Q1Walk me through a CI/CD pipeline you've built end-to-end.
In one lineCommit triggers build, test, and scan, producing one immutable versioned image. Deployment is a separate, auditable step — never baked into the build.
  • Jenkins or GitHub Actions runs build → unit tests → SonarQube/JFrog → image push on every commit to main.
  • A separate step updates a GitOps manifest repo with the new image tag; ArgoCD picks that up and reconciles the cluster.
  • Splitting "build" from "deploy" this way is what let deployment cycle time drop 25% at Terawe without also raising risk — rollback becomes a Git revert, not a re-run of the whole pipeline.
Q2Push-based deploys vs. GitOps — why does the distinction matter for reliability?
In one linePush means CI holds prod credentials and applies changes directly. Pull means an in-cluster agent reconciles the cluster to match Git, so Git stays the source of truth and CI never touches prod.
  • Smaller blast radius — a compromised CI job can't push arbitrary changes to prod because it never had prod access to begin with.
  • Continuous drift detection — ArgoCD constantly diffs live state against Git and can auto-heal manual changes.
  • The audit trail is just Git history; rollback is a git revert, not a manual scramble.

Q7Give me a complete DevSecOps pipeline, stage by stage — what tool would you use at each gate, and why?
In one lineShift security left — a check at every stage from commit to runtime, each catching a different class of problem, so nothing reaches production on trust alone.
  1. Pre-commit — gitleaks/git-secrets as a git hook; a credential never reaches the remote repo.
  2. Source control — branch protection, required PR review, signed commits; the first real gate, and it's process, not a scanner.
  3. SAST — SonarQube, Semgrep, or Checkmarx against the source itself; catches insecure code patterns before any build happens.
  4. SCA — Snyk, OWASP Dependency-Check, or a Trivy filesystem scan against every third-party dependency; catches known CVEs in code you didn't write.
  5. Build — multi-stage Docker build, minimal base image, no build tools left in the final layer.
  6. Image scan — Trivy or Grype against the built image; catches OS- and package-level CVEs baked into the image, plus a secrets-in-layers check.
  7. Sign & attest — Cosign/Sigstore signs the image, an SBOM (Syft) gets attached, so anything deployed later can be verified as coming from this exact pipeline run.
  8. Push — immutable tag to the registry, never :latest.
  9. Policy gate — OPA/Conftest or Kyverno checks the manifest itself (no root containers, resource limits required, no privileged mode) and blocks the GitOps sync if it fails.
  10. Deploy to staging — GitOps/ArgoCD reconciles, same pattern as the base pipeline.
  11. DAST — OWASP ZAP against the actually-running staging app; catches what static analysis can't — auth bypass, misconfigured headers, live injection attempts.
  12. Approval gate — automated if every prior gate passed clean, manual for anything touching a regulated or critical path.
  13. Deploy to prod — GitOps, progressive delivery/canary.
  14. Runtime security — Falco (or a cloud-native equivalent) watches the running containers for anomalous behavior — an unexpected shell, an unexpected outbound connection — after everything upstream has already passed.
Q8How would you reduce CI/CD pipeline cost without cutting test coverage or deployment safety?
In one lineMeasure where pipeline minutes actually go first — caching and path-based triggering usually beat throwing bigger runners at the problem.
  • Cache dependencies (Maven/npm/pip layers, Docker layer caching) — repeated full downloads on every run is the single most common waste.
  • Path-based/conditional triggering — a docs-only change shouldn't kick off a full integration suite; scope triggers to what the change actually touches.
  • Parallelize independent test stages instead of running them serially on one large runner.
  • Right-size build agents — a small/medium runner for lint and unit tests, a larger one reserved only for the stages that actually need it.
  • Clean up old artifacts and images on a retention policy, rather than storing every build forever by default.
  • The goal is cost per unit of confidence, not raw pipeline minutes — cutting a security scan to save 90 seconds is a bad trade even if it looks good on a cost dashboard.

Greenfield Microservices Architecture

The open-ended design question — there's no single right answer, but there's a right way to reason through it out loud.
Q1You're designing a microservices platform from scratch — walk me through your approach.
In one lineStart from the domain, not the tech — draw service boundaries around business capabilities, then bring in only the infrastructure each boundary actually needs.
  • Domain-driven service boundaries — each service owns its data, no shared database.
  • An API Gateway as the single entry point (auth, rate limiting, routing) instead of every service handling those cross-cutting concerns itself.
  • Sync (REST/gRPC) for request/response paths; async (event bus/queue) for anything that doesn't need an immediate answer — this decouples services and absorbs load spikes.
  • Observability and CI/CD wired in from service #1, not retrofitted later — far more expensive to bolt on after twenty services already exist.
  • Design for failure from day one: timeouts, retries with backoff, circuit breakers on every inter-service call.
Interview tipWhoever asks this is usually listening for decisions you drove, not a components inventory. Frame it as "I chose X because Y," not a list of technology names — even inside a platform-team setup, you owned specific calls somewhere in the system. Lead with those.
Q2Sync vs. async communication between services — how do you decide?
In one lineIf the caller needs an answer right now to proceed, sync. If it just needs to know something happened, async.
  • REST/gRPC for user-facing request/response where latency is visible to a human.
  • Events or queues (Kafka/SQS/RabbitMQ) for anything fan-out, anything that can tolerate eventual delivery, anything where the producer should stay decoupled from how many or which consumers exist.
  • gRPC over REST internally when you control both ends and want strong typing plus lower latency.
Q3How do you keep one misbehaving service from taking down the whole platform?
In one lineAssume every dependency will fail, and design so the failure stays local.
  • Timeouts on every network call — no infinite waits.
  • Retries with exponential backoff and jitter, not a naive immediate retry — that's how you DDoS your own dependency.
  • Circuit breakers to stop hammering a dead dependency and fail fast instead.
  • Bulkheads — separate connection/thread pools per dependency so one slow dependency can't exhaust resources another one needs.
Q4How do you handle data consistency across services without a shared database?
In one lineGive up strong consistency across service boundaries on purpose, and make eventual consistency safe with patterns like Saga and the outbox.
  • Saga pattern (choreography or orchestration) for multi-step business transactions spanning services — each step has a compensating action for rollback.
  • Transactional outbox — write the state change and the "event to publish" in the same local DB transaction; a relay process publishes it — avoids the dual-write problem where the DB commits but the event publish fails, or vice versa.
Q5Tell me about a time you migrated a legacy application into containers and Kubernetes.
In one lineLegacy Java and Lucee applications, containerized and moved onto Kubernetes — the hard part usually isn't the Dockerfile, it's everything the app quietly assumed about its environment that was never written down.
  • Situation: legacy Java and Lucee applications running on traditional, hand-maintained infrastructure — deployment was manual, environment drift between servers was common, and scaling meant provisioning another full server.
  • Task: containerize these applications and move them onto Kubernetes without breaking behavior nobody had fully documented.
  • Action: started by capturing everything implicit about the current runtime — file paths, environment variables, startup order, session/state handling — before writing a single Dockerfile, since a legacy app almost always has undocumented assumptions baked into how it currently runs. Built multi-stage Docker images, moved configuration into ConfigMaps/Secrets instead of files baked into the image, and addressed session handling explicitly — legacy apps are often built assuming in-memory session state on one server, which breaks the moment there are multiple replicas behind a Service.
  • Result: the applications ran as proper Kubernetes deployments — horizontally scalable, self-healing, deployed through the same CI/CD pipeline as everything else — instead of hand-maintained servers only one or two people really understood.

SRE Practices — SLI / SLO & Your Metrics

Q1In your own words — SLI, SLO, SLA, and Error Budget.
In one lineSLI is what you measure, SLO is your internal target for it, SLA is the external promise (usually looser, with a penalty), and the error budget is 100% minus your SLO — the amount of unreliability you're allowed to spend.
  • SLI — "percentage of requests completing in under 300ms."
  • SLO — "99.5% of requests under 300ms over a rolling 30 days," the internal target.
  • SLA — "99%, with a service credit if missed" — external, contractual, deliberately looser than the SLO, so you breach your own target before you ever breach the customer's.
  • Error budget — the 0.5% of requests over 30 days you're allowed to be slow or wrong. Spend it on risk (deploys, migrations) or save it (change freeze), based on what's left.
Q2Walk me through how you actually defined SLIs and SLOs for a real platform.
In one linePick SLIs that reflect what users actually feel, set the SLO from historical baseline plus business tolerance, and alert on budget burn rate instead of static thresholds.

  • SLO set from historical baseline plus business tolerance, not an arbitrary round number picked in a meeting.
  • Wired into Grafana as a burn-rate panel, with burn-rate alerting — fast burn pages immediately, slow burn opens a ticket — so alerts map to actual budget risk instead of firing on every blip.

Q7What is chaos engineering, and why does it actually help reliability?
In one lineDeliberately injecting controlled failure into a system to find its weaknesses before an uncontrolled failure finds them for you in production.
  • Start from a steady-state hypothesis — a measurable definition of "the system is healthy" (latency and error rate within normal bounds).
  • Inject a real-world failure mode in a controlled, scoped way — kill a process, cut network access to a dependency, force a failover — and watch whether the system holds its steady state.
  • Minimize blast radius — start small (one instance, one AZ), expand only once confidence is earned.
  • The goal isn't breaking things for its own sake — it's converting an assumption ("the failover should work") into a validated fact, on your own schedule, not at 3am during a real incident.

  • Budget headroom returning to a healthy level is what actually lifts the freeze — not a fixed calendar date.
Q10What are the RED and USE methods, and when do you reach for which?
In one lineRED for anything request-driven — services, APIs. USE for the infrastructure underneath them — CPU, memory, disk, network.
  • RED — Rate, Errors, Duration. Requests per second, the error rate among them, and how long they take. The service-level view — what a user actually experiences.
  • USE — Utilization, Saturation, Errors. How busy a resource is, how much queued demand exists beyond capacity, and its error count. The infrastructure-level view — what's underneath the service.
  • In practice they're used together, not instead of each other: RED tells you the API is slow; USE tells you it's slow because the node's CPU is saturated, or the disk queue is backed up.
  • Neither replaces the SLI/SLO layer — RED/USE are the diagnostic vocabulary you reach for once the SLO has already told you something is wrong.
Q11How do you validate disaster recovery — RTO, RPO, and what actually counts as "tested"?
In one lineA DR plan isn't validated until you've actually failed over and measured the real recovery time — backups existing isn't the same as recovery working.
  • RTO (Recovery Time Objective) — how quickly service must be restored after a failure. RPO (Recovery Point Objective) — how much data loss, measured in time, the business can tolerate.
  • Define both explicitly per service before designing anything — a payments service and an internal reporting tool have very different acceptable RTO/RPO, and one DR strategy doesn't fit both.
  • Test actual restoration, not just backup completion — a nightly backup job reporting "success" for a year proves nothing about whether that backup can actually be restored under time pressure.
  • Run controlled failover exercises — the same spirit as chaos engineering, applied specifically to the DR path — and measure the real recovery time against the stated RTO, rather than assuming the runbook works because it reads correctly.
  • Feed the actual measured numbers back into the runbook and the architecture — a DR exercise that doesn't change anything afterward wasn't a real validation, it was a rehearsal of theater.

Q1Hands-on: write a bash script that checks disk usage across a list of servers and alerts if any exceed a threshold.

#!/usr/bin/env bash
set -euo pipefail

THRESHOLD=85
SERVERS=("web01" "web02" "db01")

for host in "${SERVERS[@]}"; do
  usage=$(ssh -o ConnectTimeout=5 "$host" "df -h / | awk 'NR==2 {print \$5}' | tr -d '%'")
  if (( usage >= THRESHOLD )); then

      -H 'Content-type: application/json' \
      -d "{\"text\":\"Disk alert: $host at ${usage}%\"}"
  else

  fi
done
Q2Hands-on: write a bash script that health-checks a list of endpoints and retries before alerting.
In one lineRetry with a delay before declaring anything down — a single blip shouldn't page anyone.
healthcheck.sh 
#!/usr/bin/env bash
set -euo pipefail

ENDPOINTS=("https://api.example.com/healthz" "https://payments.example.com/healthz")
MAX_RETRIES=3
RETRY_DELAY=5

check_endpoint() {
  local url=$1
  for attempt in $(seq 1 "$MAX_RETRIES"); do
    status=$(curl -s -o /dev/null -w '%{http_code}' --max-time 5 "$url")
    if [[ "$status" == "200" ]]; then
      echo "OK: $url"
      return 0
    fi
    echo "Attempt $attempt/$MAX_RETRIES failed for $url (HTTP $status)"
    sleep "$RETRY_DELAY"
  done
  echo "ALERT: $url unhealthy after $MAX_RETRIES attempts"
  return 1
}

failures=0
for url in "${ENDPOINTS[@]}"; do
  check_endpoint "$url" || ((failures++))
done

exit "$failures"
Q3How do you think about metric types in Prometheus — counter, gauge, histogram?
In one lineCounter only goes up — always wrap in rate(). Gauge goes up and down — read directly. Histogram buckets observations so you can derive percentiles.
  • Counter (requests_total, errors_total) — the raw value alone is meaningless; always wrap in rate() or increase() to get something a human can read.
  • Gauge (current memory, queue depth, active connections) — read as-is, no rate() needed.
  • Histogram (request duration) — gives you histogram_quantile() for p50/p95/p99; choose bucket boundaries that actually bracket real latency, not defaults that sit entirely below or above the real numbers.
Q4Hands-on: write a PromQL query for p95 latency, and a Prometheus alerting rule for error-budget burn.
In one linep95 comes from histogram_quantile() over the duration histogram; the burn-rate alert compares the 5xx rate to a multiple of the SLO's allowed error rate.

Q5Prometheus/Grafana vs. an APM tool like New Relic or Dynatrace — when do you reach for which?
In one linePrometheus/Grafana for infrastructure and the custom service metrics you define; APM tools for automatic code-level tracing and profiling without instrumenting everything by hand.
  • Prometheus/Grafana — open-source, you own the metric definitions, strong for infra and SLO dashboards, pull-based, requires instrumentation.
  • New Relic/Dynatrace — auto-instrumentation, distributed tracing down to the code line, faster initial time-to-value, but licensing cost scales with hosts and data, and you're more locked into their query language and UI.
  • Many senior setups run both — Prometheus/Grafana for platform-level SLOs, an APM tool for deep app-level root cause during an actual incident.
Q6A Grafana panel shows "No data" or looks wrong — how do you debug it?
In one lineIsolate datasource from query from dashboard — in that order — before assuming the metric itself is missing.
  • Confirm the datasource itself is reachable — Grafana's datasource settings page has a built-in "Test" connection check.
  • Run the panel's query directly in Grafana's Explore view, bypassing the dashboard entirely — this isolates "the query is wrong" from "the dashboard is wrong."
  • Check the time range and timezone — a dashboard default range or a browser/server timezone mismatch is a very common false "no data."
  • If a relabeling rule changed recently, label names/values the query filters on may no longer match anything — diff the query's label selectors against what the target is actually exposing now.
  • Dashboard variables (a service or environment dropdown) can interpolate into the query as an empty or unexpected value — check the variable's current resolved value, not just its dropdown label.
Q7An alert isn't firing when you'd expect it to — or it's firing too much and flapping. How do you debug the alerting pipeline?
In one lineSplit the pipeline in two — is the rule evaluating and firing at all, and separately, is the notification actually reaching anyone — because a silent alert can fail at either stage.
  • Check Prometheus's own /alerts (or Grafana Alerting's state view) directly — confirm the rule is evaluating at all and see its current state (inactive/pending/firing), before assuming anything about notifications.
  • Confirm the underlying metric actually exists with the label cardinality the rule expects — a rule referencing a label that no longer exists silently never fires, with no error anywhere.
  • Check the rule's for: duration — a real breach that resolves faster than the for: window never promotes to firing.
  • If the rule is firing but no one was notified, the problem has moved to Alertmanager — check routing rules, active silences, and mute timings; a correctly firing rule can still be correctly and silently suppressed downstream.
  • For flapping: add hysteresis (a lower clear-threshold than the fire-threshold) or lengthen for:, rather than just widening the raw threshold, which usually just trades false positives for false negatives.
Q8What are the three pillars of observability, and how is "observability" actually different from "monitoring"?
In one lineMonitoring tells you something is wrong from signals you already knew to watch for; observability gives you enough telemetry to figure out why, including failure modes you didn't predict.
  • Metrics — the aggregate numbers: rate, error count, latency percentiles, saturation. Tells you what is happening and how much.
  • Logs — event-level detail. Tells you the specifics of a single request or error, the context a metric alone can't carry.
  • Traces — the path of a single request across distributed services. Tells you where in a multi-hop chain the time or error actually happened.
  • Monitoring is built around known failure modes — a threshold on a dashboard you set up because you expected that specific thing to break.
  • Observability is what lets you debug the failure mode you didn't predict — a genuinely new incident where the question isn't "did metric X cross threshold Y," it's "what's actually going on," and logs/traces are what answer that live.
Q9How does Splunk fit alongside Prometheus and Grafana in your stack — what's each one actually for?
In one linePrometheus/Grafana for time-series metrics and dashboards; Splunk for the detailed, searchable event-level log data a metric can't hold.
  • Prometheus scrapes and stores numeric time-series; Grafana visualizes it and drives alerting on thresholds and SLO burn rate — this is the "is something wrong, and how bad" layer.
  • Splunk ingests and indexes logs — structured and unstructured — and is where you go to answer "what exactly happened, on this specific request, at this specific time" once a metric has told you something's off.
  • In a real investigation the two are used together: Grafana narrows the window ("errors spiked between 14:02 and 14:07"), then Splunk is queried against that exact window to pull the actual error payloads, stack traces, or affected request IDs.
  • Where compliance is in scope — PCI DSS environments in particular — Splunk is also the audit/security log system of record, so retention and access-control requirements apply independent of whatever the operational troubleshooting need is.
  • Logging volume is a real cost driver at scale — high-cardinality or overly verbose logging can make ingestion cost rival compute cost, worth flagging proactively rather than discovering at the next license renewal.
Q10Hands-on: write a Python script that checks a service's health endpoint and reports status.
In one lineA simple GET with an explicit timeout and a clear healthy/unhealthy branch — the timeout matters more than it looks, since a hung request without one can block the whole check.
healthcheck.py 
#!/usr/bin/env python3
import sys
import requests

ENDPOINTS = [
    "https://api.example.com/healthz",
    "https://payments.example.com/healthz",
]

def check(url, timeout=5):
    try:
        resp = requests.get(url, timeout=timeout)
        return resp.status_code == 200, resp.status_code
    except requests.exceptions.RequestException as exc:
        return False, str(exc)

if __name__ == "__main__":
    unhealthy = []
    for url in ENDPOINTS:
        ok, detail = check(url)
        print(f"{'OK' if ok else 'FAIL'}: {url} ({detail})")
        if not ok:
            unhealthy.append(url)
    sys.exit(1 if unhealthy else 0)
  • Explicit timeout is the detail people skip — without it, one hung endpoint can block the entire check indefinitely instead of failing fast.
  • The exit code (0/1) matters as much as the printed output when this runs inside a cron job or a CI step — that's what lets it gate a pipeline or trigger an alert, not just log to a file nobody reads.
  • Same shape as the bash version earlier in this section, but Python is the better fit once the check needs real logic — parsing a JSON health payload, retrying with backoff, feeding results into a ticketing API — rather than a one-line status check.
Q11Hands-on: write a script that cleans up stale Docker images and stopped containers on a node before disk pressure becomes an incident.
In one linePrune what's safely unreferenced on a schedule, so disk-pressure NotReady never gets the chance to happen instead of being cleaned up after the fact.
docker-cleanup.sh 
#!/usr/bin/env bash
set -euo pipefail

THRESHOLD_GB=20
FREE_GB=$(df --output=avail -BG / | tail -1 | tr -dc '0-9')
echo "Free space before cleanup: ${FREE_GB}GB"

# Remove stopped containers older than 24h
docker container prune -f --filter "until=24h"

# Remove dangling and unused images not referenced by any container
docker image prune -a -f --filter "until=72h"

# Remove unused volumes (only ones with no container reference)
docker volume prune -f

FREE_GB_AFTER=$(df --output=avail -BG / | tail -1 | tr -dc '0-9')
echo "Free space after cleanup: ${FREE_GB_AFTER}GB"

if [ "$FREE_GB_AFTER" -lt "$THRESHOLD_GB" ]; then
    echo "WARNING: still below ${THRESHOLD_GB}GB after cleanup — needs manual review"
    exit 1
fi
  • The filters matter more than the prune command itself — until=24h/until=72h avoid nuking an image mid-deploy or a container that stopped intentionally seconds ago.
  • Runs safely on a schedule (cron, or a DaemonSet in a cluster context) rather than only reactively once a node is already flirting with disk pressure — this is exactly the failure mode behind the NotReady scenario earlier in this handbook.
  • The non-zero exit on "still low after cleanup" is what turns this from a silent script into something that can page someone before it becomes a real node failure.
Q12Hands-on: write a script that reports pods with abnormally high restart counts across all namespaces, so nobody's manually running kubectl across a dozen namespaces every morning.
In one lineQuery once, filter for the signal that actually matters, and print only what needs a human — that's the whole point of killing this kind of toil.
restart-report.py 
#!/usr/bin/env python3
from kubernetes import client, config

RESTART_THRESHOLD = 5

def main():
    config.load_kube_config()  # use load_incluster_config() if running inside the cluster
    v1 = client.CoreV1Api()
    pods = v1.list_pod_for_all_namespaces(watch=False)

    flagged = []
    for pod in pods.items:
        statuses = pod.status.container_statuses or []
        for cs in statuses:
            if cs.restart_count >= RESTART_THRESHOLD:
                flagged.append((pod.metadata.namespace, pod.metadata.name, cs.name, cs.restart_count))

    if not flagged:
        print("No pods above the restart threshold.")
        return

    flagged.sort(key=lambda row: row[3], reverse=True)
    print("namespace | pod | container | restarts")
    for ns, pod_name, container, count in flagged:
        print(f"{ns} | {pod_name} | {container} | {count}")

if __name__ == "__main__":
    main()
  • Filters at the API level for what actually matters (a real restart-count threshold), rather than dumping every pod's status and making a human eyeball it.
  • Same shape whether it prints to stdout for a manual morning check, or gets wired into a scheduled job that posts the output to Slack — the toil-reduction win is in not running this query by hand across a dozen namespaces every day.
  • A high restart count is a leading indicator worth catching before it becomes a paging incident — a good candidate for the "what would you automate first" answer: frequent, low-complexity, and it directly feeds earlier detection.
§9

Incident Management & RCA

The process matters as much as the outcome here — restore-first thinking under pressure, not a perfect diagnosis.
Q1Walk me through your incident management process end to end.
In one lineDetect, triage, mitigate, recover, then RCA and postmortem — in that order, because restoring service always outranks finding the perfect root cause in the moment.
  • Detection — an alert fires, or a customer/monitoring signal surfaces the issue; first move is confirming it's real and establishing scope (one user, one region, everyone).
  • Triage — assess impact and severity, form initial hypotheses, pull in the right people. Fast, not a deep investigation.
  • Mitigation — the actual priority: rollback, scale, failover, disable a feature flag, or restore a failed dependency. Stop the customer impact first.
  • Recovery — confirm the service is genuinely healthy again (SLO recovering, not just the alert clearing) before standing down.
  • RCA — once stable, dig into the real cause using metrics, logs, deployment history, and dependency behavior.
  • Postmortem — blameless review, written up with concrete corrective actions and owners, not just a narrative of what happened.
Q2What's the difference between MTTD and MTTR, and how does each actually get reduced in practice?
In one lineMTTD is how fast you find out; MTTR is how fast you're back. They're reduced by different levers — better signal for detection, better runbooks and automation for recovery.
  • MTTD (Mean Time to Detect) — the gap between an incident starting and someone or something noticing. Reduced by better dashboards, SLO-based alerting instead of raw thresholds, and cutting the noise that makes real signals easy to miss.
  • MTTR (Mean Time to Recover/Resolve) — the gap between detection and service being restored. Reduced by runbooks, pre-approved rollback paths, clear on-call ownership, and automated remediation for known failure modes.
  • The two don't move together automatically — you can detect something instantly and still take an hour to recover with no runbook, or detect it late but recover in 90 seconds because the fix is a one-command rollback.
  • Postmortem action items should say which one they target — "add a burn-rate alert" is an MTTD fix, "add an automated rollback trigger" is an MTTR fix; conflating the two produces vague action items that don't move either number.
Q3Explain Root Cause Analysis and the 5 Whys technique, with a real example.
In one line5 Whys means not stopping at the first plausible answer — keep asking why until you hit something you can actually fix, not just something that's technically true.
  • RCA is the structured process of finding the actual underlying cause, not the first symptom you happen to see.
  • Example: the app went down → why? the pod crashed → why? it hit its memory limit → why? memory usage grew steadily all day → why? a cache wasn't evicting expired entries → why? an unbounded cache with no TTL shipped in the last release. That last answer is fixable; "the pod crashed" is not.
  • Stopping too early is the common failure mode — "the pod crashed" as an RCA conclusion tells you nothing about how to prevent recurrence.
  • Not every incident cleanly resolves to one root cause — sometimes it's several contributing factors that combined; a good RCA says so rather than forcing a single tidy answer.
Q4What makes a postmortem "blameless," and why does that matter operationally, not just culturally?
In one lineBlameless means the writeup targets systems and processes, not individuals — because a team that fears blame stops reporting near-misses, and near-misses are exactly what you want reported before they become real incidents.
  • Focus on what allowed the failure — a missing safeguard, an untested assumption, an alert that didn't exist — rather than who clicked what.
  • Every corrective action gets a named owner and a due date; a postmortem with no action items is a story, not a prevention mechanism.
  • The practical payoff: engineers are far more likely to say "I think I caused this" or flag a near-miss early when they trust the process isn't building a case against them — and early, honest reporting is what actually shortens the next incident's MTTD.
Q5Give me a real RCA walkthrough, structured the way you'd present it.
In one lineIncident → detection → timeline → investigation → root cause → mitigation → prevention — the same shape every time, so a reviewer can follow it without extra narration.
  • Incident — the customer-visible symptom (elevated errors, latency, unavailability).
  • Detection — what actually surfaced it: an alert, an SLO burn-rate warning, a customer report.
  • Timeline — the exact start time, correlated against deployments, infra events, and dependency changes around that window.
  • Investigation — what was checked: logs, metrics, recent changes, resource utilization, dependency health.
  • Root cause — the actual underlying driver, not just the symptom.
  • Mitigation — the specific action that restored service.
  • Prevention — the concrete follow-up: a new alert, a runbook, a code fix, a capacity change.
Interview tipWalk this structure using one of your own real incidents from Terawe/Unique Vacations/RSAB in the room — it lands far better than a generic hypothetical, and it's the shape an interviewer is listening for regardless of which incident you pick.
Q6You've got five alerts firing at the same time. How do you decide what to work first?
In one lineCustomer impact and business criticality decide the order, not arrival time — and the first check is whether some of those five are actually one incident wearing five alerts.
  • Rank by actual customer/business impact — a payment-path availability alert outranks a non-prod CPU warning regardless of which fired first.
  • Check for a shared root cause before treating them as five separate problems — one underlying failure (a node down, a dependency outage) commonly fans out into several simultaneous alerts.
  • Delegate what can be delegated — this is also where clear on-call ownership and escalation paths pay off; one engineer triaging five fires alone is a process gap, not something to route around silently.
  • Communicate status on the lower-priority items even while focused on the top one — silence on the other four erodes trust in the response, even when the prioritization itself was correct.
Q7How do you reduce MTTR specifically — not detection, the actual recovery time?
In one lineThree levers: better diagnosis tooling so the cause is found fast, pre-built remediation so the fix doesn't need to be invented live, and automation so some of it doesn't need a human at all.
  • Diagnosis — dashboards, logs, and traces that get an engineer to the likely cause in minutes; a well-labeled Grafana panel beats a data lake queried cold at 3am.
  • Remediation — runbooks for known failure modes, and a rollback path that's actually pre-approved and one command away, not invented under pressure.
  • Automation — for recurring failure modes, auto-remediation (restart, failover, scale) removes the human-reaction-time floor entirely.
  • The postmortem loop closes this — every recurring incident that gets automated away is MTTR reduced to zero for that specific cause, permanently, which compounds far more than shaving minutes off manual response.

Performance Testing & Capacity Planning

The senior signal here is refusing to scale blindly — bottleneck first, capacity second.
Q1Load, stress, endurance, and capacity testing — what's the actual difference, and when do you run which?
In one lineLoad tests expected traffic, stress tests beyond it to find the breaking point, endurance tests a sustained run for slow-building problems, and capacity testing answers "how much can this actually take."
  • Load testing — validates behavior under expected/normal traffic; the baseline sanity check before a release.
  • Stress testing — pushes past expected capacity deliberately, to find the breaking point and, just as importantly, how the system fails and recovers once past it.
  • Endurance (soak) testing — a sustained realistic workload run for hours, built to surface things a short test never reveals: memory leaks, connection-pool exhaustion, gradual degradation.
  • Capacity testing — determines how much traffic the system can actually support while still meeting its SLOs, not just "before it crashes."
  • These map directly onto real risk: stress testing tells you the failure mode before a real traffic spike does; endurance testing catches the slow leak a 10-minute load test would never surface.
Q2What do you actually measure during performance testing, beyond "is it fast"?
In one linePercentiles over averages, always — an average can look fine while your worst 5% of users have a broken experience.
  • Throughput and requests/sec — how much the system is actually processing.
  • p95 and p99 latency, not just average — the tail is where real user pain lives, and an average latency chart can hide a p99 that's already breaching SLO.
  • Error rate under load — does reliability degrade before throughput does, or the other way around.
  • Resource saturation alongside the app metrics — CPU, memory, network, database connection-pool utilization — so a latency increase ties back to an actual resource constraint instead of a guess.
Q3Production latency suddenly doubles. Walk through the troubleshooting sequence.
In one lineScope it first — everywhere or one endpoint — then correlate the exact start time against deployments, traffic, and scaling events before touching infrastructure.
  • Determine whether it's global or isolated to specific endpoints, services, or a subset of traffic — that alone rules out or points toward a large chunk of possible causes.
  • Establish the exact start time and correlate against recent deployments, traffic pattern changes, and scaling events around that window.
  • Check p50/p95/p99 specifically, not the average — a shifted tail with a flat median usually means a subset of requests are hitting something specific (a cold cache, a slow query path, one bad node), not a system-wide issue.
  • Work outward from the app: CPU/memory/network on the compute layer, then database latency and connection-pool behavior, then downstream dependency response times.
  • If a deployment lines up with the start time, compare old vs. new version directly rather than assuming causation from timing alone — then mitigate before finishing the investigation.
Q4How do you do capacity planning without either running out of headroom or over-provisioning for demand that never comes?
In one lineForecast from real historical growth and known business events, validate the forecast with an actual load test, and always weigh the answer against cost — not just against "will it hold."
  • Start from historical traffic and resource-utilization trends, not a guess — actual growth rate beats an assumed one every time.
  • Fold in known business events (a marketing push, a seasonal peak, a new client onboarding) that historical data alone won't predict.
  • Identify the point where current architecture would breach the SLO under projected growth, and plan headroom ahead of that point — not right at it.
  • Validate the forecast with real load/performance testing rather than trusting the math alone; a capacity model is a hypothesis until it's been tested.
  • Cost is part of the answer, not an afterthought — provisioning six months of headroom on day one is its own kind of waste; the goal is enough runway to react, not maximum runway regardless of spend.
Q5Traffic is expected to spike 10x tomorrow. What do you actually do — not "increase replicas by 10x"?
In one lineFind the real bottleneck first — the database and stateful components almost never scale as cleanly as the stateless app tier does, so scaling only the easy part gives false confidence.
  • Identify the actual constraint — application horizontal scaling is usually the easy part; the database, cache, and any other stateful component are the more likely limiting factor.
  • Validate that HPA/cluster autoscaling can actually react fast enough for the expected ramp — a scale-up that takes 3 minutes doesn't help against a spike that arrives in 30 seconds.
  • Test the expected load in a controlled environment beforehand if there's time, rather than discovering the bottleneck live.
  • Check ingress and load-balancer connection limits, not just compute — these have ceilings too, and they're easy to forget until they're the reason a "successfully scaled" backend still can't be reached.
  • Have a degradation plan ready regardless — a feature flag to shed non-critical load, or a graceful "temporarily limited" response, beats an outright outage if the capacity assumptions turn out wrong.
§11

Production Judgment & Prioritization

Less about the one right technical answer, more about whether your reasoning holds up when the interviewer keeps pushing.
Q1CPU on a node or pod suddenly spikes to 95%. What do you actually do?
In one lineScope it before reacting — one pod, many pods, or the whole node — and separate legitimate traffic from "something's wrong" before deciding to scale.
  • Determine blast radius first — a single pod at 95% is a very different problem from every pod on a node being pegged.
  • Check whether traffic actually increased to match — a real, proportional increase means scale; a CPU spike with flat traffic means investigate the workload itself (a stuck loop, a bad query, a runaway job).
  • Check what HPA is already doing about it — it may already be reacting correctly, and the "action" is confirming that rather than intervening manually.
  • If it's anomalous and not traffic-driven, profile the actual process before adding capacity — more CPU doesn't fix a bug that's burning cycles unnecessarily; it just makes the bug more expensive to run.
Q2Memory usage keeps climbing and doesn't come back down. How do you find out if it's a real leak?
In one lineCompare the growth curve against traffic and time of day — a leak keeps climbing regardless of load; healthy caching behavior plateaus.
  • Check whether the growth is container-specific or node-wide — narrows scope immediately.
  • Compare the memory curve against traffic — if usage keeps climbing during low-traffic periods too, that points toward a leak rather than legitimate cache growth under load.
  • Check OOM events and application logs for the exact pattern — a slow steady climb reads differently from a sudden jump, and each points toward a different class of bug.
  • A temporary capacity bump can buy time during an active incident, but the permanent fix has to address what's actually holding the memory — an unbounded cache, an unclosed connection, a growing in-memory collection — or the same incident recurs on a longer cycle.
Q3The database is slow and app latency is climbing with it. (Same failure family as the connection-pool-exhaustion chaos experiment on your resume.)
In one lineDon't reflexively raise the connection pool size — that can make a genuinely slow database worse by letting even more concurrent load hit it.
  • Correlate app latency directly against DB latency, connection-pool utilization, and query performance to confirm the database is actually the source, not just correlated with it.
  • Check for connection leaks — connections held open longer than they should be — versus a genuine increase in concurrent load or query volume.
  • Check for slow queries specifically — a handful of expensive queries can dominate pool wait time even while most queries are fine.
  • Increasing the pool size is not the default fix — a struggling database handed more concurrent connections can degrade further, not recover; this ties directly back to the chaos-engineering project, where connection-pool exhaustion was one of the scenarios that surfaced a genuine single point of failure.
  • Stabilize first — shed load, fail over, or throttle non-critical traffic — then address the underlying query/connection behavior.
Q4One Kubernetes node goes down in production. Walk through what happens and what you check.
In one lineKubernetes should self-heal this — your job is verifying it actually did, not manually intervening by default.
  • Confirm the workload impact first — Kubernetes should reschedule evictable pods onto healthy nodes automatically.
  • Verify remaining node capacity can actually absorb the rescheduled pods — a node going down when the cluster is already near capacity can cascade into Pending pods elsewhere.
  • Check PodDisruptionBudget settings — they can slow voluntary rescheduling in ways that look like a stuck cluster but are actually a safety mechanism working as designed.
  • Confirm the service stayed within SLO through the event — a successful self-heal that still breached the SLO for a few minutes is still worth a postmortem line item.
Q5The app works when you test it internally but fails for external users. Where do you look?
In one lineTrace outward along the exact path an external user actually takes — internal access usually skips several hops that are exactly where the problem lives.
  • Internal testing (from inside the cluster/VPC) frequently bypasses DNS, the public load balancer, ingress, and any WAF/security layer entirely — so "it works for me" from inside proves less than it seems to.
  • Walk the actual external path: DNS resolution → public load balancer → ingress rules → TLS/certificate validity → security group/network policy → the same service/pod layer internal traffic also hits.
  • An expired or misconfigured certificate, a DNS record pointing at the wrong target, or a security-group rule that only allows internal CIDR ranges are all common causes that never show up in an internal test.
Q6Error rate spikes right after a deployment. What's the process?
In one lineEstablish the correlation is real, compare old vs. new version directly, and default to rollback before spending time diagnosing live in production.
  • Confirm the timing genuinely lines up — a deployment finishing 30 seconds before an unrelated spike is coincidence, not causation, and chasing the wrong lead wastes the exact time you don't have.
  • Compare logs and metrics between the previous and new version directly, rather than only looking at the new version in isolation.
  • If correlation is strong and customer impact is real, roll back first — diagnose the actual defect afterward, in a non-production environment, without the clock running.
  • Feed the finding back into the pipeline — a canary stage or a stronger pre-prod smoke test that would have caught this becomes the concrete prevention step, not just "be more careful next time."
Q7An alert fires but there's no actual customer impact. Do you just ignore it?
In one lineNo — you fix the alert, because an alert that cries wolf trains people to ignore the next one that isn't.
  • First confirm it genuinely has no customer/SLO impact — not just that it looks that way at a glance.
  • If it's truly non-impactful, that's a signal the alert's threshold or condition needs tuning, not that this specific instance should be silently dismissed — same underlying discipline as the alert-noise-reduction work on the resume.
  • Track how often a given alert fires without corresponding impact — a high false-positive rate for one specific alert is itself the metric that justifies retiring or retuning it.
  • The goal isn't fewer alerts as a vanity number; it's a signal-to-noise ratio high enough that every page still gets full attention.
Q8Cutting infrastructure 30% would save real money but increases reliability risk. What do you do?
In one lineQuantify the trade-off against the actual SLO and business criticality — don't accept or reject it on instinct in either direction.
  • Model the specific risk — does the cut threaten peak-load headroom or redundancy across a failure domain, or does it just trim comfortable slack that was never really load-bearing?
  • Look for lower-risk savings first — right-sizing over-provisioned requests, killing idle resources, storage lifecycle policies — before touching anything that trades away actual redundancy.
  • If the cut does threaten the SLO, that's the answer to bring back: not a flat "no," but "here's the SLO risk this creates, and here's what it would take to do safely" — a number the business can actually weigh, not a refusal.
  • Cost optimization is bounded by reliability requirements, not the other way around — but "bounded by" doesn't mean "never touched"; every cut gets checked against the SLO before it ships.

Linux & Networking
Q1Explain the complete request flow from a browser to a Kubernetes pod.
In one lineDNS resolves a name to an IP, TCP/TLS establish the connection, then it's the same LB → ingress → service → pod chain from the Kubernetes request-path diagram earlier in this handbook.
  • Browser resolves the domain via DNS (recursive resolver → root → TLD → authoritative), getting back an IP — typically a cloud load balancer's.
  • TCP three-way handshake, then TLS handshake (certificate validation, key exchange), establishes an encrypted connection to that IP.
  • From there it's the same chain as the Kubernetes request-path diagram earlier in this handbook: LB → ingress controller → Service → Endpoints → Pod → application.
  • Inside the cluster, kube-proxy's iptables/IPVS rules are what actually route the Service's virtual IP to a real pod IP — there's no separate internal load balancer doing this.
Q2Difference between TCP and UDP. Where have you used each?
In one lineTCP is connection-oriented and guarantees delivery/order — used for anything that can't tolerate silent data loss. UDP is fire-and-forget, faster, no delivery guarantee — used where speed matters more than an occasional lost packet.
  • TCP: handshake, acknowledgments, retransmission, ordering — the overhead buys reliability. Almost all HTTP/API/database traffic runs on it.
  • UDP: no handshake, no guaranteed delivery or order — lower latency, lower overhead. DNS queries, some metrics-scrape patterns, and anything latency-sensitive where an occasional dropped packet is acceptable.
  • DNS itself defaults to UDP, falling back to TCP only for responses too large for a single UDP packet.
Q3How does DNS resolution work internally?
In one lineLocal cache → recursive resolver → root → TLD → authoritative nameserver, each step narrowing down until an IP comes back, cached at every layer along the way.
  • Check local caches first — browser cache, then OS resolver cache — before any network query happens.
  • If not cached, the query goes to a recursive resolver, which queries a root nameserver → gets referred to the TLD nameserver (e.g. .com) → gets referred to the domain's authoritative nameserver, which returns the actual record.
  • The result is cached at every layer along the way, honoring the record's TTL — exactly why a DNS change can take time to propagate, and why "works for me, not for them" is sometimes just a stale cache somewhere in that chain.
Q4How would you debug high CPU, memory, or disk utilization on a Linux server?
In one lineIdentify the specific process first, then go tool-specific — CPU wants strace, memory wants per-process breakdown, disk wants iotop/du — rather than treating "server is slow" as one undifferentiated problem.
  • CPU: top/htop to find the process, ps -eLf for per-thread detail if one thread is pegged; strace -c -p <pid> shows which syscalls dominate.
  • Memory: free -h for the overall picture, then ps aux --sort=-%mem per-process; /proc/<pid>/status for actual RSS vs. a container's cgroup limit.
  • Disk: df -h for space, du -sh * to find what's consuming it, iotop for I/O-bound processes specifically — "disk full" and "disk I/O saturated" look similar from the outside but need different fixes.
  • In all three cases, correlate against what changed recently — a deploy, a cron job, a traffic shift — rather than treating the number in isolation.
Q5Explain Load Balancer, Reverse Proxy, and Ingress with real examples.
In one lineA Load Balancer distributes traffic across backends (an AWS ALB); a Reverse Proxy sits in front of servers and can also terminate TLS/cache/route (nginx); Ingress is Kubernetes' own API object telling a controller how to configure exactly that kind of routing for services inside the cluster.
  • Load Balancer — distributes incoming traffic across multiple backend instances. Example: an AWS ALB in front of an Auto Scaling Group.
  • Reverse Proxy — sits in front of one or more backend servers, forwarding requests to them; commonly also does TLS termination, caching, and routing. Example: nginx in front of an app server.
  • Ingress — a Kubernetes API object, not a piece of software — it declares HTTP/HTTPS routing rules; an Ingress Controller (nginx, or the AWS Load Balancer Controller) reads those rules and implements them, often by provisioning a real load balancer underneath.
  • The overlap is real: an Ingress Controller is frequently both a reverse proxy and something that provisions a load balancer — Ingress is the Kubernetes-native declarative interface to that behavior, not a separate mechanism.
Docker & Kubernetes
Q6What happens internally when you run docker run?
In one linePull the image if it's not cached, then build an isolated environment for it — namespaces, a cgroup, a union filesystem, a virtual network interface — and exec the container's process as PID 1 inside all of it.
  • Docker checks locally for the image; if missing, pulls it from the registry layer by layer.
  • Creates new Linux namespaces (PID, network, mount, UTS, IPC) so the container gets its own isolated view of processes, network, filesystem, and hostname.
  • Sets up a cgroup to enforce the container's CPU/memory limits.
  • Builds the container's filesystem from the image's layers via a union filesystem (overlay2 is the common default), plus a thin writable layer on top.
  • Creates a virtual network interface (veth pair) connecting the container's network namespace to the host/bridge network.
  • Execs the image's entrypoint/cmd as PID 1 inside that new namespace — this is why a container's main process being PID 1 matters for signal handling, which doesn't behave the same as it would for a normal process.
Q7Difference between CMD and ENTRYPOINT.
In one lineENTRYPOINT sets the fixed command that always runs; CMD supplies default arguments to it — CMD alone, with no ENTRYPOINT, is just the default command, fully overridable at docker run.
  • ENTRYPOINT defines the executable that runs when the container starts — meant to be fixed, not casually overridden.
  • CMD defines default arguments — if both are present, CMD's value is passed as arguments to ENTRYPOINT; if only CMD is present, it's the whole default command, and anything passed after the image name at docker run replaces it entirely.
  • Common pattern: ENTRYPOINT ["myapp"] + CMD ["--config", "/etc/myapp/default.yaml"] — running normally uses the default config, but docker run myimage --config /other.yaml swaps just the argument without anyone needing to override the entrypoint itself.
Q8Why is a pod stuck in CrashLoopBackOff? How would you debug it?
In one lineSame root causes and same debugging sequence as the Kubernetes section earlier in this handbook — check current and previous logs first, since the previous container usually holds the real startup failure.
  • Common causes: bad startup config, missing secrets/ConfigMaps, a failing dependency, OOMKilled, or a probe misconfiguration.
  • kubectl logs <pod> --previous is the single highest-value command here — the current container is usually already mid-restart into its next failure by the time you look.
Q9Difference between Deployment, StatefulSet, DaemonSet, and Job.
In one lineDeployment for stateless, interchangeable replicas; StatefulSet when pod identity or storage or order matters; DaemonSet for one-per-node; Job for run-to-completion work.
  • Deployment — manages stateless, interchangeable pod replicas; any replica can serve any request, and rolling updates replace them freely.
  • StatefulSet — for workloads where pod identity matters: stable network names (pod-0, pod-1...), stable per-pod persistent storage, ordered start/scale/update. Databases, message queues — anything where "which specific instance" matters.
  • DaemonSet — runs exactly one pod per node (or a matching subset) — the pattern behind node-level agents like log collectors, the VPC CNI's aws-node, or a monitoring exporter.
  • Job — runs a pod to completion for a finite task, not a long-running service; CronJob is the scheduled version of the same thing.
Q10Readiness Probe vs Liveness Probe.
In one lineReadiness controls whether a pod receives traffic; liveness controls whether Kubernetes restarts it. Full depth, plus the startup-probe interaction that trips people up, is in the Kubernetes section earlier in this handbook.
  • Readiness failure → pulled from the Service's endpoints, pod stays alive and can recover on its own.
  • Liveness failure (repeated) → Kubernetes restarts the container, even if the process is technically still running but stuck.
Q11Kubernetes pods are Running but users receive 503 errors. What will you check?
In one lineRunning doesn't mean ready — same eight-hop request-path check as the dedicated 503 walkthrough and diagram earlier in this handbook.
  • Start at the Service's selector match and the Endpoints object — a pod can be Running and still be absent from Endpoints if it isn't passing readiness.
  • Full stage-by-stage breakdown, including the request-path diagram, is in the Kubernetes section earlier in this handbook.
Q12How does Kubernetes Service Discovery work?
In one lineCoreDNS gives every Service a stable DNS name; kube-proxy programs iptables/IPVS rules on every node so traffic to that name's virtual IP load-balances across healthy pod IPs.
  • Every Service gets a DNS name via CoreDNS (service-name.namespace.svc.cluster.local) and a stable virtual IP — pods never need to know real pod IPs, just the Service name.
  • kube-proxy watches the API server and rewrites local iptables/IPVS rules on every node whenever a Service's Endpoints change — there's no separate central load balancer inside the cluster.
  • EndpointSlices track which pods are actually ready to receive traffic — the same mechanism the readiness probe feeds into.
Q13Explain ConfigMaps and Secrets. How do you manage them across environments?
In one lineSame shape, different sensitivity — across environments the pattern is one template plus environment-specific values injected at deploy time, not a hand-edited manifest per environment.
  • ConfigMap — non-sensitive configuration (URLs, feature flags, log levels), injected as environment variables or mounted files.
  • Secret — same mechanism, meant for sensitive values. Base64-encoded by default, which is encoding, not encryption — real protection comes from etcd encryption-at-rest and RBAC restricting who can read Secret objects.
  • Across environments: keep the Deployment manifest identical and let environment-specific ConfigMap/Secret values differ — via Kustomize overlays, separate Helm values files, or a GitOps directory-per-environment structure — rather than hand-editing the same manifest per environment.
  • For production Secrets, most teams keep the actual sensitive value out of Git entirely, even encrypted — a tool like Sealed Secrets, External Secrets Operator, or a cloud secrets manager referenced from the cluster.
CI/CD
Q14Explain your CI/CD pipeline from code commit to production.
In one lineCommit → build/test → security scans → image build/push → GitOps deploy to staging → validation → promotion to prod. Full 14-stage version with a tool at every gate is in the CI/CD section earlier in this handbook.
  • The short version: commit → CI build and test → SAST/SCA scans → container image build, scan, and push → GitOps manifest update → ArgoCD syncs to staging → smoke/health validation → promotion (automated or gated) to production.
Q15How do you implement zero-downtime deployments?
In one lineRolling updates with readiness probes as the actual gate — a new pod only takes traffic once it reports ready, and the old pod isn't removed until the new one already is.
  • Multiple replicas behind a Service, rolling update strategy with maxUnavailable/maxSurge tuned so capacity never drops during the rollout.
  • Readiness probes are what actually make this safe — without one, Kubernetes has no way to know a new pod isn't ready yet and will route traffic to it immediately.
  • For anything riskier than a routine release, canary or blue-green adds a validation window before the new version gets full traffic.
Q16How would you optimize a pipeline that takes 25 minutes to complete?
In one lineProfile which stage actually owns the 25 minutes before optimizing anything — caching and parallelization usually account for most of the win, and it's rarely evenly distributed across stages.
  • Break down where the time actually goes stage by stage first — "it's slow" doesn't say whether it's dependency install, test execution, image build, or a runner queue.
  • Cache dependencies (package-manager caches, Docker layer caching) — repeated full downloads/rebuilds on every run is the single most common source of wasted time.
  • Parallelize independent stages — unit tests, lint, and separate service builds usually don't need to run serially on one runner.
  • Split slow test suites and run them concurrently across multiple runners rather than one long serial run.
  • Right-size runners for the stage that's actually CPU/IO-bound, not a blanket upgrade for the whole pipeline.
  • Skip what the change doesn't touch — path-based/conditional triggering so a docs-only change doesn't run the full 25-minute suite.
Q17How do you implement rollback if deployment fails?
In one lineAutomated rollback triggered by post-deploy health checks failing, using the deployment system's own revision history — not a manual scramble to remember the last-good version.
  • Kubernetes rollout history (kubectl rollout undo) or ArgoCD's revision history both make "go back to the last-known-good state" a single command, not a rebuild.
  • Automated health/smoke checks immediately post-deploy should trigger this — waiting for a human to notice costs exactly the minutes rollback exists to save.
  • The rollback target should be a previously-validated, already-tested version — never a hotfix improvised live during the incident.
Q18How do you manage secrets securely in CI/CD pipelines?
In one lineSecrets live in the CI platform's own secret store or an external vault fetched at runtime — never in the pipeline YAML or the repo — and are scoped to only the specific jobs that actually need them.
  • Use the CI platform's native secrets store (GitHub Actions secrets, Jenkins credentials store) or fetch from an external secrets manager at runtime — never hardcoded in the workflow file or committed to the repo.
  • Scope secrets to the specific job/environment that needs them — a build job that doesn't deploy shouldn't have production credentials available to it at all.
  • Mask secret values in logs by default and avoid echo-ing them anywhere, including for debugging.
  • Rotate regularly and treat a pipeline credential leak the same as any other credential compromise — audit what that credential could reach, not just where it appeared.
Terraform & Cloud
Q19How does Terraform state locking work?
In one lineThe backend (e.g. DynamoDB for an S3 backend) holds a lock item during any plan/apply, so two people running Terraform at once can't corrupt state by writing to it concurrently. Full troubleshooting version is in the Terraform section earlier in this handbook.
  • On the common S3+DynamoDB backend, DynamoDB holds the actual lock record — Terraform checks it before any state-writing operation and releases it when the operation finishes.
  • A crashed or killed process can leave a stale lock behind — the scenario the earlier Terraform troubleshooting question walks through in full, including the safe way to clear it.
Q20Difference between count and for_each.
In one linecount indexes by number (0, 1, 2...); for_each indexes by a stable key. for_each is safer for anything you'll add to or remove from later — removing item #2 with count silently reshuffles and can recreate everything after it.
Q21How do you migrate Terraform state without recreating resources?
In one lineterraform state mv (or import, for resources not yet in state at all) — the point is telling Terraform "this existing resource is now represented by this address" without ever touching the real infrastructure.
  • terraform state mv — re-points an existing state entry to a new resource address (after refactoring a module, or renaming a resource) — the real cloud resource is untouched, only Terraform's record of it moves.
  • terraform import — brings a resource that already exists in the cloud, but isn't yet in state, under Terraform's management, by mapping its real ID to a resource address in config.
  • Migrating between two separate state files (e.g. splitting a monolithic state into per-service states) is the same state mv primitive, run against the target state via -state-out, or via state pull/push for a full manual migration.
  • The check that matters after any state surgery: terraform plan should show zero changes — if it wants to create or destroy something, the migration didn't fully line up.
Q22What is Terraform Drift? How do you detect it?
In one lineDrift is when real infrastructure no longer matches Terraform's state — detected with terraform plan (or plan -refresh-only to see it without risking an accidental apply). Full debugging workflow is in the Terraform section earlier in this handbook.

Q24Difference between IAM Roles and IAM Policies.
In one lineA Policy is the actual permission document — what's allowed on what; a Role is an identity something can assume, with one or more policies attached. You attach policies to roles, not the other way around.
  • IAM Policy — a JSON document defining permissions: which actions are allowed or denied on which resources, optionally under which conditions. Does nothing on its own until attached to something.
  • IAM Role — an identity that can be assumed — by a user, an EC2 instance, a Lambda function, or (via IRSA) a Kubernetes pod — with one or more policies attached defining what that identity can do once assumed.
  • The practical distinction day to day: roles are what you assign to a workload so it gets exactly the access it needs, temporarily, via STS-issued credentials; policies are the reusable permission content attached to potentially many roles.
Q25Explain VPC, Subnets, NAT Gateway, and Internet Gateway.
In one lineVPC is your private network; subnets carve it up (public = has a route to the internet gateway, private = doesn't); an Internet Gateway lets public resources reach the internet directly; a NAT Gateway lets private resources reach out without being reachable from it.
  • VPC — an isolated virtual network in the cloud account, with its own IP address range (CIDR block).
  • Subnets — subdivisions of the VPC's CIDR, typically one per availability zone for redundancy. "Public" or "private" comes entirely from the subnet's route table, not any special subnet setting.
  • Internet Gateway (IGW) — attached to the VPC, gives resources with a public IP a direct route to and from the internet. A subnet is "public" specifically because its route table sends 0.0.0.0/0 to the IGW.
  • NAT Gateway — sits in a public subnet, gives resources in a private subnet outbound-only internet access without ever being directly reachable from the internet — private subnets route 0.0.0.0/0 to the NAT Gateway instead of the IGW.
  • Also the classic hidden cost trap from the cost-optimization question earlier in this handbook — NAT Gateway bills per hour plus per-GB processed.

Security & Production
Q30How do you secure container images before deployment?
In one lineScan for known CVEs before the image ever reaches a registry, run as non-root with a minimal base, and sign it so what gets deployed is provably what was scanned.
  • Vulnerability scanning (Trivy/Grype) against the built image before push — catches known CVEs in OS packages and application dependencies baked into the image.
  • Minimal base images (distroless or slim variants) — fewer packages means fewer potential CVEs and a smaller attack surface.
  • Run as a non-root user (USER directive), and avoid privileged mode or unnecessary Linux capabilities.
  • Multi-stage builds so build tools and source code never end up in the final image layer.
  • Image signing (Cosign/Sigstore) plus an SBOM, so anything running in production can be verified as coming from the actual pipeline run that scanned it — full pipeline placement for all of this is in the DevSecOps pipeline question earlier in this handbook.
Q31How do you implement RBAC in Kubernetes?
In one lineA Role or ClusterRole defines what actions are allowed on which resources; a RoleBinding or ClusterRoleBinding grants that to a user, group, or ServiceAccount — least privilege by only ever binding the narrowest role that covers what's needed.
  • Role — namespace-scoped permissions. ClusterRole — the same idea, cluster-wide or for non-namespaced resources (nodes, PersistentVolumes).
  • RoleBinding — grants a Role (or ClusterRole) to a subject within one namespace. ClusterRoleBinding — grants a ClusterRole across the whole cluster.
  • Bind to the narrowest role that covers the actual need — a ServiceAccount that only reads ConfigMaps in one namespace shouldn't hold a ClusterRole with wildcard permissions because it was convenient to copy.
  • ServiceAccounts are the subject for workload identity specifically — the same mechanism IRSA builds on for granting AWS permissions to a pod, covered in the EKS section earlier in this handbook.
  • Auditing RBAC in a real cluster means checking for over-broad bindings as much as missing ones — a wildcard resources: ["*"] added "to get something working" tends to outlive the reason it was added.
Q32How do you manage secrets in production?
In one lineNever in Git, even encrypted — a dedicated secrets manager or a Kubernetes-native tool fetches the real value at runtime, with access controlled by IAM/RBAC rather than by who can read a file.
  • Kubernetes Secrets alone are base64-encoded, not encrypted — real protection is etcd encryption-at-rest plus RBAC restricting who can read Secret objects.
  • A dedicated secrets manager (AWS Secrets Manager, Vault) or External Secrets Operator keeps the actual sensitive value out of Git entirely and centralizes rotation, audit logging, and access control in one place.
  • Rotation should be routine, not incident-driven — a credential that's never rotated has a blast radius, if leaked, that's unbounded in time.
