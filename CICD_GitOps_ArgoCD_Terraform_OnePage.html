CI/CD WITH GITHUB ACTIONS, GITLAB CI, GITOPS, ARGOCD, KUBERNETES & TERRAFORM — COMPLETE GUIDE IN ONE PAGE
CI (GitHub Actions / GitLab CI) builds & pushes images. GitOps (ArgoCD) pulls & deploys from Git. Terraform provisions the infrastructure everything else runs on.

1. WHAT IS CI/CD + GITOPS?

  • CI — build, test, containerize on every push (GitHub Actions / GitLab CI).
  • CD (GitOps) — a controller (ArgoCD) inside the cluster pulls desired state from Git and reconciles it.
  • Git is the single source of truth for what's running in prod.

2. WHY GITOPS (PUSH CI / PULL CD)?

  • No external system holds cluster credentials — ArgoCD's in-cluster identity does the applying.
  • Full audit trail: every prod change is a Git commit.
  • Rollback = git revert, not a manual kubectl fix under pressure.
  • Self-heal: manual drift gets reverted back to Git automatically.

Terraform provisions and owns the cluster, IAM/OIDC roles, ECR repo, VPC/networking, and typically bootstraps ArgoCD itself (Helm release). Once the cluster and ArgoCD exist, Terraform steps back — app-level changes flow through CI → GitOps repo → ArgoCD, never back through Terraform.

Rule of thumb: if it's "does this resource exist," it's Terraform. If it's "what version of the app is running," it's GitOps/ArgoCD. Mixing the two (e.g. Terraform managing Deployments) causes constant drift fights with ArgoCD.

9. ROLLBACK STRATEGY BY LAYER

Problem is in...How to revert
App code (bug in commit)git revert on Repo A → CI rebuilds a new safe image → new tag flows through pipeline normally (never re-deploy an old broken tag by editing it)
GitOps repo (bad tag/config bump)git revert the offending commit on Repo B → ArgoCD auto-detects and re-syncs to the prior good state
Need it instantly, can't wait for Gitargocd app rollback <app> <prior-revision-id> — reverts live state immediately; follow up with the matching Git revert so Git and cluster don't drift apart
Emergency, ArgoCD itself unavailablekubectl rollout undo deployment/<name> — last resort; ArgoCD will show OutOfSync afterward until Repo B is also fixed
Infra-level (bad Terraform apply)terraform plan against previous known-good tfvars/state, review, then apply — never hand-edit state; use terraform state commands carefully if state itself is inconsistent

15. BEST PRACTICES

  • Tag images with immutable git SHA, never "latest," in the GitOps repo.
  • Require PR review on the GitOps repo (Repo B) — CODEOWNERS for prod paths.
  • Manual ArgoCD sync gate for prod; automated+selfHeal fine for dev/staging.
  • OIDC federation for CI → cloud auth; no long-lived static credentials anywhere.
  • Readiness probes that check real dependency health, not just "process alive."
  • Database migrations always backward-compatible (expand/contract), never a breaking change tied 1:1 to a deploy.
  • Terraform remote state with locking (S3+DynamoDB / Azure equivalent) — never local state for shared infra.
  • terraform plan reviewed in CI/PR before any apply touches prod infra.
  • Rollback path tested before you need it — know the exact commands under pressure.
